# 第35回：終局理由の拡張

実施開始日：2026-09-23

## 目的

第34回まで詰みだけを終局としていたCLIに、投了による終局を小さく追加する。投了の入力形式、投了側と勝者の表示、詰みとの優先順位、EOF/Ctrl-Cとの差を確認し、設計承認後にTDDで実装する。

## 一次資料で確認した規則

日本将棋連盟の対局規則第6条第1項は「対局は詰みまたは相手の投了によって終了する」と定める。第2条第4項は詰ました側の勝利と詰まされた側の敗北を定める。公式の説明でも、負けを悟った場合に詰む前に投了することが普通だと説明されている。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[日本将棋連盟「王手と詰み」](https://www.shogi.or.jp/knowledge/shogi/04.php)

## 確認問題と回答

### 第1問：投了の入力形式

問題：投了を表すCLI入力を何にするか。

提示した推薦：`resign` の1語だけを半角ASCIIで受け付ける。

本人の回答：ok

合意：`resign` を投了入力とする。

### 第2問：投了側と勝者の表示

問題：手番側が投了したとき、投了側と勝者をどのように表示するか。

提示した推薦：先手なら「先手が投了しました。後手の勝ちです。」のように両方を表示する。

本人の回答：推薦を採用

合意：投了側と相手の勝者を一度に表示する。

### 第3問：詰みとの優先順位

問題：詰みと投了が重なり得るCLI上の順序をどうするか。

提示した推薦：入力を求める前に詰みを確認し、詰みなら投了入力を受けず詰みとして終了する。

本人の回答：推薦を採用

合意：詰みを投了入力より優先する。

### 第4問：EOF/Ctrl-Cとの差

問題：EOF（Ctrl-D）とCtrl-Cを投了と区別し、勝敗なしで終了するか。

提示した推薦：従来どおり「入力を終了しました。」で正常終了し、勝者を表示しない。

本人の回答：推薦を採用

合意：明示的な `resign` だけが投了であり、EOF/Ctrl-Cは勝敗にしない。

## 設計合意と承認

設計承認日：2026-09-23

`cli.py` に凍結データクラス `_ResignCommand` を追加し、`parse_command` が厳密な `resign` を返す。`run_game` は入力前に既存の詰み判定を行い、投了なら `Position.side_to_move` を投了側として勝者を表示し、局面・手番・持ち駒を変更せず終了する。`movegen.py` の `is_game_over` は詰みだけを判定する。EOF/Ctrl-Cは従来どおり終了メッセージだけを表示する。

## 最後の理解確認

問題：なぜ `resign` は `is_game_over(position)` に追加せず、CLIの入力イベントとして処理したのか。

本人の回答：局面だけからでは投了がわからないため

補足：その通り。詰みは盤面・手番・持ち駒から判定できる局面の性質だが、投了は手番側が入力時に行う意思表示である。そのため `is_game_over(position)` は詰みの判定に保ち、`cli.py` が `resign` を受け取った時点で投了側と勝者を表示して終了する。
