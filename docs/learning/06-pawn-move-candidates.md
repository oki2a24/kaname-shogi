# 第6回：歩の移動候補

## 学習の目的

歩の向き、盤外、移動先の駒を筋・段で判断し、候補を調べる処理と実際に指す処理を区別する。今回は学習までとし、関数の設計と実装は次のタスクで行う。

## 要点

- 先手の前は段−1、後手の前は段＋1。筋は変わらない。
- 計算先が盤外なら、通常の結果として「候補なし」にする。盤内の場合だけ `Square` を作る。
- `Square` 自体の不正値チェックも維持する。
- 移動先が自駒なら候補から除外し、空マスまたは相手の駒なら候補に含める。
- 候補生成は盤面や手番を変更しない。実際の移動・駒取り・持ち駒への追加は別の処理である。
- 王手などは検証しないので、今回の候補は合法手の確定ではない。

## 確認問題・回答と補足

1. 先手７七の歩が一歩前へ進むマスはどこか。
   - 回答：７六になる。
   - 評価：正解。
2. 後手７三の歩が一歩前へ進むマスはどこか。
   - 回答：７四になる。
   - 評価：正解。
3. 成りを脇に置いて座標を計算し、先手の一段目から段0になった場合、候補に含めてよいか。
   - 回答：だめ。段0は将棋の盤に存在しない場所なので行けてはだめ。
   - 評価：正解。これは盤外の計算の確認であり、未成の歩が最奥段に残る合法局面を想定したものではない。
4. 盤内の確認は `Square` の生成前か後か。
   - 回答要旨：設計次第。LaravelのForm Requestの経験から、事前チェックして正しい値だけ渡す方がしっくりくる。ただし将棋プログラムでのベストプラクティスは分からない。
   - 補足：単純な正誤問題ではないと確認し、利用者の依頼で一次資料を調査した。調査と合意は後述。
5. 先手７七の歩の前、７六に先手の金がある場合、進めるか。
   - 回答：進めない。同じマスに複数の駒が存在することはできないから。
   - 評価：正解。自駒のマスは候補から除外する。
6. ７六に後手の金がある場合、駒の動きと駒取りだけを考えると進めるか。
   - 回答：進める。歩が後手の金を取り、歩は７六にいる状態になる。
   - 評価：正解。実際に指す際には金が先手の持ち駒になることを補足した。
7. ７六を候補として返しただけで、盤面の書き換えが必要か。
   - 最初の回答：ある。歩の位置が変わり、取った後手金を消す必要があるため。
   - 補足：これは実際に指す処理。候補を調べるだけではまだ手を選んでおらず、盤面を変更しないと説明した。
   - 再確認：まだ指していない場合、歩はどこに残るか。
   - 最終回答：７七。まだ指していないので移動していないため。
   - 評価：説明後に、候補生成と指し手適用の違いを確認できた。最初から正解したとは記録しない。

## 盤外判定の調査と合意

LaravelのForm RequestはControllerの呼び出し前に入力を検証する。利用者はこの経験との対応を考えていた。一方、今回は正しい出発マスから計算しても盤外になることがあり、外部入力の不備とは異なる。

確認した `python-shogi` は歩の利きを事前計算し、ビット移動と盤内への制限で盤外を結果に残さない。やねうら王は歩の利きの集合と生成対象の集合から指し手を作る。確認した候補生成処理では、不正な座標の生成例外を捕捉する方式を通常の盤外除外には使っていなかった。

これらは検証付きdataclassの `Square` と同一の表現ではなく、将棋ソフト全体の唯一のベストプラクティスを証明するものでもない。今回の設計への提案として「盤外の除外を候補計算の通常処理として行い、盤内なら `Square` を生成する」と整理した。利用者は「その考え方でok」と承認した。ビット演算は導入しない。

`Square` の検証は、不正なマスをどの呼び出し元からも作らせない役割として残す。例外は捕捉すれば継続可能であり、必ずプログラム全体を停止させるものではない点も説明した。
