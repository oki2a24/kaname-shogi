# 第42回：CLIでの明示的な保存・読込

実施開始日：2026-09-27
設計承認日：2026-09-27
実装完了日：2026-09-27（main取り込み前）

## 目的

第37回で実装した `GameRecord.save(path)` / `GameRecord.load(path)` をCLIの人間入力へ接続し、対局中に `save <path>` と `load <path>` を明示的に実行する。保存形式を担う `GameRecord` と、入力・表示・再入力・進行を担うCLIを分離し、読込後の局面・手番・履歴を安全に再開できるようにする。

## 一次資料で確認したこと

日本将棋連盟の対局規則第2条は、対局を初手から終局まで指し手を進めるものとし、第6条は詰みまたは相手の投了による終了を定める。棋譜利用のガイドラインは、指し手進行を再現した盤面図と指し手順の文字情報を棋譜と説明する。

今回は公式棋譜形式や時間記録を実装せず、既存の自作JSON棋譜をCLIから明示操作する範囲に限定した。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[棋譜利用のガイドライン](https://www.shogi.or.jp/kifuguideline/)

## 確認問題と回答

### 第1問：save/loadの入力形式と保存先

問題：CLIの保存・読込コマンドの入力形式とパスの扱いをどうするか。

提示した推薦：半角ASCIIの `save <path>` / `load <path>` とし、相対パス・絶対パスを一語として `Path` へ渡す。親ディレクトリは自動作成しない。

本人の回答：1

補足：この形式を採用し、保存先の解決をCLI独自の固定ディレクトリへ広げない。

合意：`save <path>` / `load <path>`、相対・絶対パス、親ディレクトリ非作成。

### 第2問：読込後の局面・手番・表示

問題：`load` 成功後に、局面・手番・表示・担当をどうするか。

提示した推薦：読込んだ新しい `GameRecord` へ置き換え、再現された盤面・手番・持ち駒を表示し、その手番の担当に従って人間入力またはコンピュータ手へ進む。

本人の回答：1

補足：読込直後の表示を行い、読込前の進行へ誤って戻らない。

合意：完全に読込んだ記録へ置換し、表示後に読込後の担当へ進む。

### 第3問：失敗時の再入力

問題：入力形式、保存先、JSON、履歴再適用の失敗時をどう扱うか。

提示した推薦：`エラー：...` を表示し、局面・手番・履歴を変えず、同じ人間手番で再入力する。`load` は完全成功後だけ置換する。

本人の回答：1

補足：`ValueError` と `OSError` を空記録や部分読込へ変換しない。

合意：失敗時は既存記録を保持し、同じ手番で再入力する。

### 第4問：終局状態

問題：詰み、投了、EOF、Ctrl-C、コンピュータの合法手空一覧の後にsave/loadを受け付けるか。

提示した推薦：終局・終了判定を先に行い、終了後は入力を受け付けない。自動保存も追加しない。

本人の回答：1

補足：対局中に明示的に保存した記録を、後の対局開始時に `load` することはできる。

合意：終了後は保存・読込を含む入力を受け付けない。

### 第5問：GameRecordの置換と記録範囲

問題：読込前後の記録と、保存・読込・終了イベントを履歴へ残すか。

提示した推薦：`load` 成功時に記録を完全置換し、読込前の手、保存・読込、投了、EOF、Ctrl-C、エラーは履歴へ残さない。読込後の成功した `move` / `drop` だけを読込済み履歴の末尾へ追加する。

本人の回答：1

補足：保存形式と `GameRecord` のAPIは変更しない。

合意：成功した指し手だけが履歴に残り、`load` は完全置換として扱う。

### 第6問：責務の切り分け

問題：保存形式を担う `GameRecord` と、CLIの入力・表示・再入力をどこで分けるか。

提示した3案：

1. 推奨：CLIに `_SaveCommand` / `_LoadCommand` を追加し、CLI進行が既存 `GameRecord.save` / `GameRecord.load` を呼ぶ。
2. `GameRecord` がCLI文字列を解釈する。
3. 保存・読込専用の新しい管理クラスを導入する。

本人の回答：良い

合意：推奨案1。`GameRecord` は変更せず、CLIだけを拡張する。
