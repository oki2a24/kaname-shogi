# 人間とCodexの共同作業で使う文書を整える

## 目的

強い将棋エンジンを追加する前に、文書を使って共同作業の現在地・合意・根拠・履歴へ無理なくたどれる状態を整える。常時指示を必要な範囲に保ち、セッション再開時の読み込みを選択的にする。次テーマを選んだ後は、別の希望がなければ新しいセッション用の引き継ぎを作り、本人が入力してから次テーマを始める。

## 調査した原則と今回の適用

- [OpenAI: Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)：常時適用する `AGENTS.md` は必要性を見直し、すべての作業で大きな資料を読むよう求めず、関連する資料へ条件付きで案内する。
- [Diátaxis](https://diataxis.fr/) と [Google Technical Writing: Audience](https://developers.google.com/tech-writing/one/audience)：学習、作業手順、確定情報の参照、背景説明を読み手の目的に合わせる。今回、既存文書を観点別に整理したが、空の分類を作る全面移行はしない。
- [Write the Docs: Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) と [GitLab Documentation Style Guide](https://docs.gitlab.com/development/documentation/styleguide/)：文書をGit差分としてレビューし、ファイル・見出しへのリンクを確認する。AIが作成した文書は、根拠・対象範囲・重複・実際のリンクを確かめる。

今回のプロジェクト向けの適用は、Git状態と短い再開案内を再開時の基点にすること、`docs/README.md` を目的別索引にすること、READMEを機能・使い方・開発環境の必要時に読むこと、現行情報と履歴の正本を分けること、各段階の更新契機を定めることとした。

## 合意した範囲

本人は、より強い将棋エンジンを追加する前に文書整理を行うことを選び、計画作成と実施を承認した。対象は `AGENTS.md`、文書更新ガイド、docs索引、再開案内、次テーマ候補・選定履歴、今回の学習記録。READMEとプロジェクト方向性は監査し、必要がある場合に限って変更する。コード・テスト・設定・ShogiHome操作、強いエンジンの設計や実装は対象外。文書だけの変更のためコードテスト・Ruffは実施しない。

## 実施した変更

- `AGENTS.md` のセッション再開案内をGit状態と `docs/resume.md` にし、README・索引・テーマ資料を目的に応じて選ぶ形へ変更。
- 次テーマを選んだ後は、本人が別希望を出さない限り、新セッション用の引き継ぎを作る既定を追加。再開プロンプトの入力前に次テーマを開始しない条件を維持。
- `docs/documentation-guide.md` に上記の参照順と引き継ぎ規則を反映。
- `docs/README.md` に現在の入口と文書の役割を反映。現在状態の正本を `docs/resume.md` に寄せた。
- `docs/next-topics.md` の古い候補・選定経緯を履歴へ移し、過去文書からの直接リンクに使う3見出しを案内として維持。強いエンジンと方式別ファイル分離の希望、未決定事項を保留欄に残した。
- `docs/next-topics-history.md` 末尾に「現在のテーマと状態」から「選定履歴」までの276行を時点付きで保存。旧アンカー案内3節は現行の `docs/next-topics.md` に維持した。作業開始HEADは `4fa5279`。
- READMEと `docs/02-project-direction.md` は今回の範囲と矛盾しなかったため変更しない。

## 検証

変更文書とそれを参照する文書のローカルリンク659件について、相対パスと見出しアンカーを検査し、すべて解決した。作業開始HEADの `docs/next-topics.md` から保全した276行は、一時保存した原文およびhistory末尾の本文と完全一致した。`git diff --check` と、変更対象文書の末尾改行・行末空白を確認した。変更パスは計画対象の文書8件のみ。コードテストとRuffは文書のみの変更なので実行していない。

## Refactorの要否

製品コードのRefactor対象はない。文書構成では、現在の候補欄と過去の選定履歴を分け、再開案内を現在状態の正本にする整理を実施した。独立レビュー後に追加の整理が必要か確認する。

## 独立レビュー

独立レビュアーはCritical 0件、Important 0件、Minor 1件と判断した。Minorは履歴保存範囲の説明不足で、旧アンカー案内3節が現行 `docs/next-topics.md` に残ることを明記して解消した。修正後にリンク・履歴一致・差分検査を再実行した。追加の未解決指摘はない。

## 振り返り

現在地、利用者向け概要、文書索引、確定知識、判断理由、開始時点の引き継ぎ、過去候補履歴を目的別に分けると、再開時に読む量を減らしながら判断の根拠を保てる。入口を短くする作業では、既存の相対リンクとアンカーを確認してから履歴を移す必要がある。テーマ完了後、本人が次テーマを選んだ時に新セッション用の引き継ぎを提示する流れを既定にする。

## 最後の理解確認

確認問題：セッション再開時、現在地を確かめる入口は何で、詳細資料をどのように選びますか？

本人の回答：

アシスタントの補足：再開時はまず `git status --short --branch` で現在のチェックアウトと変更状態を確認し、`docs/resume.md` で現在地・承認段階・未完了事項を押さえる。READMEは機能・使い方・開発環境を確認するときに読み、その他の仕様・計画・知識・学習記録は `docs/README.md` から作業目的に応じて選ぶ。過去の引き継ぎや記録にあるGit状態・検証結果は作成時点の履歴として扱い、現在値と照合する。

確認結果：本人の回答はGit状態と再開案内を入口にし、目的に応じて詳細資料を選ぶ要点を押さえている。
