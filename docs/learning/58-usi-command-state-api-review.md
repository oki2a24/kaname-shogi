# 第58回：USIコマンド型・独立状態APIの導入要否を再検討する

## 目的

ShogiHomeで `kaname-shogi` と平手対局する大テーマの途中として、第57回で追加した `run_usi_engine` の局面保持とUSIコマンド分岐を別々に見直す。USIの一次資料、ShogiHome 1.28.1の使い捨てプローブで観測した一例、ローカル実装、未確認のShogiHome挙動を分け、後の実装要件を先取りしない。

## 資料と根拠の範囲

- [USI一次資料](https://hgm.nubati.net/usi.html)にはGUIからエンジンへ送るコマンドや `go` の引数が記載されている。資料にある全コマンドをShogiHomeが送る、または本実装が対応すべきとは判断しない。
- [第54回の観測記録](54-usi-shogihome-connection-scope.md)にあるのは、使い捨てプローブとの単一対局で受信したコマンド列と投了応答後の終了通知である。合法な `bestmove` に対するShogiHomeの挙動や、複数手の通常対局を確認した証拠ではない。
- 第57回のローカル実装は文字列分割と `if` / `elif` でコマンドを処理し、`position startpos moves ...` の局面を関数内に保持していた。`go` は既存の合法手列挙・弱い一手選択・USI表記へ委譲し、乱数生成器を一回の実行中に再利用する。
- `kaname-shogi` 自身をShogiHomeに登録した実対局は未確認であり、ロードマップ第5項の後続テーマに残す。

## 本人との設計確認

| 論点 | 本人の選択 | 設計への反映 |
| --- | --- | --- |
| コマンド行を型で表すか | 既存の文字列分岐を維持 | 全コマンド用の型やパーサーを先行して作らない。 |
| 局面状態の持ち方 | `Position` だけを持つ非公開状態オブジェクト | `_UsiEngineState` を `usi_engine.py` 内に置き、公開・独立モジュールのAPIにはしない。 |
| 乱数器の位置 | 手選択処理側に残す | `run_usi_engine` が一回の実行中の乱数器を保持し、`usinewgame` 後も再利用する。状態クラスは乱数器や選択方式を持たない。 |
| 状態オブジェクトの操作 | 置換・消去・取得を持つ案を了承 | `replace_position`、`clear_position`、`require_position` の三操作とする。 |
| 将来の強いエンジン | 今回は抽象化しない | 内部探索と外部エンジン接続は別の要件ができた時点で、局面状態とは別の境界として設計する。 |

本人は設計案、設計仕様、実装計画を明示的に承認した。実装計画作成中のテスト期待値の修正理由は[実装計画](../plans/2026-10-04-usi-command-state-api-review-implementation-plan.md)と作業台帳に記録した。

## 学んだこと

- 「コマンド行をどう表すか」と「最新局面をどこで管理するか」は別の判断である。状態をまとめる理由だけでは、コマンド行の型までは必要にならない。
- `_UsiEngineState` は現在の `Position` または `None` を表す状態データであり、そのライフサイクルを操作する。将棋規則、USI文法、棋譜、乱数器、合法手選択を所有しない。
- 乱数器は現在の最弱選択器の実装詳細であり、USIから受け取った局面状態の一部ではない。将来より強い内部選択を試す場合も、この局面保持クラスをそのまま選択器の抽象へ膨らませずに済む。外部エンジン接続が具体化した場合は、別プロセスとのUSI通信を担う境界を別途設計する。
- `Position` は可変の局面で、値比較は盤 `Board` の値比較を意味しない。別々に再現した局面をテストで比較するのではなく、実際に解析された同一オブジェクトが次の処理へ渡ることを確認する。

## 実装と確認

- `kaname_shogi/usi_engine.py` に非公開 `_UsiEngineState` を追加し、`Position | None` と三つの操作だけを持たせた。
- `run_usi_engine` の文字列分岐は維持した。`position` は解析後に状態を置換し、`usinewgame` は状態を消去し、`go` は状態から局面を要求する。乱数器の生成場所と寿命、選択処理は変更していない。
- 状態APIのテストを先に作り、未実装型を示すアサーション失敗3件を確認した。最小実装後は状態テスト3件が成功した。
- 最後の `position` を使うテストでは、別々に解析した `Position` の比較が失敗した。原因は各 `Position` が別の `Board` オブジェクトを持ち、`Board` が値比較を定義していないことだった。実解析結果を記録し、2回目の解析オブジェクトそのものが `legal_moves` に渡ることを確認するテストに直した。修正後の専用USIテストは17/17件成功した。
- Refactor確認では、局面状態と選択処理の境界を保つ追加構造変更は不要と判断した。公開docstringに非公開状態と乱数器の責務分離を追記した。
- 独立コードレビューはCritical 0、Important 0、Minor 0で、コード修正は不要だった。レビュー対象の専用USIテストは17/17件成功した。
- 文書承認前の最終独立レビューでもCritical 0、Important 0、Minor 0だった。新しいレビュアーがコード・テスト・設計仕様・実装計画・学習記録・知識メモを照合し、Review Focusを確認した。専用USIテスト17/17件、全体テスト281/281件、`git diff --check` の成功も再確認された。修正はなかった。
- 専用USIテストは17/17件、全体テストは281/281件が成功し、追跡中の差分に `git diff --check` のエラーはなかった。本人は文書内容を承認した。作業ブランチへの記録後、`main` への取り込みは別途承認と取り込み先検証を経る。ShogiHome実対局は行っていない。
