# CLIで読込失敗時の表示と状態保持を一回観察する

## 目的・範囲

2026-10-20、通常CLIを人間対コンピュータ・ランダム方式・10分・30秒で一回起動し、二手後の先手人間番で、時計つきセッションの読込失敗を二例観察した。実際の端末出力と失敗前後に保存したJSONを記録する。

対象はCLIの手動操作と観察記録まで。製品コード・テスト・設定・承認済み設計は変更していない。自動テストは実行していない。旧v1棋譜の読込は資料上の互換経路として照合したが、今回CLIでは実行していない。最後の理解確認への本人回答とアシスタント補足を2026-10-21に追記し、このテーマは完了した。

## 実行した一回

リポジトリ直下で通常CLIを起動した。

```sh
python3 -m kaname_shogi
```

入力条件は対局形式`2`（人間対コンピュータ、先手人間）、方針`1`（ランダム）、持ち時間`10`分、秒読み`30`秒。先手人間は`move 7 7 7 6`を入力し、後手コンピュータは実際に`move 3 3 3 4`を指した。二手後の先手人間番を基準状態にした。CLI表示では後手の消費時間は`0.012秒`、残りは`09:59.987`だった。

失敗前後の保存・候補ファイルは次の一時ディレクトリに置いた。

```text
/tmp/kaname-shogi-load-failure-observation.kYlsP7/
```

基準状態のJSONは外側形式`kaname-shogi-cli-session-v1`、内側形式`kaname-shogi-game-record-v1`だった。棋譜は先手`7七→7六`、後手`3三→3四`。時計は初期`600000ms`、秒読み`30000ms`、先手`600000000000ns`、後手`599987989416ns`。先手人間の入力中だった。

## 二つの読込失敗

### 1. 不正な棋譜・妥当な時計

候補棋譜は先手`7七→7六`、後手`3三→3四`、先手`7六→7四`。最後の手は歩の二マス移動で不合法。時計は初期`600000ms`、秒読み`30000ms`、先手`590000000000ns`、後手`580000000000ns`にした。

CLIに表示された`load`の実出力は次のとおり。読込失敗時、CLIは盤面や棋譜履歴を再表示せず、同じ入力プロンプトを表示した。下記はPTYから採取した`load`入力からプロンプト復帰までの全出力で、文言は整えていない。

```text
load /tmp/kaname-shogi-load-failure-observation.kYlsP7/case1-invalid-record.json
エラー：到着マスは出発駒の移動先候補に含まれません
指し手を入力してください（例: move 7 7 7 6）:
```

### 2. 妥当な棋譜・不正な時計

候補棋譜は先手`7七→7六`、後手`3三→3四`の二手。時計は初期`600000ms`、秒読み`30000ms`、先手残りをboolの`true`、後手残りを`580000000000ns`にした。

CLIに表示された`load`の実出力は次のとおり。こちらも盤面・棋譜履歴は再表示されず、同じ入力プロンプトへ戻った。これはPTYから採取した`load`入力からプロンプト復帰までの全出力である。

```text
load /tmp/kaname-shogi-load-failure-observation.kYlsP7/case2-invalid-clock.json
エラー：sente_remaining_nsは初期持ち時間内の非負整数nsが必要です
指し手を入力してください（例: move 7 7 7 6）:
```

## 前後JSONの比較

各失敗例の直前・直後に`save`し、読み取り専用のJSON比較で棋譜・時計とJSON全体を比較した。

| 失敗例 | 保存ファイル | `game_record.moves` | `clock` | JSON全体 |
| --- | --- | --- | --- | --- |
| 不正棋譜 | `case1-before.json` / `case1-after.json` | 一致。元の二手を保持 | 一致。先手`600000000000ns`、後手`599987989416ns` | 一致 (`True`) |
| 不正時計 | `case2-before.json` / `case2-after.json` | 一致。元の二手を保持 | 一致。先手`600000000000ns`、後手`599987989416ns` | 一致 (`True`) |

候補1の時計は先手`590000000000ns`・後手`580000000000ns`、候補2の時計は先手`true`・後手`580000000000ns`だった。いずれも読込後の保存JSONには採用されなかった。`save`前後で基準状態のJSON全体が一致したことは、今回の実行における状態保持の証拠である。プロンプトは先手人間入力中に同じ形で戻り、二手の履歴も保存JSONで保たれていた。画面上の盤面・履歴の再描画はなかったため、再表示されたと記録しない。

## 確認できたことと限界

- 不正履歴は妥当な時計と一緒でも受理されず、不正なbool時計は妥当な棋譜と一緒でも受理されなかった。
- どちらの失敗でも、実出力はエラーと入力プロンプト復帰を示し、読込前後の保存JSON全体が一致した。
- 時計がCLIに表示されたのはミリ秒粒度、JSON保存値はns粒度だった。今回の先手・後手の保存値と候補値は実測JSONから記録した。
- 観察は一回の実行・各失敗一回。時計なし旧v1の実読込、他の不正形式、他の対局条件は実行していない。自動テスト・テストスイートも実行していない。

## 最後の理解確認（2026-10-21）

**確認したいこと:** 読込失敗時に実際に画面へ出る情報と、盤面・棋譜・時計が保たれたと判断した根拠を区別して説明できるか。

**質問:** 二つの読込失敗でCLIには何が表示されましたか。また、盤面・棋譜・時計が元の状態を保ったと判断した根拠は何でしたか。

**本人の回答:**

> エラー：到着マスは出発駒の移動先候補に含まれません
> エラー：sente_remaining_nsは初期持ち時間内の非負整数nsが必要です
> 両例とも、失敗前後の保存JSON全体が一致、が根拠

**アシスタントの補足:** 一つ目の出力は不合法な移動、二つ目の出力は`true`の残り時計を非負整数nsとして受け付けないことを示した。両方ともCLIはエラー後に同じ人間入力プロンプトへ戻ったが、盤面・履歴を再表示してはいない。状態保持の根拠は、各例で読込前後に保存したJSON全体が一致し、その中の棋譜二手・盤面を再現する開始局面と履歴・時計値が変わらなかったこと。今回の二例で観察した範囲として記録する。

## 振り返り・次回への問い

二つの失敗ではエラーの文言が異なり、どちらも同じ人間入力プロンプトへ戻った。一方、CLIは失敗後の盤面・棋譜履歴を表示しなかったため、画面再描画と状態保持を混同せず、前後JSONを根拠にした。この実測は指定した二例に限られ、旧v1互換の実行や他の不正例の保証ではない。
