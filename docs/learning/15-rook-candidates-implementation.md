# 第15回：飛車の候補生成の実装

## 目的と実装範囲

承認済み計画[飛車の実装計画](../plans/2026-09-17-rook-move-candidates.md)に従い、成る前の飛車の移動先候補を実装した。`rook_move_candidates(board, source)`は盤面と出発マスを受け、右・左・前・後ろの順に各方向を近い順で走査する。盤面の変更、手番による制限、成り、王手、合法手の確定、実際の移動や駒取りは扱わない。

## TDDの実施記録

### タスク1：入力契約

開始時に既存54テストの成功を確認した。テストから`rook_move_candidates`をimportした直後のImportErrorは、関数未定義による準備段階として扱った。その後、仮関数を置いて対象テストを実行し、空マスと飛車以外でValueErrorが出ないという振る舞いのRedを確認した。

最小実装で出発駒の存在と駒種を確認し、該当しない場合にValueErrorを送出した。対象3テストがGreenになった。

### タスク2：開いた盤面の4方向

５五の飛車について、右（筋−1）、左（筋＋1）、前、後ろを固定順で返すテストを追加した。仮関数では16候補を返せずRedを確認した。

最小実装として、先手の前を段−1、後手の前を段＋1とし、4方向の筋・段の増減を順番に走査した。空マスを候補へ追加し、16候補のテストがGreenになった。

### タスク3：停止条件と境界

自駒の手前で止まること、相手駒を最後の候補に含めて止まること、1方向の停止が他方向を妨げないこと、端で盤外へ出ないことをテストした。タスク2の一般化した走査がすでに停止条件と境界も実装していたため、追加テストは追加時からGreenだった。未実施のRedを実施済みとは記録しない。

### タスク4：契約とRefactor

候補計算後の全81マス不変、呼び出しごとのリスト独立性、手番によらず出発駒の所有者から計算することをテストした。これらも既存実装で満たされていたため、追加時からGreenだった。

Refactorでは、方向の増減を`directions`というデータにまとめ、4方向で同じ走査処理を共有していることを確認した。`next_file`、`next_rank`、`occupant`、`candidates`の名前は、それぞれ次に調べる筋・段、そのマスの駒、候補リストを表しており変更不要と判断した。公開docstringには引数、戻り値、例外、副作用、前提条件、方向順を記載した。香との共通化は、今回の学習範囲を広げないため行わなかった。
