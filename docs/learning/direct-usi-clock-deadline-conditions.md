# 直接USIで時計期限停止を確認する条件

## 学習の目的

時計引数付きUSI `go` から内部の探索期限と応答までを、ホストが送る通常 `stop` と区別して確認する条件を設計する。既存検査が示す範囲と直接プロセスで観測した一例を分け、外部時系列が内部停止の因果証明ではないことを説明できるようにする。

## 要点

- 時計予算は現在手番側の `btime`/`wtime` と秒読みから計算される。今回の後手番局面では `wtime 0 byoyomi 12000` と現行設定により目標7500ms・上限10000msとなる。
- 時計期限は協調確認点で処理される。目標期限では次の根候補を止めるが、評価中の候補は完了しうる。期限後の即時応答や実時間内完了は保証されない。
- 直接USIの記録器が測った起点は `go` のstdin flushで、エンジン内部の完成行読取時刻ではない。通常 `stop` を送らないことでその入力経路を排除できても、USI応答には停止理由が出ないため内部期限発火の完全な因果証明にはならない。
- 現行の時計計算・固定時計境界・探索中断・送受信競合のテストは各契約を確認するが、OS実時間で時計期限だけにより実エンジンが停止したという一連の証拠は提供しない。
