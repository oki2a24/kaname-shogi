## 予備手準備の合意と、例外による中断への疑問

2026-10-18、本人は「予備手確保を準備処理として分ける」案に「はい」、続いて「準備で合法手なしなら、終了状態を手なし確定、返す手と反復完了記録をなしにする」案に「はい」と回答した。個別合意であり全体承認ではない。

その後、アシスタントは再帰の戻り値への状態追加を避けられることから専用例外による中断通知を推薦した。本人は「疑問が残る。中断は例外なのか？やりやすいのは理解できるが、例外を使用する本来の用途から外れているのではないか？バッドノウハウでない根拠を示して欲しい。」と質問した。例外方式への承認ではない。アシスタントは実装の変更量だけでは根拠が足りなかったと説明し、採用を保留した。

一次資料を確認した事実：

- [Python言語リファレンスの例外](https://docs.python.org/3/reference/executionmodel.html#exceptions)：エラーやその他の例外的状況で通常の制御フローを抜け、直接・間接の呼出し元で処理する仕組み。finallyによる後片付けも規定されている。
- [asyncioのタスク取消し](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)：取消し時にCancelledErrorを送出し、通常は後片付け後に伝播させる。握り潰すと構造化並行処理の動作を壊し得る。取消しを例外で伝える標準ライブラリの例だが、本プロジェクトは同期探索であり、その設計や型をそのまま移植する根拠ではない。
- [StopIteration](https://docs.python.org/3/library/exceptions.html#StopIteration)：反復の正常な終了を知らせる例外。言語の専用プロトコルであり、任意の業務分岐への例外利用を推奨する根拠ではない。

プロジェクトへの判断：時間による中断は想定内の終了理由であり故障ではない。ただし例外機構は故障専用とは限らず、専用型で多段の呼出しから探索境界へ抜ける案を直ちに誤用とは断定できない。一方、その事実だけでは今回に適するとは証明できない。例外案は途中の呼出し元での伝播確認漏れを避けやすいが、関数の戻り値から停止経路が見えず、広いexceptによる誤捕捉・後始末の飛ばし・外への漏出に注意が必要。状態返却案は各段で分岐・伝播が必要だが、既存のcompleted付き結果と統一しやすく、学習目的に沿って経路を追いやすい。

「変更が小さいため例外を優先する」という先の推薦を見直し、既存方式との一貫性と説明のしやすさから状態返却案を優先して比較する判断を提示する。方式は未選定のまま。型・処理の比較例を用いて本人の理解を確認してから決める。コード・テスト変更や実験は行っていない。
