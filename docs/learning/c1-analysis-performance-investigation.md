## 現状と観測

- 現行readerは予定の順に一局ずつ `_load_game` を呼ぶ。全局の検証後にsummary再集計・組得点・信頼区間を計算し、最後に分析JSONを保存する。途中進捗の表示はない。
- `GameRecord.from_payload` が全手を合法再生し、その後 `_validate_and_replay` が計時・途中終局・最終終局を照合しながらもう一度再生する。
- `_validate_and_replay` は千日手終局以外の各手の後で `legal_moves(current)` を呼び、全合法手を列挙してから空かどうかだけを使う。
- 公開 `has_legal_move` も現状は `bool(legal_moves(...))` へ委譲するため、呼び名だけの置換では短縮しない。内部には最初の合法手で列挙を終える `_first_only` の仕組みがある。
- 同じ `_load_game` は局単位再開の保存局検証でも使う。変更する場合は完了局だけでなく中断・故障局を受け入れる経路も点検する必要がある。
- 稼働中の分析プロセスは確認時点でCPU約99%を使用していた。これは停止状態ではないという観測であり、何％の局を検証済みかを示す情報ではない。

参照コード：`kaname_shogi/comparison_result_io.py` の `load_completed_comparison`・`_load_game`・`_validate_and_replay`、`kaname_shogi/game_record.py` の `from_payload`、`kaname_shogi/movegen.py` の `legal_moves`・`has_legal_move`、`kaname_shogi/comparison_resume.py` の `load_resume_state`。

## 計測方法と結果

確認比較の局JSONだけを読み、各局面の手数中央値付近から一局ずつ選んだ。全4,080局の合計は781,361手、局JSONは計284,363,418 bytesだった。選定は性能調査用であり、棋力評価の標本選択・再分析ではない。

既存の `_load_game` をそのまま呼び、読込・decode時間と検証時間を `time.perf_counter` で一回ずつ測った。現行の分析CLIが同時稼働している環境での参考値である。

| initial | game-000129.json | 182 | 0.000327 | 3.318110 |
| open-bishops | game-001007.json | 184 | 0.000435 | 2.610298 |
| closed-bishop | game-001501.json | 198 | 0.000424 | 4.486358 |

198手の `game-001501.json` をcProfileで調べると、累積時間のほぼ全体が合法手列挙の経路だった。計測器による実行時間増加があるので、その絶対時間は通常実行の所要時間として使わない。一時出力は `/private/tmp/c1-analysis-current-profile.txt` であり、消える可能性がある。

同じ局で合法手列挙関数だけを、別プロセスの引数・戻り値を変えない一時的な計時wrapperで再計測した。検証全体4.491057秒、列挙198回の計4.424513秒、比率98.5183%だった。JSON読込や二重再生の整理より、中間局面の全合法手列挙を減らすことを先に検討する根拠になる。6局は全局面・手数分布を代表する保証がなく、全分析の完了時間や改善倍率はこの結果から確定できない。

## 短縮候補とアシスタントの推薦

| 候補 | 根拠と利点 | 設計時の点検 |
| --- | --- | --- |
| 合法な次の記録手を「合法手が存在する」根拠として再利用 | 途中局面には、既存の合法再生で適用済みの次の手がある。存在判定のためだけに全候補を作る必要を減らせる。最終局面の検査は残す | 次の手を合法検証したという前提を維持する。千日手・手数上限は合法手があっても終局になるため、毎手の検査を残す |
| 合法手有無を最初の一手で確定 | 中間局面でも実際に探索して真偽を得る。内部の早期終了機構を調査できる | 公開APIと共通movegenへの影響、打ち歩詰め、先後・駒打ち・成り、局面不変性 |
| 局ごとの検証を複数プロセスへ配分 | 各局の読込・検証は独立している。全局検証後の集計を予定順に戻せる | 起動・転送費用、メモリ、最初の不正入力の扱い、割込み・終了回収、決定的な出力順 |

調査時の推薦は、まず「合法な次の記録手を根拠として再利用」の正しさと対象範囲を設計すること。この段階ではアシスタントの提案であり、本人の採用決定ではなかった。並列化と同時に導入すると、どちらが性能と挙動へ影響したかを切り分けにくいため、順番に評価する。

例として100手の合法棋譜なら、途中99局面には続く合法手が一つ記録されている。最終局面にはその根拠がないので、合法手の有無を現行どおり調べる。途中の千日手と手数上限は別に確認し、終局後の継続を拒否する。この根拠で保存結果の検証を保てるかを、実装前の設計で確定する。

進捗表示は待ち時間を把握するために有用だが、処理そのものの短縮とは別の候補であり、追加範囲は未選定。
