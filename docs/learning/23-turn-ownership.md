# 第23回：手番に合う駒だけを移動できること

## 目的

`Position.side_to_move` が表す「今指す側」と、出発マスの `Piece.side` が表す「駒の所有者」を区別する。`apply_move` は両者が一致するときだけ移動を適用し、不一致なら局面を変更せず拒否する最小範囲を学ぶ。

今回は、移動方向、候補生成結果との照合、駒取り、持ち駒、成り・不成、王手、王手放置を避ける合法手判定、詰み、CLI入力、評価、探索を扱わない。

## 要点

- 将棋は2人の対局者が交互に一手ずつ指し、先手番の対局者が開始する。
- `Position.side_to_move` は局面で次に指す側を表すデータである。
- `Piece.side` は盤上の各駒の所有者を表すデータである。
- `apply_move` は、出発駒の所有者と手番が一致しない場合に `ValueError` を送出し、盤面と手番を変更しない。
- 手番の照合は盤面移動と手番交代の前に行い、同じ側が連続して指すことを防ぐ。

## 出典

- [日本将棋連盟「将棋とは？」](https://www.shogi.or.jp/knowledge/about/)
- [日本将棋連盟「対局規則」第2条](https://www.shogi.or.jp/match/taikyoku_rules/)

## 確認問題と回答

### 第1問：手番と所有者の不一致

問題：先手番の `Position` で、出発マスにある駒が後手の駒だった場合、`apply_move` は盤面・`side_to_move`・例外をそれぞれどう扱うべきでしょうか？

本人の回答：盤面は変化させない・`side_to_move`は変化させない・例外を発生させる。

アシスタントの補足：正しい。出発駒の `Piece.side` と `Position.side_to_move` が違う場合は、`apply_move` が `ValueError` を送出する。盤面を動かす前、手番を交代する前に照合するため、盤面と `side_to_move` は不変である。

## 振り返り

本人の振り返り：引っかかっている点などはありません。

アシスタントの補足：手番は局面の状態、所有者は駒の状態であり、両者を照合してから移動を適用する必要がある点を確認した。次はこの最小範囲のAPI・失敗時の不変性・テスト方法を設計する。

## 次回への問い

手番と出発駒の所有者の照合を、既存の `move_piece` と責務を分けた `apply_move` にどの順序で加えるか。

## 実装・検証記録

- Redでは、所有者不一致を拒否するテストが、先手番で後手の歩、後手番で先手の歩の二つのケースで `AssertionError: ValueError not raised` となった。`apply_move` は読み込めており、所有者照合が未実装であることによる失敗だった。
- Greenでは、`apply_move` が出発駒を読み、駒が存在して所有者と手番が異なる場合に、盤面移動の前に `ValueError` を送出する最小実装を加えた。`move_piece` は変更せず、空出発・占有到着・同一マスの既存の拒否契約は維持した。
- 対象の `ApplyMoveTests` 3件、全98テスト、CLI実行、`git diff --check` を確認した。実行時点でいずれも成功し、差分形式の問題はなかった。
- Refactorでは、所有者照合を共通関数へ抽出したり、候補生成と結び付けたりしないと判断した。`apply_move` に局面の規則、`move_piece` に盤面変更を残す責務分離が、この範囲では最小である。
- 変更差分を設計書・実装計画と照合してコードレビューした。所有者照合が `move_piece` に混入していないこと、先後両方の成功と不一致時の局面不変性をテストしていること、対象外の規則を追加していないことを確認し、修正が必要な指摘はなかった。

## 実装後の理解確認

### 第2問：照合の順序

問題：後手番で先手の歩を指定して `apply_move` を呼んだとき、なぜ `move_piece` を呼ぶ前に所有者と手番を照合する必要があるのでしょうか？

本人の回答：後手番が先手の駒を動かすのはルール違反なので、実際に盤を変化させる前に対処する必要がある。

アシスタントの補足：正しい。所有者と手番を先に照合すれば、反則の移動により盤面が部分的に変わったり、手番が交代したりすることを防げる。`move_piece` は盤面専用の操作として残し、局面の規則である照合は `apply_move` が担当する。
