# 千日手ルールを学び設計する

## 学習の目的と進行状態

同一局面・4回出現・連続王手・棋譜履歴とSFENの違いを、日本将棋連盟の対局規則と現在のコードを使って学んだ。通常CLIでの適用範囲、保存と読込、探索・USIからの分離を決め、設計案と実装計画案を作成した。

本人は2026-10-22に設計案と実装計画を「承認する」と明示回答した。承認後、作業ブランチ `codex/repetition-rule` のworktreeでTDDによる実装を進め、Task 1〜5を完了した。実装コミット `4080c4a` を作成済み。mainへの取り込みは別承認、取り込み先検証後の最後の理解確認は未完了として扱う。

## 学習した要点

- 千日手の同一局面は盤上の駒配置、双方の持ち駒、手番がすべて一致した局面。棋譜の手数やSFEN手数は局面同一性に含めない。
- 一局中に同一局面が4回現れるのが通常の成立条件。連続王手の区間では王手を続けた側が負ける。
- 4回目が通常の千日手であっても指し継げば打開とされ、その局面へ再び戻らない限り指し直しにならない。
- 千日手は履歴に依存する。SFENは一局の過去の全局面を持たないが、開始局面と成功手を持つGameRecordからは再生して復元できる。
- 公式対局の指し直し規則と、比較CLIで本人が承認した「通常千日手を指し直さず別集計する」実験方針は別の仕様。
- 探索中の仮想局面を実対局履歴へ混ぜない。探索対応は今回除外し、将来必要になれば探索枝ごとに履歴を扱う必要がある。

根拠：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、現行のkaname_shogi/model.py、game_record.py、movegen.py、cli.py。実装観察にやねうら王、cshogi、ShogiHomeのコードを使った。ソフトごとの処理は、確認したソース箇所の実装例であり、将棋規則そのものや全ソフトの共通仕様ではない。詳しい仕様案と参照先は[千日手ルール設計案](../plans/2026-10-22-repetition-rule-design.md)。

## 設計の判断とトレードオフ

同一局面をキー値として正確に比較すれば、ハッシュ衝突を千日手の誤判定へつなげずに済む。一方、81マスと持ち駒の値を比較するため、ハッシュだけの高速比較より処理量が増える。現在の小規模なPythonエンジンでは、正しさの説明と確認のしやすさを優先する提案とした。

全棋譜を再生して読込時に履歴を再構成すると保存形式を変えずに済む一方、保存棋譜の手数に比例する再読込時間がかかる。通常の保存棋譜が現在の小規模利用であることを踏まえ、専用の履歴保存形式を足さない案とした。

通常CLIで4回目の通常千日手を通過させると公式規則の自動指し直しとは動作が異なるが、打開後の手順を学び扱う本人の選択を反映する。実装で違いを表示し、公式対局の裁定と混同しない。

双方が連続王手に該当する場合については、確認した一次資料に結果の裁定方法が明記されていない。本人は設計案・計画の承認時に、片側負けや通常千日手へ推測で分類せず未裁定の終局結果として停止する案を承認した。

千日手成立後の手も含む過去の保存棋譜については、終局後の続行として読み込みを拒否し、読込前の棋譜・時計を保つ案を記載した。既存CLIには千日手判定がなかったため、過去v1棋譜にはこの状況があり得る。本人はこの案も承認し、実装では候補棋譜の履歴再構成時に検出した。
