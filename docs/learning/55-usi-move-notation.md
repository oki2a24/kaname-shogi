## 既存データ境界

- kaname_shogi.move.BoardMove はsource・destination・promoteを持つ変更不可の盤上移動データ。
- DropMove はpiece_type・destinationを持つ変更不可の駒打ちデータ。Move は両型をまとめる型別名。
- kaname_shogi.model.Square は筋・段を1〜9で保持する変更不可の値。筋1は先手視点で右端、段1は上端。
- BasicPieceTypeは基本駒種8種類を表す列挙値。玉は持ち駒にならず、Hand（持ち駒枚数の可変データ）とapply_drop（局面に駒打ちを適用する操作）は玉を拒否する。

## USI一次資料の要点

USI原案では右上のマスを `1a`、左下を `9i` とする。将棋所の説明は筋を数字1〜9、段をa〜iとし、通常移動は出発・到着の連結、成りは末尾の `+`、駒打ちは大文字駒記号・`*`・打ち先と説明する。原案の持ち駒欄の駒種は飛・角・金・銀・桂・香・歩の7種である。

- [将棋所：USIプロトコルとは](https://shogidokoro2.stars.ne.jp/usi.html)
- [The Universal Shogi Interface (USI), original description](https://hgm.nubati.net/usi.html)

## 最後の理解確認

**質問：** USIの `7g7f` はどの `BoardMove` に対応し、この変換だけでは駒の動きや合法性を判定しないのはなぜか。

**本人の回答：** `BoardMove(Square(7, 7), Square(7, 6), False)`に対応する。この変換だけでは駒の動きや合法性を判定しないのは盤面の情報が無いため。

**アシスタントの補足：** `7g` は出発マスの `Square(7, 7)`、`7f` は到着マスの `Square(7, 6)`、成り記号がないため `promote=False` となる。盤面がないこの変換関数は、出発マスの駒や手番、移動先の状態、成りの可否を判断できない。ここでは一手表記と値の対応だけを扱い、局面に依存する合法性は局面処理の責務として残す。

この回答記録は本人の確認待ちであり、確認後に別コミットする。次テーマはまだ選定していない。
