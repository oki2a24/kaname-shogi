# Pythonユニットテストの並列実行

## 目的・範囲

2026-10-21、既存のPythonユニットテスト全体が約50秒かかる状況を受け、テストを削らずに実行時間を短縮できるか調べ、標準ライブラリだけの並列ランナーを実装した。実装計画は本人が承認した。

対象はテストモジュールの発見・実行方法と開発者向け案内。製品コード、テストの意味、既存テストの除外・skip・filterは変更していない。既存の逐次 `unittest discover` も維持した。作業は専用worktreeのブランチ `codex/parallel-unittest-runner` で行い、実装・レビュー後に別途承認を得てmainへ統合した。取り込み先の検証結果を以下に記録する。

## 実装前の調査と予備計測

READMEの従来コマンドは `python3 -m unittest discover -s tests -v`。`requirements-dev.txt` はRuffのみを固定し、pytestやpytest-xdistは含まれていなかった。使用中のPython 3.15にはunittest標準の並列オプションがなかった。

テストの分割単位をモジュールとし、それぞれを独立したPythonプロセスで標準 `unittest -v` に渡す方法を一時計測した。既存40モジュール・623件は4 workerで3回すべて成功し、17.147秒、17.337秒、17.894秒だった。比較した従来実行は49.689秒だった。この予備値は一回の逐次測定と同一ホスト上での比較であり、一般的な速度保証ではない。

## 実装内容

- `scripts/run_tests_parallel.py` が標準unittestと同じ有効な `test*.py` ファイル名を選び、`__init__.py` のあるpackageを再帰探索する。package自身もモジュールとして実行し、initializer内のTestCaseとimport失敗を検出する。
- workerのbootstrap内で `unittest.main(exit=False)` を呼び、testsディレクトリを `sys.path` の先頭に挿入する。これにより作業ディレクトリをリポジトリ直下に保ったまま、rootとtests内に同名ファイルがある場合も探索したtests側を実行する。0件モジュールを通常の失敗と誤認しないよう、終了値は `result.wasSuccessful()` から返す。テスト自体の失敗・import失敗は非0になる。
- 既定worker数はCPU数を超えず最大4。`--workers` で上書きでき、1未満は引数エラーにする。
- workerの出力をモジュール発見順に表示し、件数を集計する。一つでも失敗・起動エラーがあれば非0で終了し、失敗診断を保持する。workerでは `PYTHON_COLORS=0` を指定し、親環境の強制カラー設定によりskip件数の解析が崩れないようにする。
- テスト専用の契約テスト14件を追加した。有効なファイル名・package initializerのテストとimport失敗・空initializerと成功する子テスト・空package/test moduleのみの0件失敗・setup時skipのみの許容・同名モジュールの優先順位・1件と2件の件数・代表モジュールの実行記録・CLIからの失敗/起動例外/worker例外伝播・worker上限・無効値を独立した期待値で確認する。
- 人間向けの `README.md` に通常の実行方法・worker指定・逐次診断コマンドを載せた。AI作業者向けの `AGENTS.md` にも並列ランナーをPython全体テストの通常コマンドとして明記し、逐次実行を共有状態・順序依存・並列との差の診断に使う条件を加えた。

最初の契約テスト6件を実装前に実行し、探索結果が空、worker未使用、失敗が成功扱いなど、挙動に対する8件の期待違反を確認した。importや読み込みだけの失敗ではない。既定worker上限を追加して初版7件を成功させた。その後の独立レビューで、initializerテストの欠落、同名importの優先順位、CLI終了コードの未検証などを指摘された。CPythonの標準discoveryと小さな一時プロジェクトで挙動を再現し、追加した契約テストでは修正前に3つの振る舞いテストが失敗した。初回指摘への修正後、再レビューで「空initializerは0件で終了コード5となる」ことが分かり、空initializer＋成功する子テストのCLI回帰テストを追加した。さらに、全workerのテスト数が0でも成功扱いになる問題を確認した。標準discoveryの挙動を再現し、空package/test moduleのみは失敗、`setUpModule` がskipするmoduleのみは成功となる契約テストを追加した。全体0件のケースと強制カラー設定のケースは修正前に振る舞い失敗を確認し、`unittest.main(exit=False)`、テスト/skip数の集約、workerカラー無効化で対応した。修正後の専用契約テスト14件はすべて成功した。有効でない `test_alpha.copy.py` を除外し、1件・2件の期待値と代表モジュールの追記記録で件数と重複実行を検出する。

## 最終実測

worktreeは当初 `.venv` を持たず、実行ファイル経由の既存テスト3件が開発用Pythonの欠如で失敗した。テスト内容を変更せず、元の開発環境への一時 `.venv` symlinkを置いて環境条件をそろえた。該当モジュール8件が成功した。最終全体計測も同じ一時symlinkで実行し、終了後にsymlinkを削除した。

| 実行方法 | モジュール | 件数 | 所要時間 | 結果 |
| --- | ---: | ---: | ---: | --- |
| 並列・1回目 | 41 | 637 | 20.104秒 | 成功 |
| 並列・2回目 | 41 | 637 | 20.308秒 | 成功 |
| 並列・3回目 | 41 | 637 | 20.089秒 | 成功 |
| 標準逐次 `unittest discover` | 41 | 637 | 53.318秒 | 成功 |

追加した14件を含む同一637件で比べると、並列3回の平均は20.167秒、今回の逐次実行比で約2.64倍、経過時間は約62.2%短かった。初回に一時実行環境がなくランチャー関連3件が失敗したが、原因を環境に切り分けて条件をそろえた後、並列3回・逐次1回がすべて同じ637件で成功した。外側の計測スクリプトがコマンド起動も含むwall timeを記録している。

## 読み取れることと限界

- モジュール単位の別プロセス化で、この環境の全体経過時間が短縮した。各モジュール内では標準unittestのテスト意味とverbose表示を保つ。
- プロセス分割はモジュール間の共有状態を隔離するため、逐次実行と状態・順序の前提が異なる。逐次コマンドも残し、同じテスト数になることを確認した。
- 計測は一台・一Python環境での結果であり、別OS・CPU・負荷・テスト数で同じ倍率になるとは限らない。worker数の最適値も調べていない。
- モジュール出力はそのモジュール完了後にまとめて表示するため、実行中の逐次的なライブ出力ではない。
- 現在のtestsには独自 `load_tests` フックがない。initializer内の通常TestCaseとimport失敗は対象に含めたが、カスタムフックが独自suiteを組み立てたり、別モジュールを再発見する動作は検証していない。

## 検証・レビュー・統合状態

専用契約テスト14件、並列全体実行3回（各637件成功）、標準逐次全体実行1回（637件成功）、Ruff import整理・format・check、`git diff --check` を実行した。初回独立レビューはCritical 0 / Important 3 / Minor 2で、いずれも対応した。再レビューでCritical 0 / Important 1 / Minor 0（空initializer）、その後の再レビューでCritical 0 / Important 1 / Minor 1（全体0件suiteを成功扱いする問題、および計測値の古さ）、次のレビューでCritical 0 / Important 0 / Minor 2（カラー出力でのskip数解析、Red確認の記録範囲）を指摘された。カラー出力の回帰は修正前に失敗、workerで色を無効化した後に成功した。記録文もRed確認の事実に合わせて修正した。変更した文書の相対リンク647件は参照先欠落0件。最終独立レビューはCritical 0 / Important 0 / Minor 0で、レビュー指摘の未対応はない。AI向けの継続利用方針を `AGENTS.md` に追記し、`f534e6b` にコミットした。READMEの人間向け案内とAGENTSのAI向け指示をmainに統合した後、2026-10-21に承認を受けて `c89128a` までfast-forwardした。取り込み先で `PYTHONDONTWRITEBYTECODE=1 python3 scripts/run_tests_parallel.py` を再実行し、637件・41モジュールが19.843秒で成功。main側の未追跡ファイルは保持した。最後の理解確認への本人回答はまだない。

Refactorでは、発見・worker実行・CLI集約を分けた構成を維持した。テスト、実装、README間に追加の抽象化は必要と判断しなかった。

## 最後の理解確認

main統合後の取り込み先全体テストは成功済み。確認問題: 並列実行が速くなっても、逐次実行コマンドをREADMEに残して併用する理由は何か。本人回答はまだなく、理解済みとしては記録しない。

## 振り返り・次回への問い

逐次実行より短い経過時間を得た一方、並列化はテストを各々独立したプロセスに分ける実行条件の変更でもある。そのため速度だけで採用を判断せず、全件数を保ち、標準逐次経路も照合できるようにした。

次の確認では、モジュールごとの別プロセス実行でどの共有状態が失われる可能性があるか、またなぜ逐次コマンドも残したのかを説明する。
