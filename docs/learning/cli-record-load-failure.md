## 読んだ資料と用語

[README](../../README.md)のCLI起動・対局選択・時計設定・`save` / `load`手順、[CLI進行と時計の知識メモ](../knowledge/32-human-vs-computer-cli.md)、[棋譜保存の知識メモ](../knowledge/30-game-record-file-save.md)、[承認済みCLI時計設計](../plans/2026-10-20-cli-search-time-control-design.md)の保存・読込と時計検証を読んだ。

- `GameRecord`は開始局面と成功した指し手履歴を持つ棋譜データ。現在局面は保存せず、読込時に履歴を再適用する。
- `CliSession`は棋譜と任意の時計をまとめるセッションデータ。`load`はファイルから候補状態を検証して読む操作で、CLIの現在状態は全体の読込成功後にだけ置き換わる。
- 時計つき外側形式は`kaname-shogi-cli-session-v1`で、`game_record`に棋譜v1全体、`clock`に`initial_time_ms`、`byoyomi_ms`、`sente_remaining_ns`、`gote_remaining_ns`を持つ。
- 初期持ち時間・秒読みは非負整数msでbool不可、両方0は不可。先後の残り時間は非負整数nsでbool不可、初期持ち時間のns換算以下。
- 時計つきセッションの棋譜・時計・ファイルを全て検証する。どれかに失敗したら現在の棋譜と時計を保ち、理由を示して同じ人間手番の入力へ戻る。

## 固定した基準状態

前回の保存・再読込観察で記録した二手を持つ、コンピュータ対局の先手人間入力中を基準にした。前回の残り時間を今回の紙上例で固定値として使うが、これは製品の期待値や性能基準ではない。

| 基準項目 | 値 |
| --- | --- |
| 対局・手番 | 人間対コンピュータ、先手人間の入力中 |
| 現在の棋譜 | 先手7七→7六、後手8三→8四 |
| 初期持ち時間 | `600000ms`（10分） |
| 秒読み | `30000ms`（30秒） |
| 先手残り | `600000000000ns` |
| 後手残り | `599986433834ns` |

ここからの失敗例では、読込前にこの棋譜・時計・先手人間の手番がある。候補ファイルは全検証を通るまで現在状態へ反映しない。

## 固定例の紙上照合

### 1. 不正な棋譜と妥当な時計

候補の時計は妥当な値として、初期`600000ms`、秒読み`30000ms`、先手残り`590000000000ns`、後手残り`580000000000ns`とする。両残り値は初期持ち時間のns換算以下である。

候補棋譜は基準の二手に「先手7六→7四」を追加する。日本将棋連盟の[対局規則（第4条・第5条）](https://www.shogi.or.jp/match/taikyoku_rules/)では歩は前へ一マスだけ動くため、7六にある歩の7四への二マス移動は不合法となり、開始局面からの履歴再適用で失敗する。

| 照合対象 | 読込前 | 読込後 |
| --- | --- | --- |
| 棋譜 | 7七→7六、8三→8四 | 同じ二手を保持 |
| 時計 | 先手600000000000ns、後手599986433834ns | 同じ値を保持 |
| 手番・入力 | 先手人間の入力中 | 先手人間の同じ入力へ戻る |

時計だけを先に採用すると、読み込めなかった棋譜に別の残り時間が結び付いてしまう。この例は、時計が妥当でも棋譜検証失敗でセッション全体を置き換えないことを確かめる。

### 2. 妥当な棋譜と不正な時計

候補棋譜は「先手7七→7六、後手3三→3四」とする。二手とも合法で、手番は先手人間となる。候補時計は初期`600000ms`、秒読み`30000ms`、後手残り`580000000000ns`とし、先手残りだけ`true`にする。boolは整数値として扱わず、時計の整数条件に反する。

| 照合対象 | 読込前 | 読込後 |
| --- | --- | --- |
| 棋譜 | 7七→7六、8三→8四 | 元の二手を保持（候補の3三→3四へ置換しない） |
| 時計 | 先手600000000000ns、後手599986433834ns | 同じ値を保持 |
| 手番・入力 | 先手人間の入力中 | 先手人間の同じ入力へ戻る |

棋譜だけを先に採用してから時計エラーにすると、手番は同じでも盤面・履歴が別の対局へ変わり得る。セッション形式として識別されたファイルの時計が不正なら、時計のない旧形式として補完する経路へ落としてはならない。

### 3. 時計のない旧v1棋譜の互換成功

旧`kaname-shogi-game-record-v1`に基準と同じ妥当な二手があり、時計欄がない場合を別の成功例にする。コンピュータ対局の起動時に持ち時間・秒読みを空入力した場合、設計上の既定値は10分・30秒である。読み込んだ棋譜へその初期条件から時計を新しく作る。

| 照合対象 | 読込前 | 読込後 |
| --- | --- | --- |
| 棋譜 | 基準の二手 | 旧v1の二手を採用 |
| 時計 | 先手600000000000ns、後手599986433834ns | 起動時条件から双方600000000000nsを作成 |
| 手番・入力 | 先手人間の入力中 | 二手後なので先手人間の入力中 |

これは読み込み成功後に時計を補う互換経路であり、時計つき形式の不正時に現在の時計を保つ失敗経路とは違う。人間同士で旧v1を読む場合は時計を作らない。いずれも現在CLIで選んだ対局モードを読み込んだ棋譜が変更しない。

## 確認できた理由

新しい棋譜と時計は一つの保存済み対局状態を作るため、片方だけを置き換えると別の時点・別の局面に属する値を混在させる。両方を一時状態として検証し、全て成功した時点で一緒に反映すれば、その混在を防げる。失敗時に同じ人間手番へ戻る契約は、利用者がエラー後に入力を続けても元の対局が保たれることを示す。

旧v1には時計が保存されていないため、コンピュータ対局では起動時に設定済みの初期条件を使って時計を新しく作る。時計つきセッションの時計不正は「情報がない」状態ではないので、互換補完へ読み替えない。

## 最後の理解確認（2026-10-20）

**確認したいこと:** 読込候補の棋譜と時計を一体の状態として扱う理由、および旧v1互換経路との違いを説明できるか。

**質問:** 時計つきCLIセッションで棋譜または時計の片方でも不正なら、なぜ元の棋譜・時計と同じ人間手番を保つ必要がありますか。時計のない旧v1を読む成功経路と対比して説明してください。

**本人の回答:**

> 不正なまま受け入れるとゲームが成立しない可能性があるため

**アシスタントの補足:** 回答のとおり、不正な棋譜や時計を受け入れると対局状態が不正になり、続行できない可能性がある。さらに、棋譜と時計は同じ保存時点の一つのセッションを構成するため、片方だけを先に置き換えると別々の対局状態が混ざる。両方を検証してから一緒に反映すれば、失敗時にも元の棋譜・時計と同じ人間手番を保てる。旧v1は時計が保存されない形式として正当に識別されるので、コンピュータ対局では起動時条件から時計を作る。時計つき形式の不正な時計は旧v1へのフォールバック対象ではない。

## 振り返り・次回への問い

固定例では、妥当な時計を伴う不合法履歴と、妥当な履歴を伴うbool時計を分け、どちらも読込前の状態を保つことを照合した。時計なし旧v1は失敗ではなく、コンピュータ対局の起動時条件から双方の時計を作る成功例として扱った。本人は不正な状態を受け入れるとゲームが成立しない可能性を挙げた。補足では、棋譜・時計を一体で置き換える理由と旧v1互換経路との違いを記録した。このテーマは確認問題への回答まで完了した。
