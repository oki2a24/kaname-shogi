# 第37回：棋譜・局面のファイル保存

実施開始日：2026-09-24
設計承認日：2026-09-24
実装完了日：2026-09-24（main取り込み前）

## 目的

第36回でメモリ上に保持した `GameRecord` をJSONファイルへ保存し、後から読み込んで開始局面と成功手の履歴から現在局面を再現する。ファイル形式、保存対象、保存・読込の時機、エラー時の扱い、CLIとの関係、SFEN・USIの扱いを一問ずつ確認してから設計し、承認後にTDDで実装する。

## 一次資料で確認した規則

日本将棋連盟の対局規則第12条第1項は、公式棋戦で記録係または自動記録による採譜を行うと定める。第12条第2項は、棋譜と時間を正確に記録することを記録係の役割としている。棋譜利用のガイドラインは、公式記録に基づく指し手進行を再現した盤面図と、指し手順の文字情報を棋譜と説明する。

今回は時間管理や公式棋譜の利用は扱わず、自作対局の再現可能な記録をファイルへ残す範囲に限定した。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[日本将棋連盟「棋譜利用のガイドライン」](https://www.shogi.or.jp/kifuguideline/)

## 確認問題と回答

### 第1問：ファイル形式

問題：第37回で保存するファイル形式はどれにするか。

提示した推薦：標準ライブラリのJSON。開始局面と成功手を構造化して保存でき、読込時の形式検証も学びやすい。SFEN・USIとは分ける。

本人の回答：1

補足：JSONを採用し、SFEN・USIは別テーマに分ける。

合意：`kaname-shogi-game-record-v1` の専用JSON形式を使う。

### 第2問：保存対象

問題：JSONに何を保存するか。

提示した推薦：開始局面（盤上の駒・双方の持ち駒・手番）と成功した `move` / `drop` の履歴。現在局面は保存せず、読込時に再適用する。

本人の回答：1

補足：現在局面を重複保存せず、開始局面と履歴を記録の基準にする。

合意：開始局面と成功手の履歴だけを保存する。

### 第3問：保存・読込の時機とCLI

問題：保存・読込をいつ行い、CLIとどう結び付けるか。

提示した推薦：CLI対局中には保存・読込コマンドを追加せず、`GameRecord` を受け取った呼び出し側が明示的に保存・読込する。EOF・Ctrl-C・投了・詰みによる自動保存はしない。

本人の回答：1

補足：`run_game` の対局進行と終了表示は維持し、保存操作を別の責務にする。

合意：`GameRecord.save(path)` と `GameRecord.load(path)` を明示的な公開操作として追加し、CLIは変更しない。

### 第4問：エラー時の扱い

問題：保存・読込でエラーが起きた場合の扱いをどうするか。

提示した推薦：保存前にJSON化を完了し、読込時に構造・値・指し手の再適用を検証する。不正内容は `ValueError`、ファイルの不存在・入出力失敗は `OSError` として通知し、既存の記録を変更しない。

本人の回答：1

補足：読込失敗を空の記録として扱わず、失敗理由を呼び出し側へ渡す。

合意：形式検証と合法性検証を行い、失敗時に部分的な記録を返さない。

### 第5問：SFEN・USI

問題：SFEN・USIを今回どう扱うか。

提示した推薦：JSONはこのプログラム専用の保存形式とし、SFEN・USIへの変換・読込・CLI通信は実装しない。JSONの列挙値は固定文字列にする。

本人の回答：1

補足：外部標準への変換と通信は保存モデルを確認した後の別テーマに分ける。

合意：今回の対象はJSONファイル保存・読込だけとし、SFEN・USIは対象外にする。

正式形式は、トップレベルの `format`、`initial_position`、`moves` を持つJSONとした。盤上駒は筋・段・駒種・所有者、持ち駒は先手・後手ごとの基本駒種枚数、手は `kind` に応じて盤上移動または駒打ちを表す。現在局面は保存せず、読込時に既存の局面操作を再適用する。
