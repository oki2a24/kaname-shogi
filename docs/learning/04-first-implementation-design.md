# 第4回：実装設計と判断の背景

## 学習の目的

学習済みの盤・駒・手番・初期配置を、説明できる最小のプログラム構造へ落とし込む。言語、値の不変性、パッケージ構成、将棋エンジンとの互換性を区別して考える。

## 要点と判断の背景

### Pythonと標準テストを選ぶ理由

Python、TypeScript、Rustを比較した。Pythonは短い記述で処理を追いやすく、データを保持する `dataclasses` とテスト用の `unittest` を標準で利用できる。TypeScriptは型を明示できるがJavaScriptの実行時の理解も必要で、Rustは型による厳密な表現に加え所有権・借用の学習が必要になる。

今回は処理の理解と準備の少なさを優先してPythonを選んだ。特定の言語経験があることは前提にしていない。Pythonの型注釈だけでは実行時の型は保証されないため、座標の検証は明示的に行う。

### 不変性と移植しやすさ

利用者から「`frozen=True` の方が他言語へ移行しやすいのではないか」という質問があった。

不変性は「作った値を後から変更しない」という約束を明確にするため、他言語で同じ意味を再現する助けになる。ただし、指定するだけで移植しやすさを保証するものではない。移植には、データの意味、座標変換、入力と期待結果のテストも大切である。

`Square` と `Piece` は `dataclass(frozen=True)` とする。例えば７六の座標を別のマスへ書き換えず、新しい座標を作る。将来、成りや所有者変更も新しい `Piece` で表す方針にする。

一方、`Board` と `Position` は今回は可変とする。初期配置を一枚ずつ置く処理を素直に表せるためである。`frozen=True` は内包するリストの要素まで凍結しない。局面全体を不変にするにはタプルなども含めた設計が必要なので、今回は先取りしない。

### 外部依存がないことの伝え方

利用者から「外部ライブラリ不要と示すため、空の `requirements.txt` を作る方がよいか」という質問があった。

このファイルはpipにインストールさせる項目を指定するものである。空でも問題はないが、意図的に依存がないのか未記入なのかを区別しにくい。今回はREADMEに「実行・テストともに標準ライブラリのみ」と明記し、ファイルは作らない判断をした。

### `kaname_shogi/` と `src/` の違い

利用者は、他言語でよく見る `src/` と今回のディレクトリ名の違いを確認した。

`kaname_shogi` はPythonのパッケージ名であり、インポートと `python3 -m kaname_shogi` に使う。プロジェクト名のハイフンは、Pythonの識別子として扱えるアンダースコアに置き換える。

`src/` はソースをまとめる外側のディレクトリなので、採用時も `src/kaname_shogi/` とする。Pythonでは直下配置とsrc配置の両方が使われる。src配置は開発中のファイルの意図しないインポートを防ぐ利点があるが、通常は実行前にパッケージをインストールする。今回は直下配置で準備を減らす。

### 将棋エンジンの用語と互換性

利用者は一般的な名称との差を理解したうえで、学習上必要な違いを受け入れ、将来は将棋ソフトの外部インターフェースへ合わせたいと希望した。

内部構造には統一規格があるわけではない。具体例としてやねうら王のソースと比較し、次の対応を確認した。これは一つのエンジンの実装例であり、業界全体の必須命名規則ではない。

| 今回の案 | やねうら王の例との対応・違い | 今回の理由 |
| --- | --- | --- |
| `Square(file, rank)` | `Square` はマス番号、`File`・`Rank` も定義される | 筋段を直接読めるようにする |
| `Side.SENTE/GOTE` | `Color.BLACK/WHITE` | 学習済みの先手・後手に直接対応させる |
| `PieceType` | 同名。成り駒を含む表現がある | 今回は基本8種類だけを扱う |
| `Piece(piece_type, side)` | `Piece` は先後・成りを含む整数の列挙値 | 情報を項目に分け、意味を読み取れるようにする |
| `Board` | `Position` 内の盤配列などに対応 | 配置と手番の責務を分けて理解する |
| `Position` | 同名の局面クラス | 今回は盤面と手番だけを保持する |
| `side_to_move` | 同名の取得関数 | 意味を合わせ、今回は属性として保持する |
| 左下原点の二次元座標 | １一を0とするマス番号 | 第3回の理解を引き継ぐ |

USIはGUIとエンジンの通信を定めるもので、内部クラス名や配列順を定めない。そのため、内部構造を今回の形にしても、外部形式への変換で対応できる。先後とSFENの `b/w`、筋段とUSIの座標（７六なら `7f`）の対応を設計に残す。SFENには持ち駒や手数も必要であり、今回の最小局面だけで対応済みとはしない。

## 確認した問いと回答

今回は採点式の確認問題ではなく、設計への質問と説明を通じて確認した。以下の回答要旨は説明内容の記録であり、利用者が個別に解答したものではない。

1. `frozen=True` なら他言語への移植が容易になるか。
   - 回答要旨：値を変更しない約束は移植の助けになるが、直接の保証ではない。`Square` と `Piece` に適用する。
2. 外部依存なしを空の `requirements.txt` で示すべきか。
   - 回答要旨：今回はREADMEの明記で伝え、ファイルを作らない。
3. なぜ `src/` ではなく `kaname_shogi/` なのか。
   - 回答要旨：前者は配置用ディレクトリ、後者はパッケージ名で役割が違う。今回は直下配置を選ぶ。
4. 今回の名前や表現で将来の互換性を保てるか。
   - 回答要旨：既存エンジンの内部表現とは違いがあるが、USI・SFENへの変換を分離すれば対応できる。

## 振り返り

利用者はPythonと `unittest` に賛成したうえで上記の質問を行い、説明後に「ok. 納得できました」として、理解の背景も含む文書化を依頼した。

今回の設計では、値として固定する情報と変更する盤面、パッケージ名と配置用ディレクトリ、内部実装と外部通信の規格を区別できた。実装・ファイル作成を承認前に進めず、設計への納得を先に確認した。コードの実装は今後の作業である。
