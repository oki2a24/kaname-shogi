## この引き継ぎの目的

2026-10-22、千日手テーマの最後の理解確認を記録した後、本人は次テーマ候補1「P2比較CLIの実装計画を作る」を選定した。候補2「通常対局CLIのSFEN入出力」は、いずれ行う別テーマとして記録するよう指定された。選定理由は尋ねていないため推測しない。

この引き継ぎが対象とするのは、承認済み比較設計と、実装済み千日手API・現行コードを照合して具体的なP2実装計画を作成し、内容を提示するところまでである。P2計画の作成・提示は選定済みだが、計画への明示承認と実装開始は未承認である。新セッションで計画を完成・提示したら、本人の明示承認を待つ。承認前にTDD、コード・テスト変更、製品実装を始めない。

大テーマは「駒得以外の局面評価を一項目ずつ育てる」。P1比較設計と千日手補助テーマは完了。P2実装・確認の後に、未選定・未完了の主線帰還目標A1へ戻る。通常対局CLIのSFEN入出力は独立した将来候補であり、P2へ自動追加しない。

## 選定後の進行順

1. 新セッションで最初にGit状態を確認し、再開案内・本引き継ぎ・次テーマ候補と実物を照合する。
2. 承認済み比較設計の全体、P1記録、千日手の確定仕様・学習記録、実際のコードと関連テストを必要な順に読む。特に公開APIと局面履歴の開始点を現行状態で確認する。
3. 比較設計に書かれた実装範囲、契約、保存形式、エラー・中断境界、確認方法を、小さくレビュー可能な実装タスクへ具体化する。タスクごとに対象契約、独立した期待値、検出したい誤り、専用・関連・全体での検出範囲、未検証事項を記す。テストを実行・追加するのは計画承認後の実装段階である。
4. 実装計画を提示して本人の明示承認を待つ。比較設計からの仕様変更が必要なら、理由・影響を説明し、変更を計画へ確定する前に承認を得る。
5. 計画承認後、別途合意した実装開始に従ってP2を実行・検証・レビュー・統合・取り込み先確認し、計画にある小さな試行と記録を行う。その後A1へ戻る。

## すでに承認されている比較設計の要点

- 専用の比較CLIを作る。基準方式と候補方式を事前指定の組数だけ対局させ、条件・棋譜・終了理由・記述集計・計算時間を保存する。勝ちや評価改善の統計判定・自動採用・Elo・SPRT・信頼区間は行わない。
- 承認済みの開始局面セットは道具の動作確認用であり、棋力評価の代表局面セットではない。平手初期局面から合法な準備手順を再生し、比較開始局面から千日手履歴を新しく始める。準備手順を比較対局の履歴へ含めない。
- 同一組の二局では基準・候補の先後担当を交換し、盤面や駒の所属は反転しない。先後、乱数種、予定順と独立性の限界を記録する。
- 通常千日手は勝敗へ読み替えず、指し直し・再戦を自動で始めず、専用件数として集計する。連続王手側の負けは勝敗に算入する。`max-plies` は必須で、手数上限は未決着とする。終局優先順位は千日手・連続王手、合法手なし、手数上限。
- Ctrl-C、探索・適用失敗、保存失敗は勝敗に混ぜず、確定済みの一貫した棋譜と状況を記録する。自動再試行しない。入力をすべて検証した後に出力先作成・対局を始める。
- 出力契約は条件JSON、局ごとのJSON、集計JSON。具体的な公開型・関数シグネチャ・JSONキーと厳密な構造はP2計画で確定する。設計の利用者向け意味・必須記録内容を落とさない。
- 通常CLI操作、USI接続、通常CLIのSFEN読込・書出し、持将棋・入玉、定跡、並列対局、外部エンジン、異なるGit版の起動、自動checkout・再開・故障再試行は範囲外。特に通常CLIのSFEN入出力をP2へ含めない。

## 千日手部品との照合ポイント

確定済みの `RepetitionTracker` は、開始局面を一回目として登録し、成功した実着手後の局面だけを `add_position` へ渡す契約である。局面キーは81マスの駒種・所有側、双方の持ち駒、手番からなり、棋譜手数を含めない。探索中の仮想局面は渡さない。`GameRecord.iter_positions()` と `RepetitionTracker.from_positions()` は保存済み開始局面・指し手から履歴を再構成するための既存操作である。

`RepetitionOutcomeKind` は継続・4回目後の継続・通常千日手・一方の連続王手負け・双方王手の未裁定を区別する。通常の連続王手なしは4回目を `FOURFOLD_CONTINUE` として指し継ぎ、打開後の5回目では直近4出現区間を調べて `REPETITION` または連続王手結果にする。この具体的な通常CLI方針は本人選択を含む実装済み契約である。

P2計画では次を明示する。

1. 比較一局ごとに独立した履歴を用意し、準備手順ではなく比較開始位置を一回目にする。
2. 一手を正常に適用・確定してからその局面を履歴へ加え、探索だけの局面や失敗した手を含めない。
3. `FOURFOLD_CONTINUE` を終局の `repetition` と取り違えない。比較設計で承認済みの「通常千日手を再戦せず別集計」は、終局した通常千日手から自動再戦を開始しない意味で接続する。4回目と5回目の境界を設計・試験契約に明記する。
4. 連続王手負けの勝者と通常千日手の勝者なしを別扱いにし、双方連続王手の未裁定状態を勝敗へ誤変換しない。P2比較設計と実装済みAPIの間に、利用者向け仕様の変更が本当に必要と分かった場合だけ、根拠・影響を説明して本人の判断を求める。
5. 手数上限ちょうどで終局した場合も、比較設計の優先順位どおり先に千日手判定を行う。
