## 育てる方式のイメージ

通常局面の評価を概念上「駒得点 ＋ 採用した評価項目の点」とする。項目ごとに視点・符号・尺度・重みを設計する。詰みの勝敗を通常点より優先する既存の考え方を維持する。

最初の新方式は、一手指した直後を評価する一手駒得を土台にする案である。これは今回の対話からの具体化案であり、対象範囲の確定は最初の項目の設計時に行う。二手・四手探索への新評価の適用は別途判断する。

採用済みの版に一項目を追加した候補版を作り、直前の採用版と比較する。初回の直前版は一手駒得となる。項目追加による棋力向上や応答時間の短さは仮説として扱い、測定結果の範囲で記録する。評価方式の名称、保存・選択方法、CLI/USIで公開する版の数は具体設計で決め、全組合せを自動的に作らない。

## 全体の流れ

| 段階 | 位置付け | 成果と次へ進む条件 |
| --- | --- | --- |
| 0 全体方針 | 完了・主線 | 本書を確認し、本人がロードマップを承認する。最後の理解確認と回答記録を終える |
| P1 比較方法と道具の設計 | 完了・一度整える補助テーマ | 比較条件、先後別方式選択、反復対局・記録・停止・集計の最小範囲と確認方法を設計し、設計全体の承認と最後の理解確認を得る。千日手テーマ追加に伴い、比較実装計画は同テーマ完了後・P2実装前に作成し明示承認を得る調整を[比較設計](plans/2026-10-21-engine-comparison-design.md)と併せて本人承認済み |
| 千日手の学習・設計・実装 | 追加した補助テーマ・完了 | 履歴・連続王手・SFEN開始以前の履歴・接続範囲を学び、設計と計画の承認後に通常CLIへ実装。独立レビュー、ローカルmain統合、統合先検証、最後の理解確認まで完了した。実績は[学習記録](learning/repetition-rule-design.md)を参照 |
| P2 比較の道具の実装・確認 | 完了・一度整える補助テーマ | 千日手テーマの確定契約を使う実装計画を本人が承認し、比較CLIを実装・検証・独立レビュー・ローカルmain統合した。統合先全体テスト705件・45モジュール成功、最後の理解確認と回答記録まで完了。詳細は[P2学習記録](learning/engine-comparison-design.md) |
| A 項目nを学び設計する | 項目ごとの主線 | 一次資料と現行コードを確認し、一項目を選ぶ。改善仮説、独立期待値、評価の定義、既存項目との関係、検証範囲を具体化し、設計と実装計画の承認を得る |
| B 項目nを実装する | 項目ごとの主線 | TDD、Refactor要否確認、独立レビュー、記録、承認後の統合と取り込み先検証を終える |
| C 項目nを接続して評価する | 項目ごとの主線 | CLI・USIへの接続と確認、反復対局、ShogiHome実践を終え、結果と採用判断・未確認事項を記録する |
| 次のA | ループの帰還先 | 最後の理解確認と回答記録を終え、本人が次項目への移行を選んだら、新セッション用に引き継ぐ |

流れは `0 → P1 → 千日手の学習・設計・実装 → P2 → A1 → B1 → C1 → A2 → B2 → C2 → …`。Cの結果で修正が必要なら同じ項目のAまたはBへ戻る。次項目へ進む際も本人の選定を待つ。

比較の準備を始めても、帰還先は「最初の評価項目の学習・設計」である。道具の拡張を自動的に追加し続けない。

## セッションの切り方

原則は一セッション一目的とし、A・B・Cをそれぞれ別セッションとする。終了条件に到達しなければ同じ段階を継続し、理解確認・承認・検証を省略して一回に収めない。

- Aが大きければ、学習・設計と実装計画作成を分ける。
- Bが大きければ、独立して検証できる振る舞い単位に分ける。
- Cは接続実装、対局による評価、ShogiHome実践へ分割できる。接続実装にも設計・計画承認と実装時の規律を適用する。
- 小さく、本人が同じセッションでの継続を希望した場合は段階を続けられる。各段階の承認と完了条件は維持する。

各セッションの開始時に目的・対象・完了条件を示す。終了時は実際の進捗と未完了を記録し、次セッションはGit状態と引き継ぎを照合して始める。

## 評価項目の候補プール

下表は学習の入口であり、採用順でも全項目の実装予定でもない。広い概念は、そのセッションで一つの測定可能な項目へ絞る。

| 候補 | 学ぶ問い・具体化の例 |
| --- | --- |
| 玉の安全度 | 玉周辺の相手の利きなどで、まだ詰んでいない局面の危険をどう見積もるか |
| 駒の働き・活性度 | 攻めや守りに役立つ駒と遊び駒をどう区別するか |
| 可動性 | どの駒の、どの移動先を数えるか。成り・不成や駒打ちをどう扱うか |
| 利きの広がり | 影響するマスを数えるか、特定の重要マスへの利きを見るか |
| 駒の連携 | 味方の支えや攻めへの協力をどの関係で表すか |
| 配置・進行度 | 位置による評価や局面の進行をどう定義するか |

「働き」「可動性」「利き」などには重なりがある。項目を追加する前に二重加点や既存項目の言い換えにならないか点検する。前の候補説明で玉の安全度を最初に示した順序はアシスタントの判断であり、本人による項目選定ではない。

## Aで決めること

1. 何が改善しそうかを一つの仮説にし、対象局面と対象外を決める。
2. 駒得をそろえる等、一項目の影響を切り出した小局面を設計する。期待値は製品の出力から作らず、定義に従う手計算などで独立に決める。
3. 指定側の視点、正負、尺度、重み、持ち駒・玉・成駒の扱い、既存評価との組み合わせを決める。
4. 先後反転、位置・遮蔽・境界など、今回の定義が依存する条件を点検する。契約、代表ケース、検出対象、既存テストの補完、未検証を記す。
5. CLI/USIへの接続範囲とCの比較条件も見通した設計をレビューし、具体的な実装計画を提示する。明示承認後にBへ進む。

確認問題は一問ずつ出し、回答を待つ。本人回答とアシスタントの補足を区別する。

## Cで確かめること

| 確認 | 目的・残す結果 |
| --- | --- |
| CLI・USI接続 | 方式を選べること、指定の方式で合法応答すること、既存方式を選べることを確認する |
| 小局面の確認 | 独立期待値に従った採点・手選択を確認する。累積した項目同士の相互作用も確認する |
| 反復対局 | 比較条件下での勝敗・未決着・処理時間を記録し、採否を検討する |
| ShogiHome実践 | 登録・設定・応答・使い心地を指定条件で観察し、ログと棋譜で確認する |

主な比較は「直前の採用版 対 今回の候補版」。一手駒得との比較も継続的な基準として使い、ランダムとの比較は必要に応じて補助にする。評価項目の差を調べる比較では、読みの深さや他の評価項目・重みをそろえる。応答時間は同じ条件で別途記録する。

P1で、開始局面群、先後入れ替え、乱数種、機器・計算条件、対局数、勝敗と未決着、故障時の扱い、採否と終了の基準を定める。同一条件の決定的な棋譜を何度も繰り返しただけで独立した証拠が増えたと扱わない。対局数と統計的判断方法は、根拠を学んでから具体化する。

P1の比較設計時点では千日手未対応で、通常CLIのコンピュータ同士には手数上限がなかった。本人の承認で千日手をP2前の独立補助テーマに追加し、通常CLI向け部品を設計・実装した。比較実験では通常千日手を指し直さず別集計する方針が承認済みで、P2では通常CLI用の千日手部品を再利用する。公式対局の指し直しと実験上の集計を混同しない。手数上限などによる打ち切りは未決着とし、規則上の引き分けや評価値による勝者へ読み替えない。

ShogiHomeでは所定のスキルと接続手順書を使用し、局面・時計・対局数・ログ・停止条件を事前に具体化する。実践観察と対局成績はそれぞれ証拠の範囲を明記する。

## 評価後の進み方と大テーマの区切り

結果は「採用」「修正して再評価」「保留・見送り」「差を判断する証拠不足」を区別する。統計的な判定ができなければ未確定と記録する。実装・接続の完了と、棋力向上の確認を区別し、全項目の採用や勝率改善をループの必須条件にしない。暫定的な試用を残す場合も、その状態を明記して本人が判断する。

採用しない場合は直前の採用版を次の基準にする。修正・再測定を続けるか、結果を記録して次の項目へ進むかは本人が選ぶ。

最初の一項目でA→B→Cを終えた時点で、学び・実装・成績・使い心地・未解決を振り返る。次の項目は改めて本人が選ぶ。必要な説明ができ、改善仮説と確認方法を持つ評価を育てられた節目で、大テーマを継続するか一区切りにするか判断する。項目数や到達棋力は事前に固定しない。

## 記録と今回の未決事項

学習・回答・承認・レビュー・検証・採否は項目ごとの学習記録に残す。確定仕様は知識メモと承認済み設計、実行手順は実装計画へ置く。現在地は再開案内、主線と補助テーマ・帰還先は次テーマ候補に反映する。

C1開始時に未決定だった接続先・比較方法は、承認済みC1設計に具体化した。本人が実装計画全体を承認し、作業ブランチ `codex/c1-rook-mobility-evaluation` で実装・小規模パイプライン確認・最終検証・独立レビューを完了した。pilotでは256手上限で5/12局が未決着、512手上限では12/12局が終局した。続く確認比較と独立追試は各4,080局・2,040組で分析し、95%区間は50%を含んだため、本人は「判断不能」でC1を一旦区切った。比較CLI局単位再開、分析CLI短時間化、比較CLI局内高速化、分析CLI局単位再開の補助作業もローカルmainに統合済み。詳細は[C1学習記録](learning/c1-rook-mobility-evaluation.md)と[分析CLI再開記録](learning/c1-analysis-resume.md)を参照する。通常対局CLIのSFEN読込・書出しは本人が将来候補として指定して保留中であり、C1へ自動追加しない。序盤テンポ・探索応答時間改善も別候補として保留する。比較設計全体、P2計画の作成時期、千日手テーマをP2前に置く順序は本人承認済み。
