# C1分析CLI：合法な次の記録手を根拠にする短時間化の設計案

2026-10-25作成。本人は[性能調査](../learning/c1-analysis-performance-investigation.md)で推薦した案を詳しく設計する方針に「yes」と回答した。その後、本書全体への「yes」と併せて正確さが落ちないか質問し、検証の同等性と実装後の確認を説明した後「ok. 続けて」と回答した。設計全体と[実装計画](2026-10-25-c1-analysis-legal-witness-implementation-plan.md)は本人承認済み。別worktreeでの実装・検証、全4,080局の旧新版分析成果物一致まで完了した。詳細は[実装・検証記録](../learning/c1-analysis-performance-investigation.md)を参照する。

## 目的と主線との関係

保存棋譜・終局・計時・成果物の照合を保ち、分析CLIが中間局面で全合法手を繰り返し生成する時間を減らす。設計時点での本筋は稼働中の分析CLI完了確認とB1の効果判断であり、この補助設計だけをC1完了とは扱わない。

調査では198手の代表局の検証4.491秒のうち、readerが呼ぶ合法手全列挙198回に4.425秒（98.5%）を使った。JSON読込・decodeは約0.0004秒だった。改善倍率はまだ未測定である。

## 現行処理と再利用する根拠

`_load_game` は先に `GameRecord.from_payload` を呼び、保存棋譜の全手を既存の `apply_move` / `apply_drop` で合法再生する。不正な指し手はここで拒否される。その後 `_validate_and_replay` が開始局面からもう一度再生し、各手の計時・方式・反復・終局と末尾局面を照合する。

今回もこの二段階の合法再生を保つ。後段の内部では、検証済み `GameRecord.moves` の変更不可タプルを一度取得し、履歴と手数の正本とする。このタプルは `GameRecord` 内部の可変リストと共有しない。

途中の第k手後に第k+1手があるなら、第k+1手は同じ開始局面・同じ手順から合法適用できた手である。したがって第k手後の手番側には、少なくとも一つ合法手がある。これは個々の手の合法性を省略する推測ではなく、既存の合法再生結果を使う存在証明である。

この根拠で確認できるのは合法手の存在だけである。千日手・連続王手や手数上限で、合法手が残っていても対局が終わる場合は別に検査する。

## 各局面で行う検証

全手について、現行どおり計時フィールド、手番、方式、USI手と棋譜の一致、合法な適用、反復履歴の更新を確認する。その後の終局確認は次の表とする。

| 状態 | 合法手の有無の根拠 | 終局処理 |
| --- | --- | --- |
| 当該手で反復による終局が成立 | 合法手の有無を使わない | 現行の反復終局理由・勝者を保持する。後続手があれば次ループで拒否する |
| 後続の検証済み記録手がある中間局面 | その次の手が合法だったことからTrue | `board_terminal` にTrueを渡し、手数上限を毎手確認する。上限後に後続手があれば拒否する |
| 後続の記録手がない末尾局面で、反復終局なし | 現行どおり `legal_moves` で実際に調べる | 合法手なしの詰み/非王手の合法手なしを上限より優先し、その後に手数上限を判定する |
| 0手の中断・故障記録 | 次の手を根拠にしない。現行どおりループなし | `allow_nonterminal=True` の既存受理範囲を維持する。0手の完了記録を新たに受理しない |

100手の合法棋譜なら、途中99局面で次の手を根拠にし、末尾1局面では現行の合法手検査を行う。末尾が反復終局なら末尾の合法手生成も現行どおり不要である。

末尾局面・手番の再生結果照合、終局理由と勝者の照合、勝者先後から方式への変換、計時一覧は現行どおり残す。局の条件SHA・予定・seed・開始SFENの検証、ファイル集合、summary再集計、組得点と95%区間の計算も維持する。

## 対象範囲と影響

- 主な振る舞いの変更対象は `kaname_shogi/comparison_result_io.py` の `_validate_and_replay`。`GameRecord.from_payload` と将棋の合法手判定規則は変更しない。
- `board_terminal` の実装・終局優先順位は変更しない。その説明は「呼出側が真偽を確認済み」と整理し、分析では検証済みの次の手を根拠にできること、対局実行側の合法手生成・計時境界は従来のままであることを明記する。
- `_load_game` は局単位再開でも共用される。このため分析用完了局に加え、`allow_incomplete=True` の中断・故障局、0手/非終局末尾/終局直後中断の既存契約を回帰確認する。再開の入力条件・再投入・ファイル保存形式は変更しない。
- CLI引数、依存関係、保存形式、評価ロジック、通常対局CLI/USI、比較実行器は追加・変更しない。並列化・進捗表示・キャッシュ・二重再生の統合は今回の設計に含めない。
- `GameRecord` の合法性検証で打ち歩詰め等に必要な内部の候補調査は引き続き行う。「合法手生成が一局全体で必ず一回だけ」とは主張しない。減らすのはreaderからの終局有無確認のための直接の全列挙である。

## 正しさと検出力の確認方針

変更後も個々の棋譜手が合法検証を通ることを前提とし、その前提を除去する変更を今回へ混ぜない。代表ケースは手書きの短い棋譜と独立した期待値を用いる。

| 契約 | 代表ケースと期待値 | 検出したい誤り |
| --- | --- | --- |
| 中間局面で全候補を作り直さない | 平手からの合法3手 `7g7f 3c3d 2g2f`、上限3。readerからの直接の全列挙は末尾の1回、終局は手数上限 | 各手で旧全列挙を続ける、最終局面でなく最初の局面を調べる |
| 前提となる合法再生を維持 | 中間手を違法な盤上移動や駒打ちへ置換し、合法性エラーで拒否 | 記録手があるだけで存在を認定する、合法再生を外す |
| 合法な手でも上限後は継続不可 | 同じ合法3手に上限2を与え、3手目を既終局後として拒否 | 中間の上限判定を末尾だけへ移す |
| 反復終局を維持 | 既存の五回目反復後に合法手を追加するケースを再利用し、拒否 | 次の合法手があることを対局継続可能と誤認する |
| 末尾の有無と勝者を実際に調べる | 詰み・非王手の合法手なし・合法手がある上限局面、先後反転と上限同時到達 | 末尾までTrue固定、詰みと上限の優先逆転、勝者先後の固定 |
| 保存局・再開の既存契約を保つ | 0手と複数手の中断/故障、末尾が非終局、終局直後中断、完成局 | 完了局だけを想定した末尾処理、再開対象の誤分類 |
| 統計・入力の整合を保つ | 代表6局の復元値、終局、計時、得点と入力ハッシュを変更前後で比較 | 局の取り違え、入力変更、組得点・集計の変化 |

既存テストは条件・seed・計時不整合、反復後継続拒否、終局優先順位、summary再集計、再開対象の分類を補完する。新しい単独テストの検出範囲は、既存全体が補完する範囲と分けて記録する。

実装計画では振る舞いごとにRed→最小実装→Green→Refactor要否を明記する。新しい直接全列挙回数の期待は旧コードで振る舞いのRedを確認する。維持する拒否・終局の例が旧コードで成功する場合は初回Greenと記録し、無理にRedと呼ばない。最終検査省略、毎手上限判定省略、反復判定省略等の代表変異で意図したassertion失敗を確認する。独立レビューの前提・範囲と残件を残す。

## 性能と成果物の確認方針

調査で選んだ同じ6局・同じ入力を用いて、変更前後の検証時間を同じPython・計測条件で比較する。測定順の偏りを避け、繰返しの中央値と各測定値を残す。単体テストの合否に秒数の閾値を入れず、直接の全列挙回数による決定的な検査と性能計測を分ける。具体的な反復数・計測手順は実装計画で明示する。

性能上の期待は「中間の直接全列挙を除去し、代表6局の検証時間が短くなる」であり、改善倍率や完了時間は保証しない。正しさ・拒否対象の一致を性能より優先する。

現行の全4,080局分析が完了した後、必要な実装・検証を経て、新版でも同じ入力を別の新規分析出力先へ通す。入力SHA一覧、条件・組数・件数・得点区間・判定・記述集計・比較時の計時は一致を確認する。新版の `analyzer.source_sha256`・Git識別等の分析器メタデータは変更されるため、JSON全バイト一致は要求しない。入力局の再対局や新しいseed抽出は行わない。

ソース変更で比較条件のsource_sha256が変わるため、旧比較結果への `--resume` は既存仕様どおり新コードから拒否される。完了成果物の分析は異なる分析器ソースを記録して受け付ける既存仕様を利用する。

## 分析ソース保全と承認後の実施状況

元分析プロセスの最終JSON生成がディスク上のPythonソース指紋を読むため、本人の希望と承認を受けて別worktreeへ実装を隔離した。元ディレクトリのPythonソースは保持した。承認済み計画に従いTDD、性能計測、全体テスト、独立レビューまで完了し、レビュー最終結果はCritical 0 / Important 0 / Minor 0。固定6局では旧新版の検証結果が一致し、合法手存在確認のためのreader直接列挙が一局ごとに従来の各手から末尾一回（反復終局なら0回）に減った。

本人は新版readerで4,080局を端末分析し、旧JSONと `analyzer` を除く全項目が一致した。条件・局・summaryのSHA-256計4,082件も実ファイルとすべて一致した。統計判定は判断不能で、B1の強さは確認できない。分析CLIの正確な実行時間は記録されず、出力JSONのmtimeと開始報告から約5分という目安だけが推測できる。

6局の性能値は全局面・全OSの性能保証ではなく、全4,080局に対する分析結果の一致も別入力すべてでの同値性を証明しない。異常な外部同時書換えへの耐性と棋力改善も未検証である。
