# 四手探索二方式を対局の選択肢に接続する設計

## 状態・目的・対象範囲

2026-10-19作成。接続先・方式の選び方・設定寿命・探索深さ・時計利用・停止時の結果・応答責務を本人と一問ずつ確認し、設計全体を提示した。本人の「yes」により、この文書の範囲と設計を明示承認済み。これは学習・接続設計であり、実装計画、コード・テスト・設定変更、実装、実時間保証の承認ではない。

目標は、開発用比較として実装済みの全幅読みとαβ枝刈りを、通常対局CLIとUSIの両方で選べる方式にすること。既存のRandom・Material・TwoPlyMaterialも引き続き選択可能にする。選択は既存のCLI対局前メニューとUSI `Difficulty` 設定に二方式を加えて行い、別の設定群は作らない。

今回の接続後も、開発用比較コマンドの役割・結果・既定動作は維持する。新二方式の通常対局での選択が新しい利用経路となる。

## 合意した選択とその理由

| 判断 | 合意内容 | 理由・意図 |
| --- | --- | --- |
| 接続先 | 通常対局CLIとUSIの両方 | どちらからも二方式を対局で選べるようにする |
| 選択の入口 | 既存CLIメニューと既存USI `Difficulty` に二方式を追加 | 方式を選ぶ窓口を既存の仕組みにそろえ、既存三方式も残す |
| 設定寿命 | CLIは一局中固定。USIは最初の `go` でその局の値を固定し、`usinewgame` 後の局で新設定を使う | 対局中に選択済み方式が切り替わらないよう、現在の寿命を踏襲する |
| 深さ | コンピュータの各手で深さ1、2、3、4の順に反復深化し、次の手では深さ1からやり直す | 4は最大深さであり、対局開始時に1〜4から選ぶ値ではない |
| 時計 | USIだけ既存の時計予算を新二方式へ接続。CLIは時間制御なし | 通常対局CLIに時計機構を新設せず、USIは既存制御を使う |
| 通常停止 | 最後に完了した深さの手を返す。完了深さがなければ準備済みの合法予備手を返す | 既存 `STOPPED` 契約を踏襲する |
| 抑制 | `SUPPRESSED` は応答用の手なしとし、`bestmove` を送らない | 抑制を投了や通常停止の手へ変換しない |
| 応答責務 | 探索部品は結果データを返す。USI接続側は送信直前に抑制を再確認し、`bestmove` を最大一回送る | 探索と通信の責務を分け、停止・抑制競合時の既存送信規則を保つ |

## 選択肢と設定の表現

CLIは現在の対局開始前メニューへ二項目を足す。表示名の案は `全幅読み（最大4手）` と `αβ枝刈り（最大4手）`。既存Random・Material・TwoPlyMaterialの表示と意味は変えない。

USIは既存 `Difficulty` のcombo optionに二つの値を追加し、未設定時の既定値 `Random` は維持する。USI内部値の候補名は `FullWidth4` と `AlphaBeta4`。最終的な識別子・表示文字列は実装計画でコード規約と既存選択モデルに照らして確定する。

CLIでは、選んだ方式を一局の全コンピュータ手で使う。USIでは現在の実装と同じく、設定値を最初の `go` で局用に固定し、対局中に届いた設定変更は `usinewgame` で始まる次局から使う。Randomを含む既存三方式にも設定寿命の変更を加えない。

## 探索と時計の流れ

1. 局面を受け取り、選択済み方式を特定する。
2. コンピュータの一手ごとに同じ開始局面から深さ1、2、3、4を順に探索する。前深さの最善手は次の深さの根の順序づけに利用できる。指し手を適用した次のコンピュータ手では新しい反復を深さ1から始める。
3. CLIは時間制御を行わず、深さ4まで探索する。現行のCLI中断・対局終了の扱いは維持する。
4. USIは現行の `go` と時計入力から作る予算・制御を一回の反復全体へ渡す。各深さや子局面で時計原点・予算を作り直さない。
5. 時計の目標、上限、または `stop` で通常停止したときは、最後に完了した深さを使う。深さ1の完了前なら合法予備手を使う。上限深さ4まで完了する保証はしない。
6. `gameover`、`quit`、応答無効化を伴う入力などで抑制されたときは、結果データに完了記録が残っていても応答用の手を返さない。USI接続側は送信ロック下で抑制状態と送信済み状態を再確認する。
7. 合法手がない結果は既存USI契約に従い `bestmove resign` とする。通常の選択手がある場合だけ `bestmove <手>` を一回出す。

USIの既存時計予算を使い、予算式を変更しない。探索停止の各確認点は応答の上限時間を保証しない。単一の合法手生成・適用・評価処理は強制終了できず、深さ4到達も保証しない。CLIは時計なしなので全幅四手の待ち時間が長くなる局面があり得るが、現在の資料には新方式の対局実測がない。これを実行不能の証拠とはせず、実時間は実装後に観察すべき未検証事項とする。

## 探索部品と接続責務

既存の `search.core.search_controlled` は `pruning` を指定でき、全幅／枝刈りの共通再帰処理と停止確認を持つ。一方、公開された `minimax` には制御付き入口がなく、`iterative_deepening.search` と `search_controlled` は一深さの探索先をαβ方式に固定している。したがって全幅方式をUSIの通常停止・抑制に対応させるには、単発の完了結果だけを返す比較入口では足りない。

設計上は、全幅側に `core.search_controlled(..., pruning=False)` へ委譲する薄い制御付き入口を設け、既存αβ入口とともに一深さ探索として選択可能にする。時間制御なしのCLI経路でも既存の `minimax.search` と `alpha_beta.search` を一深さ処理として呼び分け、USI経路では制御付きの各入口を同様に呼び分ける。反復深化の共通管理はどちらの経路でも再利用し、探索本体・評価・停止確認・反復ループを方式ごとに複製しない。名前や引数の具体形は実装計画で定める。

通常対局CLIとUSIの接続層は、選択方式・制御の有無を探索へ渡す。探索は `ControlledSearchResult` 相当の結果データを返すだけで、USI行の送信、抑制の最終判定、送信回数管理を行わない。USI接続層がこれらを所有する。Random・Material・TwoPlyMaterialの既存呼出しとUSIの入出力規則は保持する。

この不足は既存の共通探索本体で埋められる接続差分であり、全幅読みを比較専用に限定する技術的理由にはならない。ただし四手全幅の実行時間と時計応答は未計測で、時間保証は設計しない。

## 確認方針と検出範囲

以下は確認設計であり、テストの作成・実行結果ではない。テスト設計では [検出力点検手順](../knowledge/test-coverage-review.md) と個人観察 `~/.codex/observations/test-driven-development.md` の考え方に従い、実装時に対象契約・独立期待値・単独／全体の検出範囲を具体化する。

| 対象契約 | 独立した期待値と代表ケース | 検出したい誤り |
| --- | --- | --- |
| 二方式の選択と既存三方式 | メニューとUSI宣言に五方式が現れ、明示選択した方式が一深さ探索へ対応づく。既存三方式の既知の選択結果は変わらない | 新方式の片方の欠落、表示と実際の方式の不一致、既存方式の置換 |
| 設定寿命 | CLIは一局固定。USIは最初の `go` で固定し、`usinewgame` 後に更新値を反映する | 対局途中の誤切替、USI設定値の早過ぎる反映／反映漏れ |
| 全幅・αβの深さ1〜4 | 小さい人工探索木で各深さの期待評価と最善手を手計算し、両方式をそれぞれ照合する。両方式同士の一致だけを正解根拠にしない | 深さのずれ、全幅を枝刈りに誤接続、枝刈り方式の取り違え、反復間の局面・手順序の混入 |
| 反復の順序と局面単位 | 一手の呼出し順が1→2→3→4、対局上の次のコンピュータ手で再び1から始まることを呼出し記録から確認する | 深さの飛ばし、前局面から深さを継続する誤り |
| 通常停止・抑制 | 制御を決定的に操作し、深さ完了前は予備手、途中停止は最後の完了手、抑制は手なしとなることを結果値で確認する | 未完了手の採用、記録なし時の手なし、抑制手の復活 |
| USI時計と送信 | 合成した時計値・停止要求・送信ロック競合を使い、通常停止では合法手を最大一回、抑制では送信0回とする。合法手なしは既存の投了表現を使う | 予算の作り直し、二重 `bestmove`、抑制後送信、手なし状態の誤変換 |
| 回帰 | 既存三方式のCLI/USI選択、設定寿命、既存時計・stop・抑制テストを個別と全体で確認する | 新分岐による既存利用経路の破壊 |

個別テストは各契約の局所誤りを狙い、関連・全体テストは接続後の回帰を検出する。これらは別々に必要で、成功件数のみで十分性を判断しない。テストだけでは探索木の期待値を独立に導けているか、すべての競合順序・局面を覆うか、実時間内応答を保証できない。

## 未検証事項・今回の対象外

- 全幅四手の通常対局での実時間、各局面での実際の深さ到達、利用者が許容できる待ち時間。
- USIの時計がある全局面で期限内に応答すること、OSスケジューリングやすべての停止／送信競合。
- ShogiHome等の実機での新方式対局、互換性、棋力向上。
- 千日手等の履歴を使う終局判定、評価関数の強化、定跡、置換表、並列探索。
- CLIへの時計制御、時間保証、最大深さ4の完了保証。
- 実装計画、テスト作成・実行、コード・テスト・設定変更、実装。
