# プロジェクト内Ruff導入の設計・実装計画

> **AIエージェントへの指示:** 承認後は `executing-plans` スキルを使用してこのセッションで実装する。独立レビューには別のレビュアーを使用する。

**目標:** このプロジェクトだけにRuffを導入し、ステージしたPythonコードの整形・基本検査が成功した場合だけ通常のGitコミットを許可する。

別PCでcloneした後も、追跡された依存関係・スクリプト・説明から同じ開発環境を構築できるようにする。

**アーキテクチャ:** Ruffをリポジトリ内の `.venv` に固定版で導入する。リポジトリ限定のGitフックから、インデックス（コミット予定内容）を一時ディレクトリへ展開して検査する。フックは自動修正・再ステージをしない。

**技術スタック:** Python 3.9.6、標準ライブラリ、Ruff 0.16.10、Gitのpre-commitフック。

**仕様:** 本書の「合意と具体案」。作成時はツール選定のみ承認済みだった。その後、別PC向け追記を含む本計画に本人が「良い」と明示承認し、実装を開始した。その後、記録確認・コミット・フック有効化・main統合・取り込み先検証も本人が承認した。

**グローバル制約:**
- 説明・記録は日本語。プログラム実行・既存テストに外部依存を追加しない。
- 計画の明示承認前にTDD、コード・テスト変更、実装開始へ進まない。
- 実装は作業ブランチで行う。main統合には検証・独立レビュー・記録と本人の承認が必要。
- CriticalまたはImportantのレビュー指摘を解消し、再検証・再レビューしてから記録更新とコミットへ進む。

## 合意と具体案

本人は「Ruffの整形＋明示した基本ルールから始める」を選択した。

その後、別PC向けのPython依存関係、Gitスクリプト設定、READMEとエージェント向け説明の追加を依頼した。以下を計画へ追加した。その後、本人の「良い」という明示承認を得て実装した。

- `pyproject.toml`：`target-version = "py39"`、`line-length = 88`、`lint.select = ["E4", "E7", "E9", "F"]`、`required-version = "==0.16.10"`。previewや追加ルールは有効にしない。Python対象は本体・テストおよび今後追加するリポジトリのPythonコード。
- `requirements-dev.txt`：`ruff==0.16.10`。グローバルインストールせず、`python3 -m venv .venv` と `.venv/bin/python -m pip install -r requirements-dev.txt` で導入する。
- `.gitignore`：`.venv/`、`.ruff_cache/` を追加する。検査フックは `--no-cache` を使う。
- `.githooks/pre-commit`：実行可能なシェル入口。Gitのリポジトリルートへ移動し、`.venv/bin/python scripts/check_staged_python.py` を実行する。仮想環境がなければ案内してコミットを止める。
- `scripts/check_staged_python.py`：標準ライブラリだけでインデックスを一時ディレクトリへ展開し、ステージ済みの `pyproject.toml` を指定して `ruff format --check` と `ruff check` を実行する。対象はスナップショット内の追跡済みPython通常ファイルで、空白を含むパスも引数配列で扱う。Ruffはこのcheckoutの `.venv/bin/ruff` を使用する。設定・ツールの不足や検査失敗は非0終了とする。一時ファイルは終了時に削除し、作業ツリーとインデックスを変更しない。
- 有効化は `git config --local core.hooksPath .githooks`。既存設定・フックを確認し、競合があれば上書きせず解決案を提示する。グローバルGit設定は変更しない。cloneごとに環境構築と有効化が必要。
- `scripts/setup_dev.py`：リポジトリ直下で `python3 scripts/setup_dev.py` を実行すると、前提条件と既存フックの競合を確認し、`.venv` 作成、固定版依存関係のインストール、Ruffのバージョン確認、リポジトリ限定のフック有効化を順に行う。Python 3.9以上とGit、初回のパッケージ取得に必要な通信環境を前提とする。既存 `.venv` は再利用し、同じコマンドを再実行可能にする。壊れた環境や別PCからコピーされた環境は無断削除せず、再作成方法を案内して止める。依存関係導入に失敗した場合はフックを新たに有効化せず、成功と表示しない。引数なしの入口とし、無関係な機能や環境管理ツールは追加しない。
- 今回のセットアップ対象はmacOS/Linuxの通常のcloneとする。実機確認したOSとPython版は記録し、Linuxを未実測で実測済みと扱わない。Windowsネイティブ・別worktree固有の導入は今回保証せず、別途確認が必要な範囲としてREADMEに明記する。
- `.venv` はGitで配布・別PCへコピーしない。追跡するのは依存関係ファイル、Ruff設定、セットアップスクリプト、フック、説明である。Ruffは単一パッケージの固定版なので、追加の依存管理ツールは導入しない。本体・既存テスト用の空の依存ファイルも作らない。
- 通常の開発では `.venv/bin/ruff format .`、`.venv/bin/ruff check .`、差分確認、再ステージ、コミットの順に行う。フック内ではネットワーク接続やインストールをしない。
- 初回の全体整形は機能変更と分離する。フック・設定の導入コミットとは別の整形コミットを同じ作業ブランチで作り、両方が整ってからフックを有効化する。mainへの取り込み・pushはこの計画への承認に含めない。
- `--no-verify` による回避はGitとして可能だが、アシスタントは通常作業で使用しない。フックは単体テストや独立レビューの代替ではない。

## 調査の根拠（実装前の実測）

Python 3.9.6の一時環境で、既存の本体・テスト24ファイルを調査した。Ruff 0.16.10の上記基本ルールは0件、import順序とbugbear追加時はimport順序20件。Flake8 7.3.0既定は185件、Black 25.11.0とPylint 3.3.9の組合せではPylint既定104件だった。検査範囲が異なるため件数を優劣とは扱わない。

Ruff・Blackとも20ファイルに整形差分が出た。Ruffは追加2,122行・削除1,254行、Blackは追加2,129行・削除1,260行。整形したコピーでは両方とも全24ファイルのAST一致、全326テスト成功。最初のコピーにはUSI起動ファイルがなく2テスト失敗し、コピーを補った後に成功した。これは本体の修正ではない。

Ruffを選ぶ理由は、整形・基本検査を一つのツールと設定にまとめられ、今回の学習範囲で管理対象を増やさずに済むこと。速度比較や全バグの検出性能は測定していない。

出典：[Ruff設定](https://docs.astral.sh/ruff/configuration/)、[Ruffリンター](https://docs.astral.sh/ruff/linter/)、[Ruffフォーマッタ](https://docs.astral.sh/ruff/formatter/)、[Gitフック](https://git-scm.com/docs/githooks)。

## レビューフォーカス

1. ステージ版に問題、作業版に修正がある場合もコミットが止まること。
2. ステージ版が合格、作業版に未ステージの問題がある場合はステージ版の検査で成功すること。
3. Ruff・仮想環境・ステージ済み設定の不足時に検査を省略せず止まること。
4. 空白付きパス、削除済みファイル、Pythonファイルなしで適切に動作すること。
5. 検査が元のファイル・ステージ状態を変えず、既存フックを無断で置換しないこと。

セットアップについては、初回・再実行・依存導入失敗・既存フック競合・不正な仮想環境の各条件も確認する。
