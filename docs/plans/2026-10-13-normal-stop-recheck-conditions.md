# 通常停止の再確認条件案

## 状態と範囲

2026-10-13作成。本人の「ok」で条件案が承認され、その後の「実施開始して」でこの条件に沿う一回の実施を承認された。実行は一回で終了し、直接USIプロセスで通常 `stop` 後の合法な一応答と正常終了を観測した。本人は画面証拠がない状態でこの一回を受け入れた。ShogiHome操作、コード・テスト・設定変更は行っていない。mainへの取り込みは別の判断とする。

対象は「実エントリポイントを使う一回のUSIプロセスで、探索中に通常の `stop` を送信し、その後の応答を観測する」ことに限る。ShogiHomeのGUI操作、時計設定からの期限停止、実対局の時間内応答は対象外とする。

## 現行契約と今回の切り分け

- 時計引数を省略した `go` は、時間予算なし（`None`）として探索する。`go infinite` とは別であり、後者はShogiHomeの解析経路にも関わるため使わない。[USI応答仕様](../knowledge/usi-engine-response.md#時計受付と設定の寿命)、[時間予算](../knowledge/time-budget.md)
- 探索中の通常 `stop` は応答抑制ではない。合法な予備手または計算済みの最善手を一度返し、合法手なしが確定したときは `bestmove resign` を返す。合法手の確保・手なしの確定を待つ場合があり、応答時間は保証されない。`quit`、EOF、`gameover` は未送信応答を抑制するため、通常停止の代わりにはならない。[USI応答仕様](../knowledge/usi-engine-response.md#入力送信故障回収2026-10-12接続)、[探索停止](../knowledge/search-stop.md)
- ShogiHome資料では「対局中断」は対局を終了してプレイヤーを閉じる経路で、通常のUSI `stop` の観測手段ではない。エンジン時間切れありOFF時の `stop` は時計切れ経路であり、エンジン内の期限や人間側時計の影響を分離できない。解析中断の経路は `go infinite` を使う。したがって今回の条件ではShogiHomeを起動せず、直接USI入出力を制御する。[接続ガイド](../shogihome-connection-guide.md)、[ShogiHomeの対局操作](https://github.com/sunfish-shogi/shogihome/blob/main/src/renderer/view/main/ControlPane.vue)、[対局終了処理](https://github.com/sunfish-shogi/shogihome/blob/main/src/renderer/game/game.ts)、[USIプレイヤー](https://github.com/sunfish-shogi/shogihome/blob/main/src/renderer/players/usi.ts)

上記ShogiHomeコードは公式リポジトリの `main` を2026-10-13に参照したもの。リンク先は可変ブランチであり、参照時点のコードを示すための案内で、固定版の根拠ではない。現在インストールされている版・画面・その版のコードは今回確認していない。この案はGUI挙動に依存しないため、実機でShogiHomeの版を確認する条件も含めない。

## 局面の選定

今回の候補は次のC2局面、後手番とする。

```text
l4S2l/4g1gs1/5p1p1/pr2N1pkp/4Gn3/PP3PPPP/2GPP4/1K7/L3r+s2L w BS2N5Pb 1
```

前回G2で使ったC1を引き継がず、過去に候補として記録されたものの実機では使っていないC2を、今回あらためて構造面から選ぶ。両者の持ち駒に複数種類・複数枚の駒があり、`TwoPlyMaterial` が根の候補と各候補への応手を調べるときに、駒打ちを含む分岐を作りやすい。これは探索が一定時間続くという測定結果ではなく、停止を試す候補としての静的な見立てである。所要時間は未計測で、早く自然完了する可能性も残る。

実施時に局面文字列・手番・駒台が一致しなければ開始しない。`TwoPlyMaterial` を一局面・一回だけ用い、自然完了が先行しても別局面へ切り替えず再試行しない。前回G2のC1、時計、目標・上限値、起動数は採用しない。

## 時計・起動・操作

時計はUSIの `go` から全て省略する。これは直接プロセスで通常停止を分離して観察するための時計条件であり、ShogiHomeの時計なし対局を意味しない。時計予算の期限停止、秒読み、時間切れ、ShogiHomeの設定値は評価しない。

条件が別途承認され、実施開始が別途明示された後に限り、リポジトリのルートを作業ディレクトリとして、READMEにある実エントリポイント `python3 -m kaname_shogi.usi_engine` を一度だけ起動する。これは `kaname-shogi-usi` ランチャーの検査とは別の入口である。標準入力・標準出力・標準エラーを分け、各送受信・flushを単調時計で記録する一時的な制御役を `/private/tmp` に用意し、リポジトリへ追加しない。制御役はイベントを一列に記録し、OSのCPU時間サンプルとプロセス終了も記録する。次の順に送る。

1. `usi` を送り `usiok` を待つ（5秒以内）。
2. `setoption name Difficulty value TwoPlyMaterial`、`isready` を送り `readyok` を待つ（5秒以内）。
3. `usinewgame`、上記SFENを使った `position sfen ...`、`isready` を送り、二度目の `readyok` を待つ（5秒以内）。
4. 時計引数のない `go` を一度送り、標準出力を継続して読む。`go` 送信から最大3秒を、探索中かどうかを確認する時間とする。macOSの `proc_pidinfo(..., PROC_PIDTASKINFO, ...)` から得る `proc_taskinfo.pti_total_user` と `pti_total_system` の累積値を生値で記録し、500ミリ秒以上離した連続2回のサンプルで合計値の増加が確認でき、標準出力に応答がなく、子プロセスが生存している最初の時点で `stop` を一度だけ送ってflushする。500ミリ秒間隔は一度の差分でなく連続した活動を確認しつつ、3秒の観察窓内で判断するため今回新たに置く。CPU差分を必須条件にするのは、応答のない生存プロセスだけでは探索中と区別できないためであり、取得失敗・増加なしならstopを送らず停止未観測とする。受信イベントと入力送信の順序は同じ記録器で記録するが、標準出力の受信時刻はエンジン内部の応答生成時刻そのものではない。[Apple XNUの `proc_taskinfo` 定義](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)
5. `stop` 送信後、最大10秒だけ `bestmove` を待つ。応答を受けたら、その後1秒間重複応答がないことを確認する。続けて `quit` を一度送り、最大3秒で終了を待つ。

5秒・3秒・10秒・1秒の各値は、今回の一回を有限に運用するために新しく置いた管理上の上限・観察窓である。エンジンの性能目標や応答保証ではなく、前回G2の時計・目標・上限・待機値を転用したものではない。SIGTERM後の2秒は、強制終了を避けながら最終状態を確認する今回の有限待機とする。起動1回・再試行なしは、条件を変えて成功例だけを選ぶことを避け、「一回の通常停止観測」という今回の問いを固定するためである。

## 判定と終了・復帰

### 観測成立

以下を全て満たした場合に限り、「この実エントリポイント、この局面、この時計なし `go` の一回で、探索中と推定できる時点に通常 `stop` を送り、その後に一応答を受けた」と記録する。

- `go` 後、`stop` の送信記録より前に `bestmove` が記録されていない。
- `stop` 送信直前にもプロセスが生存し、連続したOS CPU時間サンプルが増加している。
- `stop` を一度だけflushした後、10秒以内に `bestmove` が一度だけ届き、重複観察窓にも追加応答がない。
- 応答が `bestmove <usi move>` の場合、その手が記録局面の合法手と一致することを読み取り専用で照合する。`bestmove resign` はこの局面では想定しないため、届いた場合は手なし契約との整合を別途判断対象にし、成功には数えない。
- `quit` 後3秒以内に子プロセスが終了し、終了コードが0で、標準エラーに未説明の診断がない。

この成立を、内部探索位置を完全に証明したこと、stopが結果を変えた因果の証明、時間予算停止、ShogiHome実通信、時計制限内の応答保証へ一般化しない。OS CPU時間の増加はプロセスがCPUを使っていた証拠であり、内部の探索関数がまさに実行中だったことまでは直接示さない。

### 未成立・終了

- `bestmove` が `stop` より先に届いた場合は「自然完了先行」。`stop` は送らず `quit` で終了する。一回の試行を終了し、再試行しない。
- 3秒以内に活動条件を満たさない場合、または起動・ハンドシェイク・局面確認が失敗した場合は「停止未観測」。`stop` は送らず、`quit` を一度送り3秒待つ。
- `stop` 後10秒以内に応答がない場合、または重複応答・想定外の出力があった場合は「応答異常/判定保留」。追加の `stop`・`go` は送らず、`quit` を一度送り3秒待つ。
- `quit` 後も終了しないときは、今回起動したPIDだけを対象にSIGTERMを一度送り2秒待つ。なお残る場合は自動でSIGKILLせず停止し、PIDと状態を提示して本人の個別判断を待つ。プロセス名指定や一括killは使わない。
- プロセスが終了した後、今回作成した一時保存先に証拠を保全し、エンジン設定・ShogiHome設定・棋譜・ログ設定には変更がないことを確認する。一時保存先は `/private/tmp/kaname-normal-stop-<実施日時>/` とし、前回G2の保存先は再利用しない。結果確認前に削除しない。

起動1回、`go` 最大1回、`stop` 最大1回、`quit` 最大1回を上限とし、自然完了・失敗・異常のいずれでも別局面や別時計での追加試行をしない。
