# 第37回：棋譜・局面のファイル保存の設計仕様

作成日：2026-09-24
設計合意日：2026-09-24
実装承認日：未承認

## 目的

メモリ上の `GameRecord` をJSONファイルへ明示的に保存し、後で読み込んで開始局面と成功手の履歴から現在局面を再現できるようにする。対局が終了しても、指し手順と局面を失わないことが目的である。

## 一次資料と今回の範囲

日本将棋連盟の対局規則第12条は、公式棋戦で記録係または自動記録による採譜を行い、棋譜と時間を正確に記録すると定める。棋譜利用のガイドラインは、公式記録に基づく指し手進行を再現した盤面図と、符号・記号による指し手順の文字情報を棋譜としている。

本プログラムは時間管理・公式棋譜の利用を扱わない。今回対象にするのは、自作CLI対局の開始局面と成功手を、プログラム終了後にも再現できるように保存することだけである。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[日本将棋連盟「棋譜利用のガイドライン」](https://www.shogi.or.jp/kifuguideline/)

## 確認問題で合意した範囲

1. ファイル形式はPython標準ライブラリのJSONとする。人が構造を確認でき、読込時に型・値を検証しやすいためである。
2. 保存対象は開始局面（盤上の駒、双方の持ち駒、手番）と、成功した `move` / `drop` の履歴とする。現在局面は重複保存せず、読込時に再現する。
3. 保存・読込は `GameRecord` を受け取る呼び出し側が明示的に行う。CLI終了時の自動保存、対局中の `save` / `load` コマンドは追加しない。
4. 保存前には内容全体をJSON値へ変換する。読込では構造・型・値と全手の再適用を検証する。不正な保存内容は `ValueError`、ファイル不存在・権限・入出力失敗は `OSError` として通知する。失敗時に既存の `GameRecord` を部分変更しない。
5. SFEN・USIは実装しない。JSONはこのプログラム専用の形式とし、Pythonの `Enum.auto()` の数値に依存しない固定文字列で列挙値を表す。

## 比較した方式と選択

### 選択：`game_record.py` に公開操作を置く

`GameRecord` に保存・読込の公開操作を追加する。記録の意味、開始局面・履歴の変換、履歴再適用による検証を一つの型に集められる。CLIはすでに `GameRecord` を返すため、CLIの責務を増やさずに呼び出し側が保存できる。

### 見送る方式

- 新しい `storage.py` へ分離する方式は、入出力境界が増え、今回の小さな保存範囲では学習対象を増やしすぎる。
- CLIに `save` / `load` を追加する方式は、対局中断・再開、入力解析、ロード後の表示・終了状態まで決める必要があり、今回合意した範囲を超える。
- SFEN・USIを使う方式は、外部標準の局面・通信仕様を新たに学ぶ必要があるため、別テーマに分離する。

## 公開インターフェース

`GameRecord.save(path)` は、開始局面と成功手の履歴をJSONファイルへ保存する操作とする。`path` は文字列または `pathlib.Path` を受け取る。JSON化できない内部状態を残さずに変換してからファイルへ書き込む。

`GameRecord.load(path)` は、JSONファイルから新しい `GameRecord` を作るクラスメソッドとする。読込途中に既存の記録を変更することはなく、成功したときだけ独立した新しい記録を返す。

正確なJSONキー名、バージョン識別子の要否、公開操作の引数型とdocstringは、実装計画で現行Python 3.9との互換性も含めて確定する。

## JSONの表現方針

- トップレベルに形式識別子を置き、他形式を誤って受理しない。
- 開始局面は、各盤上駒を筋・段・駒種・所有者で表す。マスの内部添字や `Enum.auto()` の整数は保存しない。
- 持ち駒は、先手・後手ごとに玉以外の基本駒種と枚数で表す。0枚の扱いは保存側・読込側で一貫させる。
- 手番は先手・後手の固定文字列で表す。
- 履歴は順番を保つ配列とし、盤上移動は出発・到着・成り指定、駒打ちは基本駒種・到着を表す。各要素には操作種別を持たせる。

## 読込とエラー処理

1. ファイルを読み、JSONとして解釈する。ファイル操作の失敗は `OSError` とする。
2. トップレベル、形式識別子、局面、履歴の構造とJSON値の型を検証する。不正なJSON、欠けたキー、未知の文字列、範囲外の筋・段、玉の持ち駒、負数の枚数などは `ValueError` とする。
3. 検証済みの開始局面から新しい `GameRecord` を作る。
4. 履歴を先頭から `GameRecord.apply_move` / `GameRecord.apply_drop` で再適用する。手番違い、移動候補外、二歩、王手放置など、既存規則で不合法な履歴は `ValueError` とする。
5. 全手が成功した場合だけ、新しい記録を返す。

読込操作は新しい記録だけを構築するため、失敗しても呼び出し側がすでに保持する記録を変更しない。保存操作も変換失敗時にファイルを開かない。OSレベルの書込み途中失敗から既存ファイルを保護する原子的置換は、今回の対象外とする。

## CLIとの関係

`run_game` はこれまでどおり `GameRecord` を返す。CLIの対局進行、入力形式、終了表示、EOF・Ctrl-C・投了・詰みの扱いは変更しない。ファイル保存・読込は、将来のCLIコマンドまたは別の呼び出し側が明示的に `GameRecord` の公開操作を呼ぶ。

## 対象外

- 対局中の `save` / `load` コマンド、終了時の自動保存、再開CLI
- SFEN、USI、外部GUIとの通信
- 時間記録、千日手、持将棋、入玉、反則勝敗
- 公式棋譜の配布・利用、棋譜表記の完全な標準化
- 原子的ファイル置換、複数形式の後方互換、ファイル選択UI

## 確認方法

TDDでは次を振る舞いごとに確認する。

1. 初期局面、通常移動、成り、駒打ちを含む記録を保存・読込すると、開始局面・履歴・再現局面が一致する。
2. JSONが列挙値の内部整数ではなく固定文字列を使う。
3. 存在しないファイルやOS入出力エラーは `OSError` として扱う。
4. 不正JSON、構造・型・列挙値・座標・持ち駒枚数が不正な内容、不合法な指し手履歴を `ValueError` で拒否する。
5. 読込失敗後も、既存の `GameRecord` とファイルへの保存前の内部状態を変更しない。
6. CLIの既存テストを通し、CLIの挙動が増減していないことを確認する。

実装後は対象テスト、全テスト、CLIスモーク、`git diff --check` を実行し、独立コードレビューのCritical・Important・Minorを記録する。
