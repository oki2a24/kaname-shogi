# 通常対局CLIの探索時間制御・承認済み設計

## 状態・意図・範囲

2026-10-20作成・**設計全体承認済み**。独立レビュー・再確認後に、棋譜変換の公開境界追加と本文で具体化した時間表現・判定順序・保存形式も含めて全体を提示し、本人は「yes」と回答した。設計書整理への先の「ok」と、この全体承認を区別する。個別回答・変更理由は[学習記録](../learning/cli-search-time-control-design.md)に保存する。本書は実装計画ではなく、作業順・TDD手順を定めない。製品コード・テスト・設定は変更していない。

目的は、通常対局CLIでもUSIと同じ探索入口・予算計算・停止契約を利用し、コンピュータの待ち方と停止後の一手を扱えるように設計すること。探索自体の高速化や棋力向上を目的とせず、訪問回数比較や過去の約5分という概算から時間・原因・予算を推定しない。時間内応答・深さ4完了を保証しない。

対象はCLIの五方式、コンピュータ側の時計、結果表示、既存保存・読込窓口での時計情報。USIの製品経路・時計予算式・停止確認点・設定値・結果型を変更する提案は含めない。ShogiHomeの設定・対局操作も含めない。人間側の時計、加算時間、先読み、探索中の入力受付、時計なしの選択、時間切れ判定を無効にする設定は今回追加しない。

## 本人が選んだ方針と代替案

本人は、単発の探索期間をCLI専用に直接設定する案よりも、USI利用時と同じ持ち時間・秒読みからの予算計算を希望した。コンピュータ側だけ時計を持ち、コンピュータ同士は双方に同じ初期条件を与え、それぞれの残り時間を独立管理する。

最初は既存CLIの事前詰み判定を維持し、新方式の完了深さ・手の由来も表示する案に個別合意した。その後、本人が本セッション全体でUSIとの差分提示を希望した。差分を示した上で、次のように合意を変更した。

- コンピュータ手には事前の詰み確認・全合法手生成を挟まず、USIと同じ制御付き入口を使う。合法手なしの正常結果は投了とする。
- 現行USI向け戻り値にない完了深さ・手の由来は表示しない。表示のために別の探索経路や共有結果型の拡張を作らない。

推薦する構成は、探索部品を現状のまま再利用し、CLIの対局管理層に時計を置くもの。GUIのタイマー・USI通信・担当スレッドまでCLIへ複製する案は採らない。同期CLIとしての違いを下記へ明記する。

## USIとの共通部分と差分

| 対象 | USIとの対応 |
| --- | --- |
| 探索入口 | `game_search.search_move(position, policy, rng, control)`を同じまま使う。これは探索結果を返す操作 |
| 五方式 | 既存三方式・全幅最大4手・αβ最大4手を維持。新二方式は各手で深さ1から開始 |
| 予算 | 同じ`load_time_management_config`と`calculate_search_budget`を使う操作。同じJSONを一回読み、実行中保持。式や値を複製・変更しない |
| 制御 | `SearchControl`は一探索の期限・停止要求を持つデータ。各コンピュータ手に新しく作り、深さ・子・次の手で原点を作り直さない |
| 結果 | 同じ`SearchResult`（終了状態と手のデータ）。`COMPLETE`の手なしは投了、`INTERRUPTED`は合法手、`SUPPRESSED`は手を適用しない |
| 時計の所有 | USIは各goで外部時計を受ける。CLIはGUIの役割として時計を保持・更新する。人間側は計時しない |
| 原点と終点 | USIはgo完成行読取りが原点。CLIはコンピュータ手番の処理開始を原点とし、予算作成・探索用局面取得の前に読む。終点は探索返却直後。通信、結果整形、出力、指し手適用・その合法性再検査はCLIの消費時間に含めない |
| 対局の時間切れ | USI自身は判定しない。CLIは返却後に実測で判定し、時間切れなら手を適用しない。ShogiHomeの100ms周期・イベント順とは異なる |
| 入力 | USIの整数ms・時計なし・明示0予算に対し、CLIは分・秒入力、既定値あり、同時0不可。CLIに時計なし選択は設けない |
| 中断 | CLIのCtrl+Cは対局終了。USIの通常stopと同じ操作ではない。USIの抑制・送信同期・担当回収を複製しない |
| 表示・保存 | 日本語の時計表示と時計つきCLI保存はCLI側の追加機能。USIのbestmoveやpositionへ新情報を送らない |

同じ局面・方式でも実測時刻が違えば停止地点や手が異なり得るため、USIと常に同じ手・深さになるという意味ではない。参照するShogiHomeソースは固定版1.28.1であり、現在インストールされている版・設定・実動作との同一性は確認していない。

## 起動時の入力と設定寿命

現在の対局形式・一手選択方針を選ぶ窓口を維持する。コンピュータが参加する場合だけ、方針選択に続けて「コンピュータの持ち時間（分、空入力10）」と「秒読み（秒、空入力30）」を尋ねる。人間同士には時計設定や時間予算JSONの読込を要求しない。

持ち時間・秒読みは0以上の整数とし、両方0を拒否する。空入力は各欄の既定値。10分・30秒は本人が選んだ暫定値であり、性能測定に基づく最適値でも将棋共通の標準でもない。不正入力は理由を表示して時計の入力をやり直し、設定が確定するまで対局を開始しない。入力表記の提案は前後空白を除いた半角十進数字のみ（符号・小数・指数表記は不可）とする。USIの符号付き整数表記の受付とは異なるCLI側の表記である。

予算用JSONはUSIと同じローダーで、コンピュータが参加する対局の入力準備段階で一回読み、実行中同じ設定を使う。読込失敗・不正設定を別の既定値で隠さず診断して起動を中止する。実入口はstderr診断・終了1を提案する。直接呼出しでの既存入口の互換性・新引数名は、後続計画で既存呼出し元を調べて定める構築者判断とする。

対局モードと一手選択方針は現行どおり実行中に固定し、時計条件も手動で途中変更しない。保存棋譜の読込は保存された対局状態への復帰なので、時計情報がある場合はその設定・残り時間を採用する。時計のない旧棋譜の補完には、後から読んだ棋譜の値ではなく、そのCLI起動時に入力した初期条件を使う。

## 時計のデータと更新（草案での具体化）

局面`Position`（盤・持ち駒・手番のデータ）へ時計を混ぜない。CLIの対局状態として、棋譜と別に初期時計条件・先後それぞれの残り持ち時間を保持する。新規開始では両側へ同じ初期値を置き、人間担当側の値は計時・減算しない。保存棋譜を別モードで開いた場合も、動作を決めるモード・方式は現在のCLI選択を使う。保存された先後の残り時間は保持し、コンピュータ担当側だけ減らす。

数値表現は以下のとおり。名前・単位・丸めはアシスタントが草案で具体化し、本文全体への本人「yes」によって承認された。

| 値 | 表現・制約 |
| --- | --- |
| 初期持ち時間・秒読み | `initial_time_ms`・`byoyomi_ms`。非負整数ms、bool不可、同時0不可。CLI入力の分は60000倍、秒は1000倍する |
| 残り持ち時間 | `sente_remaining_ns`・`gote_remaining_ns`。非負整数ns、bool不可、それぞれ初期持ち時間のns換算以下 |
| 今回の計時 | USIと同じ単調時計`monotonic_ns`で開始・返却時を読む。時計取得操作は差替え可能にし、SearchControlにも同じ時計を渡す |
| 一手の消費 | `elapsed_ns = returned_ns - started_ns`。非負を前提とし、負なら時計契約の故障として扱う。表示値で計算しない |
| 予算へ渡す残り時間 | 手番開始時の残りnsを1000000で割った整数商ms。1ms未満の切捨ては予算用変換だけで、保持する残りnsを切り捨てない |
| 更新値 | 手番側だけ`max(0, 開始時の残りns - elapsed_ns)`。秒読みは減らして持ち越さず、各手で元の設定値を使う |

整数nsを保持するのは、手番ごとの端数切捨てを積み重ねて残り時間を作らないため。予算へ渡す時計値は切捨てで最大1ms未満小さくなるが、0msでは既存式の秒読み分岐へ入るため、探索予算の値まで単調に小さくなるという意味ではない。1ms未満の残りを0msで受けたUSIと同じ式を使い、実際の時間切れは切り捨てていない残りnsで別判定する。外部時計を毎回受け取るUSIにこの残りnsの保持処理はない。起動初期値とJSON予算設定を分け、応答余裕などの予算係数を棋譜へ複写しない。

## 一手と終了の契約

コンピュータ担当側の手番処理に入った直後、探索用の局面取得・予算作成の前を計時原点とする。手番の担当判定までの対局ループ管理は原点の外。時計の現在値と一回読んだ予算設定から予算を計算し、同じ原点・時計の新SearchControlを作る。探索用局面を非共有で取得し、同じ制御付き入口を同期的に一回呼ぶ。事前の無制御な詰み確認・全合法手生成はしない。

返却直後に時計を読み、消費時間と更新後の残り時間を計算する。以下の優先順位は二段階案を具体化した草案である。

| 状態 | CLIでの扱い |
| --- | --- |
| 探索や時計の例外 | 正常停止・投了・時間切れへ変換しない。元の故障を伝える。Ctrl+C/EOFは既存の対局終了境界で扱う |
| SUPPRESSED | 手を適用せず対局を終了する。投了・時間切れへ変換しない。通常CLIで要求する状態ではないが、返された場合も手を復活させない |
| 非抑制で対局時計の時間切れ | 返された手があっても適用・指した手としての表示をせず、時間切れ負けで終了する。手なし結果でもこの時計判定を先に行う |
| 時間内のCOMPLETE・手なし | USIのbestmove resignに対応し、手番側の投了として相手の勝ちを表示する。事前の詰み優先へ戻さない |
| 時間内のCOMPLETE・手あり | 返された一手を一回適用し、対局を続ける |
| 時間内のINTERRUPTED | 返された合法手を一回適用し、対局を続ける。未完了手を作り直したり再探索したりしない |

探索予算の上限到達は通常停止の契機であり、対局時計の時間切れと同一ではない。対局時計は、`elapsed_ns >= 開始時の残りns + byoyomi_ms × 1000000`で時間切れとする。判定には等号を含め、表示用の丸めを使わない。秒読み0・残り持ち時間0の保存状態も保持できるが、次のコンピュータ手ではこの条件で時間切れとなる。原点で即座に強制終了する特別な探索分岐は作らず、既存探索から返った後に判定する。

現在の設定には応答余裕2000msがあるが、この値は設定の現在値であり固定の新ルールではない。余裕より長く単一処理・OS待ち等が続けば対局時計を超過し得る。合法予備手または手なし確定までは通常停止を保留する既存契約も維持する。返却前に時間切れ画面を出すタイマーや強制中断は設けない。

人間手番は現行CLIの詰み確認・入力・投了・EOF/Ctrl+Cを維持し、消費時間を減らさない。コンピュータの手を適用した後に人間が詰んでいれば、人間側の次手番の既存判定で終局する。終局理由は成功した指し手の履歴へ混ぜない。

## 利用者への表示（草案文言）

コンピュータの手番開始時に「先手／後手のコンピュータが思考中です。」と一回表示する案。開始表示は計時原点より前に出す。探索中の定期更新は行わない。

着手する場合は次の情報を一組として表示し、その後に盤面を表示する。既存の指し手表記を利用する。

```text
探索状態: 完了
消費時間: 1.234秒
先手の残り持ち時間: 09:58.766（秒読み30秒）
先手の指し手: …
```

状態は既存COMPLETEを「完了」、INTERRUPTEDを「通常停止」と表示する。「完了」はその方式で必要な調査が完了した意味であり、全方式が深さ4まで読んだ意味ではない。通常停止を目標・上限のどちらかと断定しない。表示しない深さ・評価・手の由来を推測しない。

消費時間と残り時間はnsをmsへ切捨てた値を用いて小数第3位まで表示する案。秒未満の内部端数を保持し、表示から内部値を復元しない。残り時間の分は59を超えてもよい。秒読みは設定値であり、その手の未使用分ではない。

時間切れは消費時間と更新後残り時間を表示し、「先手／後手が時間切れです。後手／先手の勝ちです。」とする。探索が通常停止だったかどうかと時間切れ負けを混同しない。投了は同じ時計情報と既存投了文言。抑制は「探索結果が抑制されたため対局を終了しました。」、Ctrl+C/EOFは現行の終了表示。抑制・中断を勝敗へ変換しない。

時計更新・適用の確定後に再び保存コマンドを受け付ける。Ctrl+Cで出力の途中まで表示される可能性や、既存適用処理の任意地点の割込みに対して、新しい原子性保証は設けない。既存の終了境界を維持し、中断後に手を再取得・再表示しない。

## 保存・読込の表現と再利用境界（提案）

USIにはないCLI管理側の追加である。時計を将棋局面やUSI時計設定へ混ぜず、CLIの対局保存を一ファイルで保持する。二つの別ファイルへ局面と時計を分ける案は、取り違え・片方だけの保存を避けるため採らない。

提案する保存形式は、`format`が`kaname-shogi-cli-session-v1`の外側オブジェクトで、`game_record`に既存の`kaname-shogi-game-record-v1`全体、`clock`に上記四つの時計値を置く。外側とclockは指定キーのみ必須とし、未知・不足・不正型・bool・負値・範囲超過を拒否する。clock省略やnullを旧棋譜と解釈しない。初期条件と残り時間だけを保存し、計時原点・終了時刻・SearchControl・探索途中結果を保存しない。

棋譜の既存変換・合法手再生は複製せず再利用する。ただし現行GameRecordはファイルsave/loadのみ公開し、辞書変換は非公開関数である。**提案する追加範囲**は、GameRecordの既存v1辞書変換・検証再生をファイルI/Oから利用可能な公開操作へ分け、CLI保存側から同じ処理へ委譲できるようにすること。名前の候補は`to_payload`（辞書データを返す操作）と`from_payload`（検証して棋譜データを作る操作）。既存save/loadも同じ本体へ委譲し、v1の構造・既存API契約を維持する。この棋譜の再利用境界追加は草案時点では個別未承認だったが、全体提示時に追加範囲として明示し、本人の設計全体への「yes」により承認された。USI・共通探索のAPI拡張は必要ない。

新形式の読込では、一時的な新しい棋譜・時計状態を全て検証してから現在のCLI状態を置き換える。棋譜・時計・I/Oのいずれが不正でも読込前の双方を維持し、理由を表示して同じ人間手番へ戻す。

旧v1棋譜は現行の規則で読めるように保つ。コンピュータが参加する場合は起動時の入力初期条件から双方の時計を新しく作り、「時計情報がないため、対局開始時に選んだ初期値を使用しました。」と表示する。時計つき形式の不正をこの補完へ落とさない。人間同士で旧形式を読む場合は時計を作らない。

人間同士で時計つき形式を開いた場合も値を検証・保持するが、人間の手では減らさない。保持した時計があれば再保存時に外側形式で保存する。時計がない人間同士の新規記録は従来v1形式で保存する。読込によってモードや方式は変更しない。

時計つきの新形式を過去版のCLI・GameRecord.loadが直接読めることは保証しない。CLIの読込窓口で形式を判別する。保存コマンドの利用可能時点は現行の人間入力中のままとし、コンピュータ同士の探索中保存・自動保存・終局後の新しい保存対話は今回設けない。

## 確認方針と検出対象

これは設計上の確認方針であり、実装計画・テスト作成・実行結果ではない。[検出力点検](../knowledge/test-coverage-review.md)と個人観察の方針に従い、独立した時計値・結果・期待状態で確認する。実時間で特定深さや一定秒数以内の返却を期待する検証は置かない。

| 契約 | 代表ケース・独立期待値 | 検出したい誤り |
| --- | --- | --- |
| 入力・設定寿命 | 空欄10/30、0/30、10/0、0/0、不正文字、人間同士。JSONを一回だけ読み別手・読込後も同じ設定 | 同時0を無制限化、人間同士への不要設定、手ごとの再読込、故障を既定値で隠す |
| 共通入口と原点 | 五方式それぞれ一回のgame_search.search_move、事前の無制御詰み・全生成なし。同じ原点・同じ時計で予算準備・局面取得後に探索 | 旧choose_moveへの誤接続、余分な生成、原点を探索直前へ遅らせる、手番をまたぐ制御再利用 |
| 予算 | 固定の残り時間と設定を既存式へそのまま渡す。1ms未満の残りも含め、入力ms変換と保持nsを別確認 | 式の複製、単位違い、0と時計なし混同、丸めによる持ち時間の累積増減 |
| 時間更新 | 5秒＋30秒で20秒消費後は0秒＋次手30秒。両側で異なる残り時間、人間手と表示の遅延 | 秒読みの使い残し持越し、相手時計減算、人間入力や表示時間の誤減算 |
| 時間切れ | 許容境界の1ns前・一致・1ns後。予算上限超過でも許容時間内なら着手。結果手あり・手なし・抑制 | 等号の誤り、表示丸めで判定、予算上限を時間切れ負け化、時間切れ後の手の適用・指した表示、抑制を投了化 |
| 投了・停止 | 時間内COMPLETE/Noneは投了、INTERRUPTEDは返された手を一回適用。コンピュータの事前詰み優先を置かない | 手なしを勝敗不明へ変換、合法予備手の不採用、途中結果を再選択・再探索 |
| 表示・中断 | 合成COMPLETE/INTERRUPTEDと固定時間を対応表示。出力・入力・探索からのCtrl+Cを終了として扱う | 架空の完了深さ・手の由来、通常停止の原因断定、Ctrl+Cを通常停止として着手 |
| 時計つき保存 | 別々の先後残りnsを保存して再読込、終了時刻を持たない。旧v1から起動初期値、不正clockでは旧状態維持 | 相手値の上書き、再開ごとのリセット、保存中の経過減算、不正情報を時計なし扱い、局面だけ置換 |
| 回帰 | 人間同士・既存保存v1・既存棋譜API、五方式の選択、USI時計・stop・抑制・応答の既存契約 | CLI接続に伴うUSI・共通探索・棋譜変換の破壊 |

既存の予算・制御・方式・将棋部品の検証は内部契約を補完するが、CLIの原点・入力・時計更新・表示・保存読込の接続を単独では確認しない。後続実装では対象契約ごとの検出力・単独と全体の補完範囲を点検し、件数だけで十分としない。今回製品テスト・変異注入は行わない。
