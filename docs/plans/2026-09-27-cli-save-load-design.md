# 第42回設計仕様：CLIでの明示的な保存・読込

作成日：2026-09-27

## 目的

対局中の人間入力として `save <path>` と `load <path>` を追加し、既存の
`GameRecord.save` / `GameRecord.load` を用いて、対局を明示的に保存・再開できるようにする。
JSON保存形式や将棋の局面規則を変更せず、CLIの入力解析・表示・再入力と、保存形式を担う
`GameRecord` の責務を分ける。

## 一次資料と対象範囲

日本将棋連盟の対局規則第2条は、対局を初手から終局まで指し手を進めることと説明し、
第6条は詰みまたは投了による終了を定める。棋譜利用のガイドラインは、指し手進行を再現した
盤面図と指し手順の文字情報を棋譜と説明する。

今回の対象は、既存の自作JSON棋譜をCLIから明示的に保存・読込することだけである。公式棋譜
形式、時間、千日手、持将棋、入玉、反則、SFEN、USI、自動保存は扱わない。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、
[日本将棋連盟「棋譜利用のガイドライン」](https://www.shogi.or.jp/kifuguideline/)

## 合意した仕様

### 入力形式と保存先

- 人間担当の手番で、半角ASCIIの `save <path>` と `load <path>` を受け付ける。
- `<path>` は空白を含まない一語とし、実行時のカレントディレクトリ基準の相対パスまたは絶対パスを受け付ける。
- 親ディレクトリは自動作成しない。
- 形式が合わない入力は、既存と同じ入力形式エラーにする。

### 責務の分離

- `GameRecord` は変更しない。既存の専用JSON形式、保存、読込、読込時の履歴再適用、構造・合法性検証を担う。
- CLIの `parse_command` は `_SaveCommand` と `_LoadCommand` を作る。これらはパスを保持する入力値であり、ファイル操作をしない。
- CLIの対局進行が `GameRecord.save(path)` と `GameRecord.load(path)` を呼び、表示と再入力を担う。

### 保存・読込後の進行

- `save` 成功時は成功を表示し、局面・手番・履歴を変更せず、同じ人間手番の入力へ戻る。
- `load` 成功時は、`GameRecord.load(path)` が返した新しい記録で対局ループの記録を完全に置き換える。
- 読込直後に、再現された局面（盤面・手番・持ち駒を含む）を一度表示する。
- その手番が人間担当なら入力待ちへ、コンピュータ担当なら既存の自動手の進行へ移る。
- 読込前の指し手、`save` / `load`、投了、EOF、Ctrl-C、エラーは履歴に残さない。読込後の成功した `move` / `drop` だけを、読込済み履歴の末尾へ追加する。

### 失敗時と終了状態

- `save` の `OSError`、`load` の `OSError` または `ValueError` は、理由に `エラー：` を付けて表示する。
- 失敗した `save` は記録を変更せず、失敗した `load` は既存記録を置き換えない。いずれも同じ人間手番で再入力する。
- 詰み、投了、EOF、Ctrl-C、コンピュータの合法手空一覧は既存の優先順位・表示・終了動作を保つ。終了後は入力を受け付けず、保存も読込もできない。
- 終了時の自動保存は行わない。

## 実装の見通し

`kaname_shogi/cli.py` にだけ、保存・読込コマンドの入力値、解析、対局ループ内の分岐を追加する。
`kaname_shogi/game_record.py` とJSON形式は変更しない。CLIテストに、入力解析、保存後の同一手番、読込後の局面・手番・表示・担当切替、失敗時の不変性と再入力、終了時に入力を受けないこと、履歴の置換を追加する。

## 仕様の自己レビュー

- 未決定のプレースホルダはない。
- `load` の置換は成功後だけであり、失敗時不変性と矛盾しない。
- 保存形式は `GameRecord` の既存APIに限定し、CLIがJSON構造を知る設計ではない。
- 今回は対局中の人間入力だけを対象とし、終了後の保存や自動保存を含めない。
