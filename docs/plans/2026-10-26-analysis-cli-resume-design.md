2026-10-26作成。本人は分析CLIの再開機能と局単位チェックポイントを選び、本設計と実装計画全体を承認した。作成時点では実装前だった。2026-10-26現在、承認範囲の実装と小規模fixture検証は `/Users/oki2a24/.codex/worktrees/c1-analysis-resume/kaname-shogi` の `codex/c1-analysis-resume` で完了した。独立最終レビューでCritical/Importantなし。fstat前の外部lock path差し替え競合は保証対象外として記録した。main・元checkoutへは未統合。

## 目的

長時間かかる `kaname_shogi.analyze_comparison` をCtrl-C等で止めても、既に検証した局の棋譜再生を繰り返さずに続けられるようにする。C1確認比較の結果・統計判定・得点は変えず、比較結果ディレクトリも変更しない。

## 現行動作と設計上の制約

- 分析CLIは条件・予定を読み、予定順に全局のJSONを `_load_game` で合法再生・照合する。summaryを局から再集計して照合し、全局・全組の分析値を作ってから新規の分析JSONを保存する。
- 途中状態はメモリだけにあり、Ctrl-Cでは終了コード130を返すが、次回は先頭から検証し直す。
- 各局の高コスト検証を省くには、再開時に前回の検証済み結果を信頼する必要がある。チェックポイントの形式・条件・元入力ハッシュ・分析器のソース指紋を照合し、偶発的な破損や異なる入力の再利用を拒否する。署名鍵を持たないローカルファイルなので、人が内容を書き換えた場合に意味的な改ざんまで見抜く保証はしない。この制約は本人が了承した。
- 現行の完成分析JSON v2、入力比較結果、95%区間の計算方法と候補方式視点の得点を維持する。通常CLIのSFEN入出力、飛車可動性バージョン2、比較CLIの追加高速化は扱わない。

## 採用する方法と代替案

1. **局単位の検証済みチェックポイント（採用案）**：各局の検証完了後に、その局の入力SHA-256と最終集計に必要な小さな結果を原子的に保存する。再開時に保存済み局の入力ハッシュを再確認し、検証済み局は読み戻して未検証局だけを合法再生する。停止時に失うのは処理中の一局分まで。
2. **保存済み局も再検証**：既存比較CLIと同じく、保存済み局を再度合法再生する。検証済み局のチェックポイントを信用する問題は避けられるが、再開後も大半の時間がかかるので目的に合わない。
3. **局途中の再開点を保存**：棋譜再生・計時照合・千日手履歴などの途中状態も保存する。保存形式と復元条件が大きく複雑になり、局単位チェックポイントより作業中の一局だけ多く救うため、今回の目的に対して採用しない。

本人が選んだのは1である。再開時は、元入力をSHA-256で照合した後、CLIが作成したチェックポイントをローカル中間データとして再利用する。

## CLIと保存の流れ

- 初回実行の引数は現行どおり `--input-dir` と `--output`。出力JSONの隣に `<output名>.checkpoint/` を作り、conditions・summaryのSHA-256、予定局一覧、分析器指紋を含むmanifestと、検証済み局ごとのチェックポイントを保存する。初回は棋譜ファイル全体を余分に先読みせず、検証時に得た各局のハッシュをその局の記録へ入れる。
- 各局のチェックポイントは、その局の入力JSONを通常どおり完全検証した後にだけ原子的に保存する。処理中の局は完了扱いにしない。
- 中断時は終了コード130を返し、分析JSONは作らず、完成済み局のチェックポイントを残す。中断表示に保存済み局数と再開に使う `--resume` を案内する。
- 再開時は同じ `--input-dir` と `--output` に `--resume` を加える。入力ディレクトリ、条件、summary、局の集合、各保存済み局のファイルハッシュ、チェックポイント形式、Pythonソース指紋を照合する。保存済み局だけを再生せず、欠落している局を予定順に検証する。未処理局は通常検証の読込時にハッシュを計算する。
- チェックポイントがある状態で `--resume` を付けない場合、最初からの実行で既存進捗を誤って上書きしないよう拒否する。`--resume` だけを付けてチェックポイントがない場合も拒否する。出力JSONが既にある場合は引き続き上書きしない。
- 全局の検証後、既存どおりsummaryの再集計、組得点、信頼区間を照合・計算し、最終分析JSONを新規保存する。完成保存後にチェックポイントを削除する。完成JSONの保存後・削除前に異常終了した場合は完成JSONを保持し、再実行で上書きしない。
- 同じ出力先の同時分析を排他ロックで拒否する。強制終了でロックが残った場合は、PIDが動作中でないことを確認してから人が削除する既存比較CLIの方針を踏襲する。
- 進捗表示の常時更新、局の並列分析、局途中からの復元、自動削除による最初からのやり直しは今回の対象外。入力が変更された・チェックポイントが壊れた場合は安全のため再開を拒否し、診断を表示する。新しくやり直す場合のチェックポイント削除は利用者が内容を確認して行う。

## チェックポイントに保存する情報

- manifest：チェックポイント形式版、入力ディレクトリ識別、条件・summaryのSHA-256、予定の順序と局ID、分析器Pythonソース指紋。
- 一局分：局IDと元局JSONのSHA-256、検証済み終局理由、勝者先後・方式、成功手数、方式別計時の件数・合計・最大値。各記録は形式・予定との一致に加え、記録内容のチェックサムも照合する。
- 局面・組・先後の予定情報はmanifest内の検証済みscheduleから復元する。棋譜本文・手ごとの全計時は複製しない。summaryの再集計には一局ごとの件数・勝者・計時集計から作る新しい軽量集計経路を使い、元summaryと全項目を照合する。これはsummary v1/v2/v3の既存検証と同じ期待値を生成する必要があり、最終計画で独立期待値と境界ケースを明記する。
- 再開後の組得点は、復元した終局理由・勝者方式から既存の `game_score_bounds` と `make_pair_score` で改めて導出する。保存済みの区間や平均値をそのまま信用しない。

## 対象範囲と非対象

- 主な変更対象は `comparison_result_io.py` の一局単位読込・分析用軽量集計・全体読込境界と `main`、新しい分析チェックポイント管理コードである。`analyze_comparison.py` は現在 `main` を再公開する薄い入口のため、必要がなければ変更しない。既存 `load_completed_comparison` の呼出し契約は可能な限り維持する。具体的な分割は実装計画で定める。
- 正常入力時の既存分析JSONの統計項目・得点・丸め・入力SHA一覧・判定は維持する。`analyzer` のソース/Git識別は新実装に応じて変わる。
- CLI呼出し例・中断時の再開方法・チェックポイント削除の注意点を利用資料へ記録する。主線C1の評価自体は既に独立分析済みであり、この機能の正しさ確認に実データの強さ再判定や長時間分析CLIの再実行は行わない。
- 新しい依存関係、比較対局の再実行、統計手法変更、並列化、任意ファイルを開くパス参照、改ざん耐性の署名、局途中保存は追加しない。

## 確認方法と検出力

実装計画では振る舞いごとに、対象契約・独立した期待値・失敗理由・最小変更・Green・Refactor要否を示す。最低限、次を対象にする。

| 契約 | 代表ケース | 検出したい誤り |
| --- | --- | --- |
| 初回実行は全局を検証し、既存どおりの分析結果だけを最終保存する | 手書きの少数局fixtureと独立に算出した勝敗・得点・入力SHA | チェックポイント値を分析結果へ混ぜる、途中JSONを完成結果と見せる |
| 各局の検証完了後だけ進捗が確定する | 2局目の検証・保存で割込みを注入 | 未検証局や途中局を完了扱いする、保存済み1局を失う |
| 再開は保存済み局を再生せず、未完了局を一度だけ検証する | 2局中1局のcheckpoint作成後に再開し、検証呼出しと独立期待値を数える | 全局再生し直す、1局を飛ばす、同じ局を二重加算する |
| 条件と入力が一致する場合だけcheckpointを使う | conditions・summary・局JSON・局集合・ソース指紋を一つずつ変更 | ハッシュ照合省略、余分/欠落ファイル許容、条件を越えたキャッシュ共有 |
| checkpoint破損や排他競合で既存成果物を壊さない | JSON破損・未知schema・ロック残存・完成output存在 | 誤った再開、既存output上書き、並行書込み |
| 途中で失敗しても次回へ残るのは完成済み局だけ | 一局checkpoint保存前/後、最終output保存時の失敗と割込み | 部分JSONの読込み、完了済み局の誤削除、正常完了を装う |

正常完了した小規模fixtureでは、初回・中断再開後の最終分析JSONについて、`analyzer` 識別を除いた全項目と入力ファイルSHAの一致を確認する。必要なら既存分析結果との新旧比較は小規模fixtureのみに限定し、4,080局の実測入力を使った長時間コマンドは人が明示的に実行する。

このテスト群が検査できるのはCLIが生成した状態遷移と、同じ入力・同じソース指紋での再利用である。チェックポイントの悪意ある手編集、電源断時のファイルシステム永続性、全OSのロック意味論、壊れた記憶媒体、任意の入力サイズは証明しない。代表変異を隔離コピーへ入れ、想定したアサーションが失敗することを確認する。単独テストと全体回帰の検出範囲を分けて記録する。
