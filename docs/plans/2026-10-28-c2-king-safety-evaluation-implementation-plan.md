## 目的と設計前提

[設計案](2026-10-28-c2-king-safety-evaluation-design.md)に沿い、比較CLIだけに安全度評価付き一手選択を接続する。baseline material-king-safety-material-only（重み10/0）とcandidate material-king-safety（重み10/1）を、同じB2一手選択経路で比較できるようにする。通常CLI・USIには接続しない。

- B2の評価部品を再利用し、既存MATERIAL・ランダム・二手/四手方式の振る舞いと既定値を維持する。
- 両比較条件は一手の深さ、詰み優先、先後交換、局面、乱数条件をそろえ、安全度項だけを変える。
- 条件・artifact・checkpoint・summary・分析の既存データ契約と過去結果の再読込を保つ。
- C2専用の局面セットと短いpipeline試験までを実装側で用意する。長時間比較・分析CLIは本人が端末で実行する。
- 設計で確定していないサンプル数・対局上限・実行予算をコードへ固定しない。

## 対象外

通常CLI・USIへの接続、通常CLIのSFEN入出力、飛車可動性バージョン2、二手・四手探索への適用、別評価項目、ShogiHomeでの対局、長時間の比較・分析実行、main統合、push。

## Task 1：一手選択と比較方式の接続

1. 対象契約と検出したい誤りを、B2部品、game_search、comparisonの現行分岐から整理する。
2. 対象テストを先に追加し、単独実行で失敗理由を確認する。最低限、B2手計算例の評価差が候補方式へ届くこと、対照で同点になること、後手視点反転、一手詰み優先を分けて確認する。
3. material-king-safety-material-onlyとmaterial-king-safetyの二方式を内部選択データへ追加し、比較CLIの対局経路から同じB2一手選択へルーティングする。重みは対照10/0、候補10/1とし、既存MATERIALは変更しない。
4. 対象テストGreenと、比較の一手選択・game_search関連テストを実行する。
5. Refactor要否を記録し、変更有無にかかわらず独立コードレビューを行う。Critical / Important / Minorの結論を学習記録・計画へ残す。Critical / Importantは解消後に再検証・再レビューする。

検出範囲の点検：主契約は評価関数の経路選択、符号、評価値と選択結果の対応、既存分岐の不変である。独立期待値は先手玉５五・後手玉９一・後手歩５三の既存手計算例（候補は合成 -11 対 -10、対照は -10 対 -10）とする。単独テストは評価・符号を、関連テストは合法候補と既存手選択を、全体テストはモジュール間の既定経路を検出する。通常CLI・USIの接続、一般的な安全度の強さ、全局面の最善手、棋力は検証しない。

## Task 2：比較CLIの条件指定

1. baseline/candidate名と重みの入力、未知名・不整合条件の拒否を確認するテストを追加する。
2. 比較CLIのconditions解釈で固定名を登録し、方式名・駒得/安全度重みを保存条件へ反映する。
3. 旧来のmaterial・rook-mobility等の比較条件、CLI既定値、呼び出し動作を変えないことを関連テストで確認する。
4. comparison I/Oとcompare_gamesの対象テストを実行する。
5. Refactor要否と独立レビューをTask単位で記録し、必要な修正後に再検証・再レビューする。

検出範囲の点検：方式選択、重み対応、異常入力拒否、既定値・旧条件の維持を分けて確認する。期待値はCLI入力とconditionsへの保存契約から独立に決める。単独テストは名前・重みの解決を、関連群は実行直前の構成を確認する。標準CLI・USIの方式一覧は変更しない。

## Task 3：保存結果・再開・分析の互換性

1. 新方式名・重みのartifact保存と、古いartifact読込の境界テストを追加する。
2. winner policy、計時、summary、checkpoint、局単位再開、分析・再読込で方式情報が一致するよう必要最小限を更新する。旧artifactでは新方式のsummary項目を要求しない。
3. 不正・欠落・改変条件を適切な段階で拒否し、過去の比較結果が分析できることを確認する。
4. 比較結果I/O・分析・resumeの対象テストと関連テストを実行する。
5. Refactor要否、独立レビュー、Critical / Important / MinorをTask単位で記録し、必要な再検証・再レビューを行う。

検出範囲の点検：条件整合、勝者識別、計時、checkpoint再開、既存保存結果の互換を別契約にする。単独I/O試験は往復と拒否を、関連試験はsummary・分析を確認する。新方式を含む短いpipelineはTask 4で入口間の契約を補う。

## Task 4：C2局面・小規模pipeline・総合検証

1. 期待値と駒得差の影響を分けて確認できる、合法なC2専用比較局面を作る。局面選定と期待値の根拠を文書に記録する。C1の位置ファイルをそのまま流用しない。
2. 比較条件の検査から短いpipelineまでのテストを追加し、固定入力で保存・再読込・分析を通す。長時間対局をテストしない。
3. 代表変異・テストの失敗理由を確認し、対象契約ごとの検出力を記録する。単に件数やGreenで十分と判断しない。
4. Refactor要否確認後、Task単位および最終の独立コードレビューを行う。Critical / Importantを解消して再検証・再レビューする。
5. python3 scripts/run_tests_parallel.py、必要な逐次診断、Ruff import整理・format・check、git diff --check、文書リンク点検、差分レビューを行う。
6. 成果・検証出力・未検証事項・実験条件の未決定を学習記録、知識メモ、計画、resume、next-topics、ロードマップへ反映する。

検出範囲の点検：C2局面では安全度だけが違う手選択例と実際の対局局面を区別する。期待値は安全度定義・合法手・重みから独立計算し、pipelineの実出力を正解生成に使わない。単独テストは規則・局面検証を、関連群は全保存条件を、短いpipelineは比較CLIの入口間の実接続を、全体テストは旧機能回帰を担う。長時間の強さ比較・実機性能・棋力改善は未検証で、本人が別途実行する。

## レビューと統合の境界

Refactor後は変更の有無にかかわらず独立コードレビューを実施し、学習記録にCritical / Important / Minorと対応を残す。実装・検証・レビュー・記録がそろった段階で、統合前の成果を提示する。main統合とpushは本計画で承認されない。必要になった時点で別途本人の明示承認を得る。統合後は統合先で再検証し、最後の理解確認を一問だけ行う。
