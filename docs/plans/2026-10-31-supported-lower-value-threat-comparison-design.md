# 支えがある駒への低価値駒の利き：比較設計案

作成日：2026-10-31。本人はVの比較を先に設計することを選び、比較方式として「V典型局面で予備比較、独立した幅広い局面で確認比較」の二段階案を選択した。選択理由は本人が述べた範囲を越えて推測しない。本人は本設計と実装計画を2026-10-31に明示承認した。比較CLIの接続、実験条件の最終固定、対局実行、棋力向上の判定はまだ行っていない。

## 目的

B段階で作成したVを、同じ一手選択経路の重み0と1で比較し、Vを追加した候補が、事前に定めた比較条件で基準より高い得点を得るか調べる。

評価項目は同じ実装を使い、重みだけを変える。

| 方式 | 重み | 通常評価 |
| --- | --- | --- |
| 対照 | `material=10, undefended=1, supported_threat=0` | `10M+U` |
| 候補 | `material=10, undefended=1, supported_threat=1` | `10M+U+V` |

両方式とも `evaluate_material_piece_threat` と既存の一手選択器を使う。一手詰み優先、合法手生成、開始側視点、同点時の扱い、終局規則をそろえる。比較差はVの係数だけにする。重み0でもVを計算する既存契約を保つ。Vの定義・参考価値・固定局面期待値は[B段階の設計](2026-10-31-supported-piece-lower-value-threat-design.md)を参照し、変更しない。

## ゴールと非ゴール

### ゴール

- 比較CLIだけに対照・候補方式を接続し、seed一覧、条件、棋譜、集計へ実効重みを保存・検証する。
- Vが現れる典型局面で予備比較を行い、接続、選択差、所要時間、上限未決着の状況を確認する。
- 予備比較とは別の幅広い固定局面セット・独立seed一覧で確認比較を行い、一つの事前指定済み主判定を得る。
- 結論を比較した局面群、選択方式、手数上限、実行条件に限定し、一般棋力の証明と混同しない。

### 非ゴール

- 通常CLI・USIからV方式を選べるようにする。
- 通常CLIのSFEN入出力、飛車可動性バージョン2、玉安全度との合成、二手・四手への適用を追加する。
- ShogiHomeで実践する。PCへアクセス可能との本人連絡があった場合に、別途提案する。
- Vの重みを最適化する、合法な交換損得や詰みを評価する、全配置または一般対局での強さを保証する。
- 本設計の承認だけで長時間比較を開始しない。本人は両比較をworker 4で行うよう明示指示済みであるため、実装・検証と条件固定を終え、実行時にworker 4が利用できることを確認してから実施する。条件を実質変更する必要があれば改めて承認を得る。

## 比較方式と実験の契約

### 接続先

比較CLIの `--baseline` / `--candidate` に限って二方式を追加する。候補識別子案は `material-piece-threat-v0` と `material-piece-threat-v1` とし、末尾はV重み0/1を示す。条件JSONの `policy_parameters` に各方式の `material`、`undefended`、`supported_threat`、一手詰み優先の実効値を保存する。識別子は実装計画で最終確認する。

両方式は `PieceThreatWeights(material=10, undefended=1, supported_threat=0/1)` を使い、同じ `evaluate_material_piece_threat` を `choose_one_ply_move` へ渡す。`10M+U` と `10M+U+V` 以外の選択・探索条件を変えない。比較CLIの既存seed-list、先後交換二局一組、出力の新規パス、未決着を候補得点 `[0,1]` の範囲に残す分析を使う。

### 検討した方式

| 方式 | 利点 | 限界 |
| --- | --- | --- |
| V典型局面だけで比較 | Vが判断を変える条件を観察しやすく、原因を切り分けやすい | 通常の広い局面群での棋力差を示す範囲が狭い |
| 幅広い局面だけで比較 | 実際の一局を通じた候補差を評価できる | Vが効く局面が少ないと、接続不備とVの影響が分かりにくい |
| V典型局面の予備比較と、独立した幅広い確認比較 | 予備でVの作動と実行負担を見てから、別の広い局面集合で主判定できる | 局面作成・seed準備・実行量が増え、二段階それぞれを管理する必要がある |

本人は三つ目を選択した。本人が示した選択内容を記録し、それ以上の理由は補わない。

## 局面設計

比較CLIは平手初期局面からの合法なUSI指し手列で開始局面を作る。玉なしのV設計例A/B/Cは独立期待値の確認用であり、実験用の対局開始局面としてそのまま使わない。新しい局面セットはそれぞれ異なるファイルとして作り、開始局面の重複、違法手順、終局済み、手番偏りを確認する。各局面のM/U/Vは参考実装の出力から逆算せず、設計の定義と盤面から独立に手計算し、手番・材料・対象の内訳とともに記録する。

### 予備比較用セット

専用のV典型局面を5件作る案とする。少なくとも次の役割を持たせる。

1. 支えのある角または飛車が歩など低価値の相手駒から狙われる状態。
2. 色を反転し、同種のV対象が後手側にある状態。
3. 対象駒種または低価値攻撃元を変えた別のV対象。
4. 支えが外れ、対象がUへ移ってVには重複しない対照。
5. Vが0の中立対照。

各開始局面は平手からの合法手順で作り、先後と候補順を一方へ固定しない。Vが非ゼロの局面では独立期待値、Uへ移る局面と中立局面ではV=0を明記する。初期局面のM差だけで結果が決まらないよう材料差も記録する。具体的な指し手列と期待値表は、実装計画の提示までに確定し、予備比較の結果を見て差し替えない。

### 確認比較用セット

予備セットと異なる6件を新たに作る案とする。開始時期を開局・駒組み後・駒交換後に分け、両方の手番を含める。特定のVパターンだけに偏らせず、対局を継続したときに生じる選択差を主判定の対象にする。確認セットの選定根拠・合法手順・M/U/Vの独立期待値を、条件とseed一覧を固定する前に提示する。確認用の組得点は6局面へ同じ重みで集計する。

現存する初期局面、C1、U用の3セット計15項目を既存ローダーとB段階のM/U/Vで読み取り確認したところ、全件とも開始時のV枚数差は0だった（セット間に重複局面を含む）。これらはV活性局面を確認する予備セットの代わりにならず、V特有の対照設計も目的にしていない。確認セットは「幅広さ」の根拠を明記して独立に選び、既存セットを自動流用しない。Vが開始時に0であることだけを理由に不適格とはせず、局面の広さと比較対局中の差を区別する。

## 二段階の比較条件案

以下の組数・手数上限は本人が設計・実装計画全体の承認により受け入れた初期条件案である。本人は2026-10-31に、予備・確認の両比較をworker 4で実施するよう明示した。比較CLIの接続・検証、局面・seed・条件・出力先の固定が済む前には実行しない。確認比較の手数上限は予備結果を見た後、実行前に最終固定する。初期案から条件を実質変更する場合は別途承認を得る。

### 予備比較

| 項目 | 提案 |
| --- | --- |
| 目的 | 方式接続、V典型局面での選択差、実行時間、上限未決着率を調べる。強さの判定には使わない |
| 局面 | 上記の専用5局面 |
| 規模 | 各10組、合計50組・100局 |
| 手数上限 | 一局1024手 |
| seed | `purpose=pilot` の新規seed一覧 |
| worker | `--workers 4`。実行時にもCLIの `--help` を確認し、利用できなければ代替worker数へ変えず停止して報告 |

予備と確認のseed一覧は別々に生成する。予備成績を確認成績へ加算しない。時間または未決着が確認比較の予算に合わない場合はそこで止め、確認比較の規模・上限を再設計して別途承認を待つ。

### 独立確認比較

| 項目 | 提案 |
| --- | --- |
| 目的 | 幅広い固定局面集合で、候補が対照より高い得点を得るか一つの主判定を行う |
| 局面 | 予備と異なる新規6局面。各局面を均等重み |
| 組数 | 6局面各340組、合計2040組・4080局 |
| 手数上限 | 一局1024手を初期案とし、予備を見た後、確認比較を開始する前に固定する |
| seed | `purpose=confirmation` の新規seed一覧。予備と独立 |
| worker | `--workers 4`。実行時にもCLIの `--help` を確認し、利用できなければ代替worker数へ変えず停止して報告 |

組ごとに同一局面の先後を交換した二局を行う。勝ち1、負け0、通常千日手0.5とする。上限未決着と勝者未裁定は勝敗へ読み替えず `[0,1]` に残す。確認比較は固定予定を完了し、途中の得点を見て停止・追加・位置差し替えをしない。

## 主判定と統計上の限界

候補側の二局平均を一組の得点とし、組を独立抽出単位とする。信頼水準95％、互角境界50％、計画上の効果目標55％、検出力80％を使う案とする。C1で採用されたHoeffdingの十分条件では、未決着がないとき `n > (sqrt(ln(40)) + sqrt(ln(5)))^2 / (2 * 0.05^2) = 2034.3037...` 組が必要となる。6局面を均等にするため、2040組（各340組）へ切り上げる。

未決着を含む組得点の上下限平均を `Lbar`、`Ubar` とし、`e = sqrt(ln(40)/(2*n))`、区間を `[max(0, Lbar-e), min(1, Ubar+e)]` とする。区間下端が0.5を超えれば改善を支持、上端が0.5未満なら悪化を支持、それ以外は判断不能とする。未決着があれば2040組で目標検出力を保証しない。局面別結果は記述値にとどめ、主判定を増やさない。

55％目標と組数は既存C1の設計を参考にしたアシスタント提案であり、本人の今回の選択ではない。設計承認時にこの統計条件を明示的に含める。固定した6局面、1手選択、重み、上限、実行環境に関する結果であり、一般棋力向上の証明ではない。

## 保存・実行・承認境界

- 局面セット、seed一覧、比較出力、分析JSONは新しい一意なパスに保存する。`data/comparison/runs/` 既存の未追跡データ、とくにC2保護4件は読書・上書き・移動・削除の対象にしない。
- 比較開始前に全出力先が存在しないことを確認する。再開する場合は同じ出力先・conditions・seed一覧だけを使う。
- 実験の実行前に、実装・検証を終えたコミットと実効重みをconditionsに固定し、seed一覧の局面SHA-256と予定を照合する。
- 予備・確認のworker 4実行は本人が2026-10-31に指示済みである。設計・実装計画の承認と実装検証を完了し、指示どおりの実験条件を固定した後に実行する。CLIの `--help` で4 workerが利用できることを再確認し、利用できなければ縮退せず停止して報告する。約一時間ごとに、実際の完了局数・組数・残数・故障・保存summaryを確認して報告する。条件を実質変更する場合は再度本人承認を得る。
- main統合・pushは別途本人承認を受ける。今回のhandoff文書コミットを統合・pushしない。元の `/Users/oki2a24/kaname-shogi` は既存変更と未追跡物を保護するため切替・上書き・clean/reset・削除をしない。

## 実装で必要になる範囲

設計承認後の実装計画で具体化する。現時点の想定は、比較用policyの追加、一手選択器への重み接続、比較CLI方式名と `policy_parameters` の保存・検証、方式別計時の維持、二種類の局面データ、関連する小規模pipelineと既存artifact回帰である。通常CLI・USIの方式一覧、評価関数本体、探索深さ、終局判定、比較共通の統計方式は変更しない。
