# 第38回：弱い自動指し手のための合法手列挙と一手選択の設計仕様

作成日：2026-09-25
設計合意日：2026-09-25
実装承認日：2026-09-25

## 目的

局面で指せる全ての合法手を、局面を変更しない変更不可のデータ列として得られるようにする。その一覧から、評価や探索を使わない弱い自動指し手が一様ランダムに一手を選べるようにする。

この回は、人間とコンピュータがCLIで対局する機能ではない。後続テーマが同じ公開操作を利用できる、最小のPython APIを整える。

## 一次資料と今回の範囲

日本将棋連盟の対局規則第5条は、自分の駒を規定どおりに動かすこと、相手駒を取って持ち駒にすること、空きマスへ持ち駒を打つこと、敵陣に関わる移動で成ることを定める。第10条は二歩、打ち歩詰め、王手放置、行き所のない駒などを反則とする。これらは既存の `apply_move` と `apply_drop` が検証済みの規則であり、今回の列挙はその操作を複製局面へ試行して再利用する。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[日本将棋連盟「反則について」](https://www.shogi.or.jp/knowledge/shogi/05.php)

## 確認問題で合意した範囲

1. 合法手は、弱い自動指し手などの呼び出し側へ渡すPythonのデータとして表す。USI・JSON・XMLなどの外部文字列形式は今回扱わない。
2. 棋譜専用の `RecordedMove` / `RecordedDrop` を再利用せず、用途に中立な一手の型を新設する。棋譜、合法手列挙、将来のUSI変換が同じ一手の意味を共有しつつ、互いの実装詳細へ依存しないようにする。
3. 盤上移動と駒打ちは異なる不変データ型で表し、一つの合法手一覧に混在させる。局面を表す `Position` は一手とは別の値であり、今回の一手選択器は評価を行わないため受け取らない。
4. 合法手一覧の順序は固定する。盤上移動を先、駒打ちを後に置く。マスの走査は一一、一二、…、一九、二一、…、九九（内部値では `Square(1, 1)` から `Square(9, 9)`）とする。盤上移動では既存の駒ごとの候補順で、不成を成りより先に置く。駒打ちの駒種は飛・角・金・銀・桂・香・歩、各打ち先は同じマス順とする。
5. 弱い自動指し手は、呼び出し側から渡された `random.Random` により、合法手一覧から一様ランダムに一手を選ぶ。乱数生成器を内部生成せず、テストでは固定種で結果を再現できるようにする。
6. 一手選択器は、受け取った一覧を再度合法性検証しない。前提条件は `legal_moves(position)` が返した一覧を渡すこととし、空なら `None`、空でなければ一覧内の一手を返す。詰み・投了・勝敗は判定しない。
7. 既存の公開操作 `has_legal_move(position)` は、合法手一覧が空でないかで判定する。合法手の有無と一覧に異なる規則が生じないようにする。打ち歩詰め検証に必要な再帰回避の内部処理は保持する。
8. CLIは変更しない。人間対コンピュータの手番、表示、終了処理は別テーマで扱う。

## 比較した方式と選択

### 選択：中立なPythonの一手データを独立モジュールに置く

`kaname_shogi/move.py` に、局面を変更しない一手の値を置く。これは「指す」操作ではなく、指し手の内容を保持するデータである。`move` は英語で動詞にもなるが、将棋・チェスの文脈では名詞として「指し手」を表す。局面へ実際に適用する操作は既存の `apply_move` / `apply_drop` のままとする。

### 見送る方式

- `RecordedMove` / `RecordedDrop` を合法手一覧にも使う方式は、棋譜という用途へ列挙器を結び付ける。現状の棋譜モジュールは `movegen.py` を利用しているため、逆向きの依存は循環を招きやすい。
- JSON・XML・固定長データ・USI文字列を今回の公開表現にする方式は、局面規則と外部通信・保存形式を混在させる。変換は将来の専用テーマで扱う。
- 盤上移動一覧と駒打ち一覧を別々に返す方式は、選択器側が二つの一覧の優先順位を持つ必要があり、意図しない偏りを作る。
- 選択器へ未使用の `Position` を渡す方式は、将来の評価を先取りする。今回のランダム選択に必要な一覧と乱数生成器だけを受け取る。
- 列挙器または選択器の内部で乱数を生成する方式は、テストの再現性を損なう。
- 合法手なしを勝敗や投了として返す方式は、選択器へ終局判定の責務を混在させる。
- 今回CLIへ自動指し手を組み込む方式は、人間とコンピュータの手番、表示、終局処理まで対象が広がるため見送る。

## 公開インターフェース

### `kaname_shogi.move`

- `BoardMove` は出発マス、到着マス、成り指定を持つ盤上移動の不変データである。
- `DropMove` は玉以外の基本駒種と打ち先を持つ駒打ちの不変データである。
- `Move` は `BoardMove` または `DropMove` を表す共通の型注釈である。

型は `Square` や `BasicPieceType` を参照するが、盤面、手番、持ち駒を変更しない。Python 3.9との互換性を保ち、具体的な型注釈の記法は実装計画で確定する。

### `legal_moves(position)`

`kaname_shogi.movegen` に置く、合法手を複数求める公開操作とする。

- 引数：盤面、手番、双方の持ち駒を持つ `Position`
- 戻り値：固定順の `tuple[Move, ...]`。合法手がなければ空タプル
- 副作用：渡された局面の盤面・手番・持ち駒を変更しない
- 検証：手番側の盤上移動（不成・成り）と玉以外の持ち駒打ちを、既存の `apply_move` / `apply_drop` に複製局面で試行する

`has_legal_move(position)` は `bool(legal_moves(position))` とする。内部では、打ち歩詰めの確認中だけ再帰を止める既存の方針を保ち、公開の一覧と詰み判定で同じ合法性規則を使う。

### `choose_weak_move(moves, rng)`

弱い一手を選ぶ公開操作を `kaname_shogi.movegen` に置く。

- 引数：`legal_moves` が返した合法手のタプル、呼び出し側が用意した `random.Random`
- 戻り値：一覧が空でなければ、その要素の一つ。空なら `None`
- 副作用：局面・指し手データを変更しない。渡された乱数生成器の状態だけを、抽選のために進める
- 前提条件：`moves` は同じ局面から `legal_moves` で得た一覧である。選択器は各要素を再検証しない

この操作は合法手なしを終局、負け、投了とは解釈しない。終局判定は既存の `is_checkmate` / `is_game_over` と、将来の対局進行層が担う。

## 列挙順と選択

列挙順は評価ではない。固定順はテスト再現性と一覧の安定した表示のために定める。弱い選択器は一覧順ではなく、注入された乱数生成器で一様ランダムに選ぶため、列挙順が直接の選択優先度にはならない。

一手の選択は、局面評価、探索、駒得、王手、成りの優先度を持たない。これらは弱い相手として最小限の範囲を超えるため、将来のテーマで設計する。

## CLIとの関係

既存の `run_game`、入力解析、盤面表示、投了、詰み、EOF、Ctrl-Cの振る舞いは変更しない。今回追加する操作はPythonコードから利用できるだけであり、CLIが自動で合法手を表示したり、コンピュータの手を指したりしない。

## 将来への申し送り

- USIは既存の将棋GUIとエンジン間で用いられるテキスト通信規約であり、盤上移動・駒打ち・投了などに外部表現を持つ。将来のUSI対応では、今回の `Move` と `Position` をUSI/SFEN文字列へ変換する専用層を設計する。今回USI通信、SFEN、標準入出力プロトコルは実装しない。
- USIでの `bestmove resign` / `bestmove win` のような終局に関わる外部表現は、今回の `None` と同一視しない。将来、終局理由を判定する対局進行層が外部表現を選ぶ。
- 人間対コンピュータCLIは、手番の担当、乱数生成器の生成・寿命、コンピュータ手の表示、終局時の停止を決めてから実装する。
- 評価・探索・定跡・強さ調整・乱数以外の選択規則は未実装である。将来追加する選択器が局面を読む必要がある場合は、その時点で別の公開インターフェースを設計する。
- `GameRecord` の記録値と中立な `Move` の相互変換、JSON保存形式への反映は今回の対象外である。既存の保存形式と読込互換性を変えない。

参考：[USIの構文実装例](https://github.com/tofutofu/haitaka-usi/blob/main/src/usi.pest)

## 確認方法

TDDでは少なくとも次を振る舞いごとに確認する。

1. `BoardMove` / `DropMove` が変更不可の一手データとして必要な値を保持する。
2. `legal_moves` が盤上移動、成り、不成、駒打ちを含む全合法手を返し、元の局面を変更しない。
3. 二歩、行き所のない駒、王手放置、打ち歩詰めなど既存規則で拒否される手を一覧へ入れない。
4. 合法手がない局面では空タプルを返し、`has_legal_move` も偽になる。
5. 列挙順が、合意した盤上移動・駒打ち・マス・成り・駒種の順に安定する。
6. `choose_weak_move` が固定種の `random.Random` で再現可能な一手を返し、空一覧では `None` を返す。
7. 選択器が渡された一覧の要素を返し、局面を変更しない。
8. CLIの既存テストを通し、今回CLIの挙動を変えないことを確認する。

実装後は対象テスト、全テスト、CLIスモーク、`git diff --check` を実行する。Refactorの要否確認後に独立レビューを実施し、Critical・Important・Minorの結論と対応を学習記録へ残す。
