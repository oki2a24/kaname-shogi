## 導出の根拠

会話の合意だけでなく、usi_engine.pyの入力・方針寿命・出力経路、movegen.pyの合法生成・打ち歩詰め・応手評価経路、既存テスト、USI仕様と公開エンジンを照合した。個人観察test-driven-development.mdと[検出力点検](../knowledge/test-coverage-review.md)に従い、契約・独立期待値・想定誤り・既存検査の補完・未検証事項を分けた。網羅性を証明したという結論ではない。

## 拡充した確認範囲（いずれも今後実装承認後）

| 対象契約 | 代表ケース・期待値の独立した決め方 | 検出したい誤り・既存検査との関係 |
| --- | --- | --- |
| 自分側の時計と配分 | 先後を入替え、正/0、秒読み有無、余裕以上/未満、目標≤上限を手計算 | 相手側時計、秒/ミリ秒混同、負予算。既存合法応答検査では不足 |
| 時刻と境界 | 読取り後の解析・複製・起動時間を含め、目標/上限の直前・一致・直後を制御時刻で確認 | 計時開始遅れ、境界比較誤り。実時間sleepに依存しない |
| 入力・設定 | 必須/重複/未知/欠落/型/非有限/0/負/読込不能、時計なし、加算0、未対応項目 | 不正入力を無制限扱い、bool数値扱い、代替既定値。期待値は契約表から独立に列挙 |
| 根の合法生成 | 盤上手/成り/駒打ちの途中、最初の合法手前後、全調査で手なし | 中断の空を手なしと誤認。既存合法性検査で通常完了側を補完 |
| 打ち歩詰め内部 | 内側の防御手生成が中断/完了、合法/違法確定を区別 | 未確定歩打ちを予備手に採用。公開apply_dropの既存契約も維持 |
| 候補・応手・詰み評価 | 候補開始前、応手途中、評価完了前後、下位中断、手なし確定 | 途中の点を完了点扱い、途中結果の真偽使用。既存二手深さ・評価向き検査だけでは不足 |
| 最終選択 | 完了候補0/1/同点複数、未完了候補の仮点が最高、Random全完了/中断 | 予備手への不必要な退行、未評価手選択、二重抽選。既存同点・候補限定検査を補完 |
| 通常停止の例外 | stop/上限時に予備手あり/なし、下位探索では保留しない | 不合法応答、無条件継続。期限超過リスクを解消したとはしない |
| 終了・エラー停止 | quit/EOF/gameover/入力エラーを予備手未確保中にも投入 | 通常停止例外を誤適用、抑制後のbestmove、回収漏れ。gameover後の受付継続も確認 |
| 競合と一回応答 | 自然完了/stop/期限/抑制入力の両順序、停止反復、送信失敗 | 二重応答、送信済みの取消扱い、失敗を完了扱い。明示的な同期点で順序を作る |
| 入力受付と寿命 | 探索中isready/usi/setoption/未知入力、position/go/usinewgame、次のgo/次局 | 入力停止、局面競合、古い停止/手/方針の流用。既存方針寿命・乱数継続検査を補完 |
| 保存と互換性 | 全盤面・持駒・手番の保存、分岐独立、停止なし公開API、三方針 | 中断時だけの局面破壊、公開戻り値変更。既存保存・分岐検査を再利用可能 |
| 実プロセス | 探索開始を確認後stop、readyok、改行/flush、応答回数、終了コード、有限待ちと回収 | 注入時計だけでは検出できない標準入力・出力・終了連携不良 |
| 担当の故障 | 探索例外、起動失敗、出力失敗、入力待ち中の故障 | 入力待ちのまま残留、joinと出力ロックの相互待ち。監査時は未決定。その後の採用契約と期待値は末尾表を参照 |

既存ScriptedInputは列終了で直ちにEOFになる。非同期化後はgo直後のEOFが応答抑制を意味するため、旧テストをそのまま使って通常応答を確認できるとは限らない。新しい入出力テストはイベント等で意図する順序を作り、実時間待ちだけで探索中だと推測しない。テスト全体の有限待ちは検査プロセスの回収用で、実エンジンの期限保証ではない。

## 点検時に発見した設計残件（その後の採用は下記参照）

1. 探索担当の故障を、標準入力待ち中の入力担当へどう通知して終了へ進ませるか。「通知する」だけでは入力待ちを解除できない。入力担当を現スレッドにする既採用案との整合を比較する必要がある。
2. join中に探索担当が必要とする出力ロックを保持しないこと、送信完了とスレッド回収・次go受付の順序、出力自体が詰まる場合の限界を具体化する必要がある。実装手順への丸投げではなく、外から見える寿命・終了契約をここで確認する。
3. 目標到達時に根の合法手一覧が未完成の場合、生成をどこまで続けるか。合意済みの「新候補評価を始めない」「上限で中断」「予備手未確保例外」との対応を明示する必要がある。

数値計算の巨大値・有限値同士の乗算での非有限化、idle stopの扱いも具体化時の点検項目。実装方式や新しい制限値は本点検で勝手に決めていない。

## 結論と限界

以前の確認案は主要分類を含むが、担当故障と入力待ち、回収順序、根生成と目標の対応が薄かった。追加しても全局面・全競合・全OSの網羅性を保証しない。まず上の設計残件を一つずつ判断し、確認表の期待値を確定する。その後に文書全体を整理・独立レビュー・本人へ提示する。40手上限と長考原因の仮説、実測安全性は今回検証していない。

## 監査後の判断と確認表の具体化

上の3点は監査時の未決定事項。その後、本人は次を採用した。

| 残件 | 採用した契約 | 補強する確認ケースと期待値 |
| --- | --- | --- |
| 故障時の入力待ち | 主担当は命令/故障通知を受け、別の入力読取り担当は内部終了通知で待機を解除して回収。具体方式はmacOS対象 | GUIが無言、改行前の部分入力、探索故障/読取り故障の通知、終了後の担当と通信路の回収。次入力なしでも終了へ進む。go読取りから受渡し待ちも計時 |
| 回収順序 | 送信完了と担当終了を区別、共通ロック外で終了待ち、前担当回収前に次探索を開始しない | 送信前の入力確定は既契約のエラー、送信後かつ担当終了前の正常次命令は回収後に処理。探索担当が同じロックを必要とする順序でも相互待ちしない |
| 根生成の目標到達 | 予備手ありは生成中断、未確保は通常停止例外。評価中候補と下位応手生成は別扱い | 予備手確保前/後、目標直前/一致/直後、一覧完了との境界、打ち歩詰め内部未完了、抑制付き停止。予備手ありで目標停止なら予備手、未確保なら合法確定/手なしまで |

部分入力や複数行同時到着、EOF直前の末尾行は、現行の行読取り契約との照合対象。移植時に見直す入力待機・読取り・回収箇所を設計文書と将来の該当コードに明示する。巨大値計算等の技術的表現は実装計画で具体化し、契約を変える制限を無断追加しない。追加ケースは未実施。2026-10-12、追加合意と確認表を含む設計全体を本人が承認。実装・安全性検証の完了を意味しない。
