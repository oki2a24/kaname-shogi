## 比較単位と計算条件

一回の起動は基準方式と候補方式の一対を扱う。現在の五方式を同一ソース内から選ぶ。将来の評価方式を選べるようにする変更は、各評価項目テーマで設計・実装・接続する。初版で未実装の候補方式や評価項目の全組合せを自動生成しない。

| コマンドの識別子 | 日本語の方式・固定の計算条件 |
| --- | --- |
| `random` | 一様ランダム。評価探索なし |
| `material` | 一手駒得。深さ1 |
| `two-ply-material` | 二手駒得。深さ2 |
| `full-width-4` | 全幅探索。深さ1から4まで反復し最終結果を使用 |
| `alpha-beta-4` | αβ探索。深さ1から4まで反復し最終結果を使用 |

既存 `game_search.choose_move`（方式に従い一手を選ぶ操作）を使う。五方式の深さ・評価・同点選択を変更しない。任意深さ指定は設けない。基準方式と候補方式が同じ指定は入力不正とする。

比較専用CLIは対局時計を作らず、探索時間予算で深さを切り替えない。従って時間切れ負けはこの実行方式では発生しない。通常CLI・USIの時間切れ仕様を変更するものではない。全幅4手など一手の計算が長い場合がある。手数上限は完了した手の数の上限であり、応答時間の上限ではない。Ctrl-Cで利用者が中断できるようにする。ハードな実時間制限・プロセス強制停止は保証しない。

評価項目の効果を見る主比較では、項目以外の深さ・既存項目・重みをそろえる。異なる深さ同士も操作上は比較できるが、その結果を評価項目だけの効果と説明しない。機器・Python・ソース・計算条件を記録する。同時に別比較を走らせず一対局ずつ実行する運用を案内する。

## コマンドと入力

入口案は `python3 -m kaname_shogi.compare_games`。通常の対局メニューへ反復対局の設定を追加しない。以下は将来実装する書式の例で、現在実行できるコマンドではない。

```sh
python3 -m kaname_shogi.compare_games \
  --baseline material --candidate random \
  --positions data/comparison/start-positions-v1.json \
  --pairs-per-position 1 --seed 20261021 \
  --max-plies 256 --output-dir comparison-results/trial-001
```

この例は道具の小さな試行用で、8局や256手を棋力判定に十分な数とする根拠ではない。特定の回数・手数上限を隠れた既定値にしない。

| 引数 | 契約 |
| --- | --- |
| `--baseline` / `--candidate` | 上表の識別子を一つずつ必須指定 |
| `--positions` | UTF-8 JSON局面セットのパスを必須指定 |
| `--pairs-per-position` | 各局面で繰り返す組数K。1以上の整数、必須 |
| `--seed` | 0以上の整数、必須。実効種と割当て方式も結果へ記録 |
| `--max-plies` | 開始局面以降に適用する手数の上限。1以上の整数、必須。先後各一手で2手 |
| `--output-dir` | 新規出力ディレクトリのパス、必須。親は既存、出力先が存在する場合は拒否 |

全引数・全局面セットを検証してから出力先を作成し、対局を開始する。未知の引数、未知キー、欠落キー、重複JSONキー、形式違い、空の局面列、重複ID、同一局面の重複は拒否する。同一局面は盤面・双方の持ち駒・手番で判定し、準備手順長やSFEN手数・局面IDの違いを別局面とは扱わない。整数JSON欄へ真偽値を受け付けない。比較条件を既定値で補って入力ミスを隠さない。

## 開始局面の入力と動作確認用の具体案

局面セットは平手初期局面からの合法な準備手順を保存する。汎用SFEN入力の合法性を新規実装する代わりに、既存の一手解析・合法手適用で開始局面を生成する。SFENだけでは玉の有無・二歩・到達可能性まで検証しない既存仕様を踏まえた選択である。生成した開始SFENも結果へ保存し、作成理由と手順を追えるようにする。

```json
{
  "format": "kaname-shogi-comparison-positions-v1",
  "id": "starter-v1",
  "positions": [
    {"id": "initial", "setup_moves": [], "rationale": "平手初期局面"},
    {"id": "open-bishops", "setup_moves": ["7g7f", "3c3d", "2g2f", "8c8d"], "rationale": "双方の角道と飛車先の歩を動かした序盤"},
    {"id": "closed-bishop", "setup_moves": ["7g7f", "8c8d", "6g6f"], "rationale": "先手が角道を閉じた、後手番の序盤"},
    {"id": "pawn-exchanges", "setup_moves": ["7g7f", "3c3d", "2g2f", "8c8d", "2f2e", "8d8e", "2e2d", "2c2d", "2h2d", "8e8f", "8g8f", "8b8f"], "rationale": "双方の飛車先で歩を交換し、双方に持ち歩がある局面"}
  ]
}
```

IDは空でないASCII英数字・ハイフン・アンダースコアに限定する。`rationale` は空でない文字列。`setup_moves` はUSI一手文字列の配列であり、空配列は平手初期局面。各手を既存 `parse_usi_move`（一手表記を指し手データへ変換する操作）と `GameRecord`（対局記録データ）へ渡す。準備手順の途中で終局判定が成立する場合、比較開始時に合法手がない場合は入力不正。千日手部品確定後、準備中の千日手・連続王手もこの終局確認へ含める。

比較の開始位置は準備手順の最終局面。千日手判定用の履歴はそこから新しく開始し、開始局面を1回と数える。準備手順は到達経路の記録であり、比較対局の履歴へ持ち込まない。準備手順の手数を `max-plies`・対局の消費時間・成功手数へ加算しない。入力由来のSFEN手数相当値と、比較開始以後の成功手数を別欄で記録する。

この4局面の用途はP2の道具の動作確認であり、棋力評価用セットとして採用したものではない。4局面はアシスタントが作成した小さな初期セット案で、定跡・棋力ベンチマークや代表的な実戦集合と主張しない。既存の合法手適用で全準備手順が通り、開始時の両玉が王手でないこと、合法手数30・40・31・52を今回確認した。最後の例は手順を追うと双方の持ち歩が2枚ずつで、取った歩の枚数にも差がない。これらは互角の保証ではない。序盤寄りで中終盤・成駒・入玉を十分に覆わない。実際の評価項目Cでは、結果を見る前に局面セットと理由を確定し、適用範囲を記す。候補方式の評価は各手で働くので、比較対象は開始局面同士の優劣ではなく、同じ開始局面における方式の違いである。ただし後の悪手が勝敗を支配して序盤の改善が最終結果に表れにくい可能性もあり、今回のエンジンでの大きさは未測定。評価項目に対する独立期待値を持つ小局面検査と、対局全体での成績観察を併用する。Cの局面群はこの4局面で固定せず、中終盤も含める必要性と選定の偏りを評価項目の目的に照らして設計する。

## 対局予定・先後・乱数

局面配列の順、各局面で反復番号0からK−1の順に処理する。局面番号p、反復番号rに対し組番号qを `p*K+r` とする。一組で同じ盤面・持ち駒・手番から二局実行し、基準方式と候補方式の先手・後手担当だけを入れ替える。盤面や駒の所属を反転させない。後手番の開始局面でも同じ規則を使う。

偶数qの第一局は基準先手、奇数qの第一局は候補先手とし、第二局は必ず担当を逆転する。方式が先手を持つ回数と、各組の第一局を担当する順をそろえる。計画局数は `2 * 局面数 * K`。

主種Sに対し、基準方式用の種は `S+2*q`、候補方式用は `S+2*q+1`。各局の開始時、方式ごとに別々の `random.Random`（乱数生成器データ）を作り直す。同じ組の第二局でも方式に同じ種を割り当てる。手番・対局順や相手の乱数消費によって一方の乱数列がずれないようにする。

これは先後を入れ替える比較用の割当てで、二局の独立性を保証しない。別の組の異なる種も統計的独立性の証明にはならない。決定的な方式同士では種を変えても棋譜が同一になる可能性を画面と結果へ明記する。棋譜の重複は削除せず、予定どおり記録し、局数を独立標本数と呼ばない。同一ソース・Python版・局面順・設定で手順の再現を目指し、経過時間の一致は期待しない。

## 一局の進行・終了理由

開始局面と成功手の履歴は各局で独立に用意する。探索で調べただけの局面は千日手履歴へ追加しない。千日手部品には比較開始局面と成功した実着手だけを渡す。

開始時と各成功手後に、(1) 千日手・連続王手の終局判定、(2) 次の手番の合法手なし、(3) 手数上限、の順で確認する。上限ちょうどの成功手で終局した場合は、実際の終局を優先する。千日手の厳密な履歴契約は専用テーマの承認済み部品へ合わせる。

| 結果識別子 | 勝者 | 比較上の扱い |
| --- | --- | --- |
| `checkmate` | 詰まされた手番の相手 | 通常の勝敗 |
| `no_legal_move` | 手番側の相手 | 王手なしの合法手なし。現在CLIの手なしを投了と扱う方針に合わせた勝敗で、理由を詰みと区別 |
| `perpetual_check_loss` | 王手を続けた側の相手 | 勝敗へ算入し、連続王手の負け件数も内訳で表示 |
| `repetition` | なし | 通常の千日手。指し直しなし、勝敗とは別件数 |
| `ply_limit` | なし | 手数上限による未決着 |
| `interrupted` | なし | 利用者のCtrl-C。対局と残りバッチを中断 |
| `error` | なし | 探索・適用等の処理失敗。バッチを停止 |

入玉・持将棋を独自評価で裁定しない。時間切れは時計を持たないため結果に作らない。探索へ非空の合法手集合を渡したのに手なしを返した場合、返った手が集合外の場合、元局面の破壊を検知した場合は故障として扱い、勝者を認定しない。

手の計算・適用・千日手履歴・計時結果は、次の完全な状態を準備した後に成功手として確定する。Ctrl-Cや故障時には確定済みの一貫した履歴だけを保存する。失敗中の手を成功手として足さない。再現できる棋譜と成功手数・計時配列の対応を確認する。

故障後は自動で次局へ進まない。既に終わった局を保持し、実行中の局の故障情報と未実行局数を記録する。Ctrl-Cも同様に一局の中断記録を残し、残りを開始しない。片側の局だけ終わった組は「組の実行未完了」とし、完了組へ水増ししない。対局開始前のCtrl-Cは開始局数へ加えない。二局の間のCtrl-Cでは架空の中断局を作らず、バッチの中断状態と未実行予定を記録する。

## 計時・結果記録・集計

一手の計算時間は単調時計 `time.monotonic_ns` で、当該局面の全合法手生成の直前から一手選択操作の返却までを測る。方式の内部にある追加合法手生成・反復深化・採点を含む。適用・終局判定・棋譜保存・画面表示は含めない。全方式で同じ境界とする。開始・手の確定後に行う終局確認の処理は一手選択時間とは別である。手なし終了の確認にかかった時間を成功手の計時へ混ぜない。

各成功手に手番・方式・指し手・経過nsを保存する。中断・故障した計算の経過nsは別の任意欄 `unfinished_calculation` に記録し、成功手平均へ含めない。時刻の逆行は故障。バッチ全体の経過nsも別に保存し、一手計時の合計と等しいとは扱わない。

初版は画面用の短い日本語表示と、UTF-8 JSONファイルを出す。JSONは再解析の正本とする。各局終了時に保存し、バッチ終了まで全局分の保存を待たない。

| 出力 | 内容 |
| --- | --- |
| `conditions.json` | 形式v1、入力条件、局面セット内容とSHA-256、生成済み開始SFEN、全予定の局面ID・組番号・担当・種、計時境界、時計なし、千日手集計方針、取得時のGit HEADと変更ありフラグ、Python・OS・機器情報、エンジンソースのSHA-256 |
| `game-000001.json` 等 | 実行を開始した各局に一件。条件のSHA-256、予定ID、基準/候補の先後、開始SFENと開始由来手数、比較開始以後の成功手数、終了理由、勝者の先後と基準/候補、既存 `GameRecord.to_payload()` のv1棋譜データ、成功手ごとの計時、任意の未完了計算と故障情報 |
| `summary.json` | 状態 `running/completed/interrupted/failed`、計画/開始/プロトコル上終了/未実行の局数、二局とも終了した組数と片局のみの組数、基準勝ち・候補勝ち・千日手・手数上限・中断・故障件数、方式別成功手数と計算時間の合計・平均・最大、全体経過ns、統計判定未実施 |

条件のエンジンソースSHA-256は `kaname_shogi` 以下の全 `.py` の相対パスと内容をパス順で連結した定義済みバイト列から計算する。具体的な区切りは実装計画で固定する。Git情報が得られなければnullと診断を残し、ソース指紋を用いる。変更ありの実行はHEADだけで内容を復元できないことを明記し、未コミットのコードそのものを保存したとは主張しない。機器情報はOS・CPUアーキテクチャ・取得可能なCPU名・論理CPU数を記録し、取得不能はnull。入力ファイルは内容の複写を記録するため、元ファイルが変わっても条件を確認できる。

`completed` は計画全局が `checkmate/no_legal_move/perpetual_check_loss/repetition/ply_limit` のいずれかで終了し、必要なファイルを保存できた状態。棋力が判定できたことを意味しない。全ゲームの排他的な終了理由件数の和は開始局数に一致する。勝敗内訳の連続王手件数を二重加算しない。未実行は開始局数へ含めない。平均時間は合計/成功手数で計算し、成功手0はnullとする。方式名が同じ指定を拒否するので二者の集計先は一意。

勝率・千日手の0.5点化・引き分け数は初版で表示しない。特に決着局だけを抜き出した勝率を全対局の成績のように示さない。局面別・先後別の件数も表示し、全体件数へ相互照合できるようにする。結果の評価は将来のCテーマで、観測条件・故障・未決着の割合も含めて本人が行う。初期試行の結果から改善・同等・悪化を自動認定しない。

各JSONファイルは同じ出力先内の一時ファイルへ書いてから置換する。局ファイルを先に確定し、集計は保存済み局ファイルの内容に基づいて更新する。複数ファイル全体の同時更新や、強制終了・OS障害時の完全保存は保証しない。保存失敗では成功と表示せず終了1にし、既存の確定ファイルを残す。summaryが古い可能性をstderrへ伝える。通常のCtrl-C処理では確定棋譜を保存して終了130とするが、保存自体が失敗した場合は終了1を優先する。

画面には予定局数、各局の担当・局面・結果・手数、最後に上記件数と方式別処理時間を表示する。盤面を毎手全面表示しない。起動時に「固定深さ・対局時計なし」「同じ棋譜の反復は独立な証拠の増加とは限らない」、終了時に「統計判定未実施」を表示する。

| プロセス終了コード | 意味 |
| --- | --- |
| 0 | 予定した全局の実行・保存完了。千日手・手数上限を含む |
| 1 | 実行中の故障・保存失敗。保存可能な故障情報を残し診断はstderr |
| 2 | 入力不正・入力読込失敗・出力先を新規作成できない。対局開始前に終了 |
| 130 | 利用者のCtrl-C。保存可能な中断記録を保存 |

## 実装の責務と依存境界

| 対象案 | 責務 |
| --- | --- |
| `kaname_shogi/comparison.py` | 実験条件・局結果のデータ、予定生成、独立した一局進行と集計。端末入力やファイルI/Oを含めない |
| `kaname_shogi/comparison_io.py` | 局面セットJSONの検証・準備手順再生、結果JSON変換・保存、条件の機器/ソース情報収集 |
| `kaname_shogi/compare_games.py` | 引数検査、各部品接続、画面表示、例外・中断と終了コード |
| `data/comparison/start-positions-v1.json` | 上記の開始局面案4件と作成理由。P2で追加する |
| 千日手テーマの承認済み部品 | 局面の反復・連続王手の判定。比較専用規則として再実装しない |

`GameRecord` は棋譜データ、`MoveSelectionPolicy` は方式データ、`game_search.choose_move` は一手選択操作、`parse_usi_move` は解析操作、`format_sfen` は局面を書き出す操作である。公開する新しい型名・関数シグネチャとJSONの全キー・厳密な構造は具体計画で固定し、日本語docstringでデータと操作を説明する。上記の利用者に見える意味・必須記録内容は計画で落とさない。

千日手部品へ要求する契約は、比較開始からの実局面履歴を受け取り、「継続」「通常千日手」「連続王手で負ける側」を区別できること。千日手の公開APIの名前・保持方法・通常CLI/USIへの接続範囲は専用テーマで決める。P2計画作成時に、その実装と本設計を照合し、仕様変更が必要なら説明して承認を受ける。

## 確認方法と検出範囲の設計

ここに列挙するのは将来の確認方法であり、未実行のテスト結果ではない。[検出力点検](../knowledge/test-coverage-review.md)と個人観測メモの契約・独立期待値・代表誤りの方針を適用する。

| 契約 | 小さな代表ケース・独立期待値 | 検出したい誤り |
| --- | --- | --- |
| 全入力を開始前に検証 | 最後の局面だけ不合法、重複ID/局面、空列、未知キー、整数境界 | 先頭だけ検証、失敗前に対局や出力作成を開始 |
| 二局の担当と種 | 局面2件×K2で8局、q0/q1の順序と数式を手書き照合 | 方式未交換、盤面反転、先後へ種を固定、生成器の相互共有 |
| 状態の独立 | 前局の履歴/生成器を変更しても次局の開始状態は同じ | 局面・持ち駒・乱数の使い回し、準備履歴混入 |
| 終局理由と境界 | 各理由、連続王手側の先後反転、上限1と上限ちょうどの詰み/反復 | 千日手を勝敗/打ち切りへ変換、最後の終局より上限を優先 |
| 異常な手は故障 | 非空候補にNone、不合法手、探索例外、適用中の中断 | 投了/引き分けへ化ける、未確定手の履歴混入、後続局の実行 |
| 計時範囲 | 手書きの偽時計と処理順で、成功手の差分・未完了計算・0手を照合 | 表示/I/O混入、時計逆行無視、中断時間を成功手平均へ加算 |
| 記録と集計 | 手書きの複数結果を保存し件数合計/勝者/平均/未実行を照合 | 勝者視点逆転、故障を勝敗へ加算、未実行/片組の水増し |
| ファイル境界 | 保存先既存、局保存失敗、summary保存失敗、Ctrl-C | 上書き、保存前に成功表示、以前の局の消失、終了コード違い |
| 実接続 | 初期セットの合法再生、既存五方式の小局面接続、専用入口のプロセス実行 | mock接続だけ通り実際には未接続、CLI引数と結果の不一致 |

棋譜再適用・SFEN解析・駒の合法性・探索そのものの既存検証は再利用する。ただし比較固有の担当・種・終局優先順・記録/集計は新しく確認する。代表的な誤りを隔離コピーへ入れ、意図したアサーションの失敗と復元後成功を確かめる。読み込みエラーを検出成功としない。上記は有限の代表例で、全局面・全OS・実応答期限・棋力・統計的な独立性は未検証のまま残る。

## 出典と判断理由

- [日本将棋連盟の対局規則](https://www.shogi.or.jp/match/taikyoku_rules/)：通常千日手の指し直しと連続王手の負け。比較で指し直さず件数を報告する扱いは本人が承認した実験方針で、公式棋戦の規則そのものではない。
- [Stockfish公式Fishtest](https://github.com/official-stockfish/fishtest)、[SPRT実装](https://github.com/official-stockfish/fishtest/blob/master/server/fishtest/stats/sprt.py)：反復対局と不確かさの学習に参照。統計手法・境界値・チェスの引き分け規則を流用しない。
- [SFENの現行仕様](../knowledge/sfen-position-notation.md)、[先行設計の比較方針](2026-10-10-evaluation-next-stage-design.md)、[評価ロードマップ](../roadmap-non-material-position-evaluation.md)。

固定組数と自動判定なしは学習と小さな比較道具の範囲を保つ選択であり、必要対局数の統計的根拠を得たことにはならない。より広い局面群・棋力判定・性能評価を求めるときは、結果を見る前にその実験計画を具体化する。
