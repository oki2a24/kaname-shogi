# 第39回：人間対コンピュータのCLI進行の設計仕様

作成日：2026-09-26
設計合意日：2026-09-26
実装承認日：未承認

## 目的

既存のCLI対局を、人間が先手、弱いコンピュータが後手を担当する対局へ変更する。
人間の入力処理、合法手の列挙、一様ランダムな一手選択、`GameRecord` の記録を既存の責務のまま接続し、弱くても一局を進められるCLIにする。

今回、手合いを選ぶ引数・画面は作らない。ただし、手番ごとに人間かコンピュータかを判断する境界をCLI内部に置き、将来、人間対人間・人間対コンピュータ・コンピュータ対コンピュータへ拡張できる形にする。

## 一次資料と今回の範囲

日本将棋連盟の対局規則第2条は、先手番の対局者が対局を開始し、二人が交互に駒を動かして対局することを定める。同第6条は詰みまたは相手の投了による終局を定める。第10条には先後誤りと二手指しも反則として挙げられている。

本CLIでは、既存実装済みの詰み・投了・合法手だけを扱う。千日手、持将棋、入玉、時間、反則勝敗は範囲外である。EOF/Ctrl-Cは公式対局の終局規則ではなく、学習用CLI固有の勝敗にしない入力中断として維持する。

出典：[日本将棋連盟「対局規則」](https://www.shogi.or.jp/match/taikyoku_rules/)、[日本将棋連盟「王手と詰み」](https://www.shogi.or.jp/knowledge/shogi/04.php)

## 確認問題で合意した範囲

1. 人間は先手、コンピュータは後手を担当する。
2. `python3 -m kaname_shogi` は既定で人間対コンピュータ対局を開始する。今回、手合いを指定するコマンドライン引数は追加しない。
3. 乱数生成器は一局の開始時に一個だけ作り、その局の全コンピュータ手で順番に使う。テストでは呼び出し側から固定種の `random.Random` を渡し、選択結果を再現できるようにする。
4. 表示順は、開始局面、人間への入力案内、人間の成功手後の盤面、コンピュータが選んだ手、コンピュータの成功手後の盤面、次の人間への入力案内とする。
5. 各手番の前に既存の `is_game_over` で詰みを判定する。詰みなら勝者を表示して終了する。
6. コンピュータ手番で、詰みでないのに `legal_moves` が空なら、`choose_weak_move` の `None` を投了・勝敗と解釈しない。「コンピュータの合法手がありません。」を表示し、勝敗なしで終了する。
7. `resign` は人間（先手）の入力だけで扱う。コンピュータは投了せず、合法手があれば一手を指す。人間の投了は局面と指し手履歴を変更しない。
8. EOF/Ctrl-Cは人間入力待ちだけで扱い、「入力を終了しました。」を表示して勝敗なしで終了する。中断時点までの成功手は保持し、コンピュータは追加で指さない。
9. `GameRecord` は人間・コンピュータを区別する情報や終局理由を追加しない。成功した盤上移動・駒打ちだけを手番順に記録し、投了、詰み、EOF/Ctrl-C、合法手空一覧は記録しない。

## 比較した方式と選択

### 選択：担当手番の小さな境界をCLI内部に置く

`cli.py` に、現在の手番を人間が担当するかを判断する非公開の境界を置く。今回は先手だけを人間と判断する。`run_game` の対局ループはその判定に従い、人間なら既存の入力経路、コンピュータなら既存の合法手列挙・選択経路を実行する。

将来はこの境界を差し替えて担当を変えられる。今回、対局者クラス、選択画面、コマンドライン引数は先取りしない。

### 見送る方式

- 後手かどうかを対局ループ中で直接分岐する方式は、今回だけなら短いが、将来の担当変更で分岐が散らばる。
- 対局者オブジェクトや複数の戦略クラスを新設する方式は、将来の拡張性はあるが、今回の固定された二担当には抽象化が大きすぎる。
- `None` をコンピュータ投了または敗北と解釈する方式は、選択不能と投了・勝敗の責務を混同する。

## 進行と責務

`run_game` は開始局面から `GameRecord` を作り、開始盤面を表示する。以降は次の順で進める。

1. 現在局面が詰みなら勝者を表示して、記録を返す。
2. 人間担当なら、既存の入力解析、投了、エラー時の再入力、`GameRecord` 経由の合法手適用を行う。成功した手の後に盤面を表示する。
3. コンピュータ担当なら、現在局面の `legal_moves` を求める。空なら定めた勝敗なしのメッセージを表示して記録を返す。
4. 空でない一覧から `choose_weak_move` により一手を選ぶ。選択内容を表示し、`GameRecord` 経由で適用して盤面を表示する。
5. 次の手番へ戻る。

コンピュータが選ぶ `BoardMove` と `DropMove` は、局面を変えない一手のデータである。これを既存の `GameRecord.apply_move` または `GameRecord.apply_drop` へ変換して適用する小さな非公開操作を置く。盤面規則や履歴の追加をCLIで再実装しない。

## 乱数生成器

`run_game` は、テスト用に任意の `random.Random` を受け取れる形にする。指定がなければ、対局開始時に `random.Random()` を一個だけ生成する。乱数生成器は単一の数値ではなく、次の乱数を順に作る状態を持つデータであり、コンピュータの各手で状態が進む。

`choose_weak_move` は引き続き乱数生成器を内部生成せず、一覧から一手を選ぶだけに留める。通常CLIでの生成と、一手選択器の責務を分けることで、テストの再現性とAPIの単純さを両立する。

## 表示と終了

コンピュータの手は、盤上移動なら人間入力と同じ `move` 形式、駒打ちなら同じ `drop` 形式で表示する。表示は適用前に行い、どの一手を選んだかを盤面変化と対応させる。

人間の形式・合法性エラーは既存どおり理由を表示して同じ手番で再入力する。EOF/Ctrl-Cは人間入力の例外としてだけ捕捉する。コンピュータの手の選択や適用で起きる想定外の例外を、投了・勝敗・入力終了へ変換しない。

## `GameRecord` と保存形式

人間手とコンピュータ手はいずれも、成功したときだけ同じ既存の `RecordedMove` または `RecordedDrop` として記録する。担当者情報や終局理由を履歴やJSON保存形式に追加しない。そのため、既存の `GameRecord.save` / `load` の保存形式と読込互換性を変えない。

## 確認方法

実装承認後のTDDでは、少なくとも次を振る舞いごとに確認する。

1. 既定CLIが人間の先手入力の成功後に、後手のコンピュータ手を一手だけ指す。
2. 固定種の乱数生成器を渡すと、自動手と複数手にわたる選択結果を再現できる。
3. 開始・人間手後・コンピュータ手後の盤面と、自動手の表示順が合意どおりである。
4. 人間手・コンピュータ手の成功手が、手番順に同じ `GameRecord` へ残る。
5. 詰み、人間投了、EOF/Ctrl-C、詰みでない合法手空一覧で、それぞれ合意した時点に停止し、履歴へ終局イベントを混ぜない。
6. 既存の入力解析・人間の不正手再入力・棋譜保存読込・合法手列挙と一手選択のテストを維持する。

実装後は対象テスト、全テスト、CLIスモーク、`git diff --check` を実行する。Refactor要否を確認後、独立レビューでCritical・Important・Minorを判定し、Critical・Importantがあれば解消して再検証・再レビューする。
