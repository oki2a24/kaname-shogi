# ShogiHomeの時計期限による停止を観測する条件案

2026-10-13。**本人が本案と実施開始を承認し、具体的な設定変更・ログ採取・棋譜保全・再起動も一括承認した後、一局・一goを実施した。外部時計期限stopは未観測。対局設定の復帰は別途本人承認を得た一回の復帰対局で完了し、本人は結果を受け入れ、最後の理解確認も完了した。文書はmainの `ae5d558` に取り込み済み。** [実施・証拠・条件とのずれ・復帰操作・理解確認](../learning/shogihome-clock-deadline-conditions.md)。以下は当初承認された条件案の履歴であり、時計期限の追加試行を許可するものではない。[前テーマの結論と本人選定](../learning/shogihome-normal-stop-conditions.md)。条件作成段階には実機操作等を行わず、実施開始承認後に事前確認へ進んだ。

## 目的と二つの期限

対象は、ShogiHome側のエンジン時計が期限に達し、ShogiHomeがUSI `stop` を送り、合法な一応答が棋譜・盤面へ反映されて人間の手番になる経路。一回の観測に限る。画面操作による通常停止、対局中断、解析中断、人間側の時間切れ負けと区別する。

| 期限 | 起点と動作 | 今回の判定 |
| --- | --- | --- |
| エンジン内部の探索期限 | `go` の自分側時計とJSON設定から予算を計算し、自身で探索を切り上げる | 外部 `stop` がなければ対象未観測。返答だけで内部期限停止と自然な全探索完了を区別できない |
| ShogiHome側の時計期限 | v1.28.2はエンジン時間切れありOFFで `player.stop()` を呼び、対局を継続する | ログにShogiHome発の `stop` と、その後の合法応答があれば候補成立 |

公式v1.28.2の[時計期限処理](https://github.com/sunfish-shogi/shogihome/blob/v1.28.2/src/renderer/game/game.ts#L469)と[USI送信](https://github.com/sunfish-shogi/shogihome/blob/v1.28.2/src/renderer/players/usi.ts#L237)を根拠にする。内部の `player.stop()` という操作名だけで実通信を実測済みとはしない。実施時の版が違えばその版の経路を再照合する。

## 実施可能性と候補の選び方

現行JSONはallocation_turns=20、maximum_multiplier=2、byoyomi_target_ratio=0.75、response_margin_ms=2000。[時間予算](../knowledge/time-budget.md)、[探索停止](../knowledge/search-stop.md)。通常はエンジンの内部期限がホスト時計より早い。従って、短い時計にするだけでShogiHome発 `stop` を再現できるとは言えない。合法予備手の未確保や単一処理の遅延でホスト期限を越える可能性はあるが、それを発生保証や推奨手法にしない。

比較した方法は次のとおり。

1. **現行エンジン・現行JSONのまま、一回だけ条件付き観測する案（推薦候補）**：製品条件を保ち、先に応答したら未観測として終了する。外部stopを観測できる見込みは未確立。
2. JSONの余裕時間・倍率を変える案：内部期限とホスト期限の関係が変わる。設定変更の別テーマ・承認が必要なので今回採用しない。
3. 遅延を入れた試験エンジンを使う案：ホスト経路を制御できるが、現行エンジンとの一回の実通信ではなくなる。コード・テスト変更を伴う別テーマなので今回採用しない。

候補局面は既存 [KIF](../records/two-ply-usability-check-2026-10-11-retry.kif) の39手目 `☗１五歩` 後、人間先手・エンジン後手。以前の通常停止案と同じ局面を、実履歴がありエンジン番を明確に指定できる理由で今回も明示的に再選定する。過去の応答時間は時計設定や再現性の根拠にしない。KIFヘッダーの旧時計は使わず、今回合意する時計で開始できることを画面で確認する。合法手の有無は実施承認後、エンジン起動前に独立再生・合法手列挙で確認し、手なしなら開始しない。

候補方針はTwoPlyMaterial、Ponder OFF。前テーマ事前確認時はDifficulty Randomだったため、その状態を自動的に変更しない。設定変更が必要なら変更前値、TwoPlyMaterialへの変更と後の復元を具体的に提示して別承認を得る。前テーマの画面値は現在値と扱わない。

## 時計と有限値の新しい提案

- 人間：持ち時間10分＋秒読み60秒、加算0。エンジン：持ち時間0分＋秒読み5秒、加算0。人間の短い切れ負けを避けつつ、エンジンのホスト期限を短く定義する今回の候補値。G2や前案の時計を既定値として引き継がない。双方別の時計を指定でき、KIF再開でその値が使われることを対象版の画面で確認できなければ開始しない。
- エンジンへ `wtime 0 byoyomi 5000` が渡る場合、現行設定の内部上限は3000ms、目標は2250ms。この計算は読み取りによる予算式の検算であり計測ではない。ShogiHome側5秒より内部上限が早いため、外部stopより先の応答が十分あり得る。この時計案は外部停止を誘発する保証ではない。
- 「エンジンの時間切れあり」OFFを必要条件とし、人間側の時間切れ判定は残る。Ponderや時計・方針・ログなどの設定変更は実施開始承認に含めず、必要な具体的変更と復元をまとめて提示する。
- 対局1局、対象局面1つ、対象 `go` 1回。追加着手・再試行・時計の段階的短縮・別局面・追加起動はしない。自動連続対局と自動棋譜保存を誘発しない設定・保存先を確認する。
- `go` から最大30秒までを観察する。ホスト `stop` が送られた場合は、その時点から最大15秒、かつgoから30秒までの早い方を応答待ちの打ち切りとする。bestmove受信後は3秒間を重複応答の監視期間とし、その期間を含め受信後最大10秒で盤面・棋譜・手番を照合する。10秒で照合できなければ判定保留とする。これらは今回新設する管理値で、応答保証ではない。

## 証拠・判定・終了と復帰

同一セッションの `position`、時計付き `go`、ShogiHome発 `stop`、その後の `bestmove` をログで照合する。時計・設定・監視画面を補助証拠として、外部stopがエンジン側の時計期限と対応する状況を記録する。ログだけでホスト内部タイマーの厳密な発火時刻やエンジン内部の停止原因まで証明しない。

合法性は対象局面の独立再生と合法手一覧で照合する。同じ手が一回だけ棋譜・盤面へ反映され、人間の手番で通常対局が続き、予期しない終局がないことを確認する。単なる応答受信・画面だけの停止表示では成立としない。

| 結果 | 扱い |
| --- | --- |
| `stop` より先にbestmove | 外部時計停止未観測。内部期限停止か自然な全探索完了かは判定しない |
| `stop` → 合法bestmove → 一回の反映・人間手番 | この一回のShogiHome時計期限によるstop経路を観測した候補。本人が証拠束で受け入れを判断する |
| stopなしで30秒、stop後の待ち上限、重複・不合法・予期しない終局・画面不一致 | 未成立または判定保留。追加着手・再試行・手入力はしない |

応答後の画面・ログ確認を終えたら、時計停止とエンジン回収のため、別の後片付けとして対象版の「対局中断」を一回使う案とする。これは上記固定版の中断終局経路に基づき、観測対象stopと区別する。結果棋譜へ中断が追記され得ることを記録し、保全先と操作を事前合意する。未応答の打ち切り時も同じ終了案を事前合意しておく。実際の画面が不一致、確認ダイアログが想定外、または反応しない場合は未知操作・強制終了へ進まず、監視のセッションと時計の残存を報告して本人へ引き継ぐ。

終了時にセッション0と時計停止を確認し、別名棋譜・必要範囲のログを保全する。ログと変更したアプリ設定を採取前値へ戻し、保存・再起動後の反映とUSI/CSAセッション0を確認する。未保存棋譜のため再起動できなければ復帰未完了と記録し、次の起動を行わない。

後片付けの有限上限も今回の候補値として定める。中断操作後30秒で時計停止・対象セッション終了を確認できなければ、その時点で復帰未完了として操作を止める。棋譜保全、元設定の保存、アプリ再起動と反映確認は各段階60秒まで、観察終了から後片付け全体で最大5分とし、先に達した上限で止める。保存失敗・想定外ダイアログ・再起動不能時は繰り返し操作せず、現在の棋譜保存状態、設定の保存値と反映状況、アプリとセッション・時計の残存を読み取って本人へ引き継ぐ。ログや棋譜の削除、強制終了、未承認の保存先変更を行わない。上限を越えて本人判断を待つことは、完了や自動復帰と扱わない。
