# 40手目の長考：調査範囲の具体案

## 状態と目的

2026-10-11作成。具体案は本人の「ok」により承認され、限定読取り調査を実施済み。実施結果は[学習記録](../learning/long-think-scope-design.md)へ保存した。本人の「40手の将棋に設定したせいでは」という仮説は未検証のまま保持する。選定の背景は[引き継ぎ](../handover-long-think-scope.md)、既存の観察は[前テーマの実施記録](../learning/two-ply-final-check.md)を参照する。

対象は再試行一局の40手目、USIログの `go` 送信から `bestmove` 受信まで28.407秒だった一応答。40手上限による終局と、応答所要時間が長くなった原因を分けて説明するための調査範囲を決める。今回の待ちは本人が許容済みで、その判断は変更しない。前テーマはmain統合・検証・最後の理解確認まで完了済み。

## 既存証拠から言えること

以下は承認後に照合したログ・棋譜・ソースコードの読取り結果である。実行時の追加計測や再現は行っていない。

- USIログsid=2の40手目では、`position` と `go btime 447569 wtime 578975 byoyomi 30000` が同じ記録時刻15:22:47.252、`bestmove B*9d` は15:23:15.659。差は28.407秒。38手目は `go` 15:22:38.355、`bestmove 4b3c` 15:22:38.771で0.416秒。両応答の間に指し手2つが加わっており、局面などが違うため統制比較ではない。
- 40手目の `bestmove` 後に `gameover draw`、`quit`、終了コード0。CP932のKIFは40手目が後手の角打ち、41手目が持将棋を記録する。これは上限到達時の終局の証拠であり、28.407秒の原因の証明ではない。
- 試行時HEAD `7cdf338` と調査開始HEAD `7ebd2c9` の間に `kaname_shogi` の変更はない。USI受付は `position` で棋譜を再生し、その後の `go` で合法手列挙と方針選択を同期的に呼ぶ。[受付](../../kaname_shogi/usi_engine.py)・[局面再生](../../kaname_shogi/usi_position.py)・[二手選択と合法手列挙](../../kaname_shogi/movegen.py)を参照。
- `go` に含まれる時計値はUSIエンジン内で時間制御に使わず、40手上限を設定するUSI項目や分岐も確認できない。最大手数設定そのものがエンジンへ直接渡り、40手目の探索を長くする経路は見つからなかった。ただしエンジンは毎回の `position startpos moves ...` の履歴全体を再生する。39手目後は37手目後より2手分長い履歴となる。アプリは `position` と `go` を同一ミリ秒で記録しており、エンジン内部ではコマンドを順に処理するため、この再生がログ上の `go` 送信→`bestmove` 受信差にどれだけ含まれるかは分からない。

- 画面反映までの待ち、全時計表示、起動時Python版、他アプリ負荷は欠測。ログ差分・KIF消費時間・画面待ちは同じ測定量ではない。

## 方法の選択肢

1. **保存証拠と関連処理の読取りだけ（推薦）**：上限設定が処理へ影響する経路と、局面による処理量増加の経路を絞る。再現性や所要時間の内訳までは実証できないが、新しい対局や長い実行を伴わない。
2. **同一局面で上限だけ変える比較**：上限の影響をより直接比較できる可能性がある。ただしアプリ操作、時計・送信内容・負荷の統制が必要。今回は承認対象に含めず、必要性を報告して別案を作る。
3. **処理区間別の再計測**：局面再現・合法手生成・二手比較などの時間を分けられる可能性がある。ただし計測用処理や再実行が必要で、観測による負荷も生じる。今回は承認対象外。

## 推薦案の対象と手順（今後の実行承認対象）

承認を得た場合も、以下の読取り調査一回で止める。

1. 対象HEAD、ランチャーと関連ファイルの変更履歴を確認し、試行時HEAD `7cdf338` と現在の関連処理が同じか照合する。異なれば現在コードで当時を説明せず、当時版を読む。checkout変更や製品変更はしない。
2. USI原本 `/Users/oki2a24/Library/Logs/electron-shogi/usi-20261011_151708.log` のsid=2に限定し、起動・方針設定、38手目と40手目の `position`・`go`・`bestmove`、40手目後の終局コマンドを読む。38手目は隣接した対照資料であって統制された比較ではない。他18応答の再集計やsid=1の分析へ広げない。
3. [再試行KIF](../records/two-ply-usability-check-2026-10-11-retry.kif) の設定と39手終了時点の指し手履歴を、40手目を指す直前の `position` と照合する。誤時計の別棋譜は混ぜない。手数欄と手番、40手目の着手前後を区別する。局面再現プログラムは実行しない。
4. ランチャー、USIコマンド受付、局面再現、一手選択、二手比較、そこから呼ぶ合法手・詰み判定の関連箇所だけ読む。上限・時計・手数等の情報がどこから届き、どの分岐や繰返しへ影響するかを参照箇所付きで整理する。リポジトリ全体の品質レビューや高速化案には広げない。
5. 下表の支持・反証・不足を報告する。未解決なら、必要な最小の追加確認案を示すだけで終了する。調査結果を学習記録へ保存し、独立レビュー・文書検証後に通常コミットする。main統合は別承認。

原本は読取りのみ。削除・上書き・外部送信なし。報告に必要な対象行だけ出典位置とともに残す。原本が読めない、sidや局面が一致しない、試行時コードを特定できない場合は、その不一致を報告して停止し、代替対局や推測による補完をしない。

## 将来比較が必要になった場合の設計境界

この節は追加案を作るための条件であり、比較実行の承認対象ではない。

- 上限比較なら、同じ39手終了時点の局面・履歴・手番、同じエンジン版・Python・方針・Ponder OFF・時計入力・PC条件を保ち、上限40と40より大きい上限の一条件だけを変える。局面入力と `go` の実送信内容も比較する。途中局面開始時のアプリ手数解釈が不明なら先にその確認案を作る。
- 同じコマンド列をエンジンへ直接送る確認はアプリを除いた処理の切り分けになるが、上限40対別上限のアプリ比較そのものにはならない。
- `go` 送信→`bestmove` 受信を既存結果との比較区間とし、プロセス起動・局面再現・一手選択の区間は別記する。画面反映は別測定。時計値や初回起動等を変えた結果は同条件の比較へ混ぜない。
- 一回の再現・不再現だけで支持・棄却しない。回数、実行順、乱数、上限秒数、停止方法、保存先を具体化し、本人承認を得るまで実行しない。既存の30秒という使用感基準を、原因判定の閾値へ転用しない。
- ShogiHomeを操作する案に進む場合は、その時点で[接続スキル](../../.agents/skills/shogihome-connection/SKILL.md)と[手順書](../shogihome-connection-guide.md)の停止条件、現在画面、未保存棋譜、設定復帰を確認する。今回はアプリを開かない。
