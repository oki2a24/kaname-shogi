# 引き継ぎ：ShogiHomeの「対局中断」経路を資料から整理する条件だけ

## 最終目標

新しいセッションで、ShogiHomeの「対局中断」経路を**資料から整理する条件だけ**を一テーマとして進める。ShogiHomeの画面操作とUSIの終了・中断コマンドの対応について、一次資料と現行リポジトリ文書を照合し、何を資料から言えるか、仮に後日実機確認するなら何を観測条件にするか、何が未確定かを明らかにする。

このテーマの成果物は条件案までとする。ShogiHome・エンジンを動かして経路を確認する作業は含めない。

## 完了事項と意思決定の背景

### 今回の完了範囲の合意

- 二手先読み方式の実装・CLI/USIからの選択・限定的な利用確認は完了している。[方向性](02-project-direction.md)、[タスク5最終確認](learning/two-ply-final-check.md)。
- 時計予算・探索停止・USIの入力並行処理も実装・検証・理解確認まで完了している。[時計・停止接続記録](learning/input-concurrency-usi-plan.md)。
- 直近の直接USI時計期限テーマでは、時計付き `go` の後、ホストから通常 `stop` を送らずに合法な `bestmove` を一度受信した。flushを起点とした外部計測では7.5秒の目標に対して7.5427875秒後の応答で、「設定した目標期限以後の応答と整合」と判定した。停止理由は出力されず内部で完成行を読んだ時刻も測っていないため、内部期限が応答の原因だとは直接証明していない。[直接USIの実施・学習記録](learning/direct-usi-clock-deadline-conditions.md)。
- 本人は二手先読みと時計の両テーマについて、**「学習・実装テーマの区切りとしては完了にでき、ShogiHomeの実機挙動や一般的な時間保証まで確認済みとは扱わない」**という整理を了承した。新テーマはこの完了範囲を拡張する必須条件ではなく、未検証のShogiHome対局中断経路を資料で整理して境界を明確にする最後の小テーマという位置付け。
- 本人は次テーマ「ShogiHomeの『対局中断』経路を資料から整理する条件だけ」を選び、新セッションの準備を依頼した。これは条件案の作成を始める指示であり、実機確認・エンジン起動・設定変更・ログ採取・計測・テスト、またはmainへの取り込みを承認したものではない。

### 過去資料にある経路の手掛かり

[通常停止の条件整理記録](learning/shogihome-normal-stop-conditions.md)は、当時確認したShogiHome v1.28.2の公式ソースについて、対局中断操作が `store.stopGame()` から `gameManager.stop()`、`end(INTERRUPT)` へ進み、プレイヤーの `gameover()` 通知を行う経路と記録している。同記録では、USIプレイヤーの `gameover()` と `close()` がそれぞれ `usiGameover`、`usiQuit` へ対応すると整理している。一方、実際の通信列は採取しておらず、画面操作による通常 `stop` と同一経路とは扱っていない。

同じ記録は、エンジン時間切れの設定に応じた時計期限の `stop`、検討機能の解析停止、通常対局の中断を別経路としている。これらは特定バージョンの過去の資料照合結果であり、現行ShogiHomeの仕様・実画面・実通信を保証しない。次のセッションでは現行の一次資料と対象版が特定できる公式ソースを確認し直す。

以前の「通常停止」テーマでは、通常対局画面のどの操作がUSI `stop` を送るかを資料上で確定できず、実施条件は成立しなかった。直接USIでの通常停止観測もShogiHome経路の証拠にはならない。[当初の条件案](plans/2026-10-13-shogihome-normal-stop-conditions.md)、[実施条件不成立の記録](learning/shogihome-normal-stop-conditions.md)。今回の「対局中断」も通常 `stop` の代替として仮定しない。

## 対象範囲と成果物案

1. 現行のShogiHome利用者向け資料と、対象版を示す公式リリース・タグ付きソースがあればそれを確認する。可変ブランチのコードとタグ付きコード、利用者向け説明と実装の記述を区別し、資料名・版・参照日・該当箇所を記録する。
2. 「対局中断」「通常対局の `stop`」「時計期限」「検討・解析中断」「終局後の `gameover` / `quit`」を区別する。資料に操作・送信・受信・棋譜/画面遷移の一部しか書かれていない場合、残りを推測で埋めず未確定として示す。
3. 既存のkaname-shogi実装・検査が確認するコマンド契約を読み取り専用で照合する。テスト名だけからホスト画面・USI通信・棋譜反映まで保証すると解釈しない。テストは実行しない。
4. 条件案では、資料上の判定対象、代表的な画面状態・経路、もし後日実施するなら必要になる送受信・画面・棋譜・プロセスの証拠、合法応答をどう扱うか、有限の停止・復帰条件、本人が結果を判断する方法、未検証事項を示す。資料だけでは中断経路を再現可能な形で定義できないと分かった場合も、無理に実施案を作らず「資料では条件不成立/保留」として終了する。
5. 作業案は `docs/plans/2026-10-13-shogihome-interruption-conditions.md` を候補とし、既存ファイルと命名を確認してから決める。条件案を独立レビューし、文書リンク・差分を検証して本人へ提示する。条件案そのものへの明示承認を待つ。

この選定は、実機で試す承認ではない。ShogiHomeの新規起動、画面操作、対局・局面選択、設定変更・保存・再起動、ログや棋譜の取得、エンジン起動、USI通信観測、時計計測、コード・テスト・設定の変更、テスト実行を行わない。後日の実施を提案するときは、条件案提示後の別の明示承認を得る。mainへの取り込みも別承認とする。

過去テーマの局面、時計値、上限時間、起動数、再試行条件、保存先、ShogiHome状態は今回に自動適用しない。資料照合だけのテーマなので、実際の試行値を決める必要がある場合は値を事実や承認済み条件として書かず、将来の条件案における未決事項として扱う。
