# テストの検出力と範囲を点検する

## 考え方

2026-10-10、本人は詰み優先テストの必要十分性の点検後、この考え方を今後の開発フローへ取り込むよう依頼した。テスト成功やメソッド数だけで十分性を判断せず、「誤った実装でも偶然成功しないか」を確認する。[今回の実例と補強](../learning/two-ply-mate-priority.md#必要十分性の点検と補強)を根拠とする。

有限個のテストだけで全入力への正しさを証明したとは扱わない。十分性は合意した契約・想定した誤り・対象範囲に対して説明する。

## 開発フローへの取り込み

1. **計画・テスト作成前**：対象の振る舞いごとに、守る契約と検出したい具体的な誤りを挙げる。期待値は製品の採点・比較結果から作らず、仕様や独立した検算から決める。
2. **ケース選定**：役割や視点の反転、順序・位置、値の符号・境界、入力の有無など、対象処理が依存する条件を点検する。該当する条件と誤りに対応する小さな代表例を選び、不要な全組合せや大規模なファズ基盤を前提にしない。
3. **検出力確認**：実処理で成功したことに加え、リスクに見合う代表的な誤りを隔離コピー等へ入れ、意図したアサーションのFAILと復元後成功を確かめる。読み込みエラーを検出成功に含めない。既存実装による初回Greenと未実装Redを区別する。
4. **単独と全体の区別**：単独テストでは検出しないが既存テスト全体では検出する誤りを区別する。共通処理の既存検証を再利用しつつ、条件固有の分岐や組合せには固有のテストが必要か判断する。検出しない誤りは隠さず、補強するか理由付きで後続へ残す。
5. **レビュー・記録**：独立レビューへ「契約／代表ケース／検出できる誤り／他テストによる補完／未検証」を渡す。Refactor要否と検証・誤り注入結果を記録し、十分性の主張を証拠の範囲に限定する。計画更新・承認・回帰検証・main統合の既存規則を省略しない。

テストを増やす判断基準は件数ではなく、現実的な誤りを新たに検出できるかである。自動生成検査やファズ検査は、入力空間・独立した期待値・保守費用に見合う場合に別途検討する。

## 今回の適用例

| 契約 | 条件 | 検出対象 |
| --- | --- | --- |
| 詰みの勝ちを通常点より高くする | 開始側先手/後手、相手持ち歩百万枚 | 勝ち通常点化、詰み無視、先手固定、後手開始だけの詰み無視 |
| 詰みの負けを通常点より低くする | 開始側先手/後手、詰ませる応手群の先頭/中間/末尾 | 負け通常点化、詰み無視、先頭/末尾だけの評価、max、先手固定、後手開始だけの詰み無視 |

評価の組と100万点の比較は任意整数への実験的証明ではない。勝敗区分を先に比較する設計の理由と、具体的な誤実装を検出する実験を合わせて説明する。
