# ShogiHomeでの平手対局確認

## 確認できた範囲

2026-10-04、Mac版ShogiHome 1.28.1で平手対局を行った。第59回は人間先手・後手 `kaname-shogi` で、人の７六歩・２六歩にエンジンが４四歩・９二飛と応じ、人間の投了で終局した。第60回は人間（息子）先手・エンジン後手で、息子の19手とエンジンの18応手を棋譜上で確認した。息子が投了操作をしていない状態で、最後の人の手 `☗４一金` の後にエンジン側の番で自動的に「投了」終局したが、その時点ではUSI通信ログを取っていなかった。

第61回では第60回の37手までのKIFを開き、37手目を画面で選択したことを確認して「現在の局面」から対局した。USIログのsid=2で、ShogiHomeからの37手の `position` と時間付き `go` に対し、エンジンが `< bestmove resign` を返し、その後ShogiHomeが `> gameover lose` と `> quit` を送り、プロセス終了まで記録された。ログ原本は `/Users/oki2a24/Library/Logs/electron-shogi/usi-20261004_201234.log`、全通信の転記と画面・棋譜の記録は[第61回学習記録](../learning/61-shogihome-auto-resign-logs.md)にある。

このログは、第61回の再現局面・ShogiHome 1.28.1・設定で一度観測した実通信である。第60回の実通信を遡って示すものではなく、他局面、他の終局理由、他バージョンにも同じ送受信列が必須だとは結論しない。

## 設定上の注意

第59回の設定画面では `USI_Ponder` が既定ONと表示された。ローカル `usi_engine.py` は `go ponder` に未対応として拒否するため、第59・60回はPonderをOFFにした。第61回のログにも `> setoption name USI_Ponder value false` が記録された。Ponder ON時の通信・挙動は未確認である。

ShogiHome登録エンジンは、過去にアーカイブ済みworktree内のランチャーを指して `ENOENT` となったため、第60回に `/Users/oki2a24/kaname-shogi/kaname-shogi-usi` へ登録し直した。第61回でもこの登録先を画面で再確認した。worktreeや作業ディレクトリが変わった後も同じパスが有効だとは決めつけず、ShogiHome上で確認する。

第61回ではUSI通信ログだけを観察中ONにし、ShogiHomeを再起動してから記録した。観察後はOFFへ戻し、再起動後の設定も確認した。ShogiHomeの通常の監視画面は稼働中セッションの補助確認に使えるが、終了済みセッションの履歴は残らない場合があるため、USI通信の主証拠はログ原本とする。プロンプトへ手動コマンドは送っていない。

第69回ではShogiHome 1.28.1からSFEN局面をエンジンへ渡し、一手応答を確認した。画面貼り付け後、人間先手・エンジン後手の一局を持ち時間10分・秒読み30秒で開始し、USIログに `position sfen ...`、時間引数付き `go`、`bestmove 9a9b` が順に記録された。棋譜にも後手の `☖９二香` が反映された。入力は手数4の4欄SFENだったが、ShogiHomeが送った `position sfen` の手数欄は1だった。この一局面の実測を、他版・全局面・SFEN付き指し手履歴の実機互換性へ一般化しない。実測の履歴は[第69回学習記録](../learning/69-shogihome-sfen-engine.md)を参照する。

公式ShogiHome 1.28.1と固定依存tsshogi 2.3.4では、局面読込で入力手数4を保持せず、USI生成時に読み込んだ開始局面のSFENへ手数1を付ける。この経路は第69回の一局面の実測と一致する。盤面・手番・持ち駒は保たれ、平手初期配置へ戻る意味ではない。kaname-shogiが受信後に局面データだけをエンジン状態へ渡す処理とは別の境界である。現行説明と固定版公式ソースは[SFEN知識](sfen-position-notation.md#shogihome-1281のsfen貼り付けと手数の境界)、調査の履歴は[第70回学習記録](../learning/70-shogihome-sfen-move-number.md)を参照する。

時計について、第69回で持ち時間0・秒読み0の開始を試みたところ、ShogiHomeは「持ち時間と秒読みが両方とも0です」と拒否した。現在の運用では0＋0を時計なし・無制限と扱わず、開始を試す前に持ち時間または秒読みが正の値であることと本人が合意した具体値を画面で確認する。先後で異なる設定なら双方を確認する。値が未合意・不適切、またはアプリが開始を拒否した場合は停止し、変更する具体値を本人と合意する。詳細と固定版の根拠は[接続手順書の時計条件](../shogihome-connection-guide.md#時計条件)を参照する。10分＋30秒はこの一回で開始できた値であり、既定値・推奨値として固定しない。

USIログ設定は保存直後でなくアプリ再起動後に現在のプロセスへ反映される。第69回では調査後にOFFで保存したが、未保存の結果棋譜を残すため再起動しなかった。この場合は次回再起動まではログ出力が続く可能性があるため、設定が実際にOFFへ反映される前に別のエンジンセッションを起動しない。再起動が未保存棋譜を失わせる場合は、棋譜を無断で保存・破棄・再起動せず、設定が未反映であることを報告して止める。

## SFEN付き履歴で確認した一例

2026-10-09、第75回にMac版ShogiHome 1.28.1で２手後SFENから先手の２六歩を追加し、後手kaname-shogi（Random、Ponder OFF）の一応答を確認した。時計は双方5分＋60秒・加算0という今回の合意値で、既定・推奨値ではない。エンジン時間切れありは既存OFFを保持し、双方無制限とは扱わなかった。

当該USIログには `position sfen ... b - 1 moves 2g2f`、`go btime 294099 wtime 300000 byoyomi 60000`、`bestmove 6a5b` が記録された。既存の局面解析・合法手列挙で、SFENに追加手を適用した局面と応答の合法性を照合し、画面・棋譜でも２六歩と５二金右を確認した。通常中断後の `quit` とプロセス終了を確認したが、他の終局の必須通信列とはしない。

未保存だった既存棋譜と今回の結果は、本人が承認した別名へ保存して保全した。ログOFF保存・再起動後の三種OFF・USIセッション0を確認して復帰を終えた。入力手数3と送信手数1、棋譜内手数、エンジンの再現結果の手数2は別の情報である。詳細は[SFEN知識](sfen-position-notation.md#shogihomeのsfen付き指し手履歴確認した一例)と[第75回学習記録](../learning/75-shogihome-sfen-moves-verification.md)を参照する。SFEN開始の確認と、平手初期局面から１手以上の履歴を条件とするKIF再開は区別する。結果をKIF保存したことは、そのKIFからの対局再開を確認した意味ではない。

## 確認していないこと

- ShogiHome 1.28.1以外の版、macOS以外のOS、他の局面・終局理由での通信。
- Ponder ON、時間管理の精度、全USIコマンドとの互換性。
- SFEN手数の扱いについての作者の設計意図、当時のインストール済みアプリと公式ソースの完全な同一性・実行中の内部状態、他版・他形式での手数保持の保証。固定版公式ソースの経路と第69回の一例の一致とは区別する。
- 第59・60回のUSI通信ログ。両回の対局内容は画面と棋譜で確認したが、コマンド列を記録していない。
- 第59・60回の棋譜ファイル出力。これらはShogiHome内の画面・棋譜で確認し、ファイルには保存・エクスポートしていない。第61回の一時KIF再現とは別の記録である。
- 第61回の結果から導く、すべての対局での後続コマンドの必須順序。
