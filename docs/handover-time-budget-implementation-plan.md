## 今回の計画へ引き継ぐ合意

### 設定

JSON形式。予定保存先はリポジトリ直下config/time-management.json、Git管理、起動時に一度読んで実行中固定、作業ディレクトリに依存しない。今回はそのファイルを作らない。欠落・不正・読込不能ならstderr診断と非0終了、コード内の代替既定値は設けない。起動入口への接続作業までこの小範囲へ含めるかは、全体の入力/探索変更を先取りしないよう計画案で明示する。

| キーと意味（すべて設定データ） | 許容範囲 | 採用済み暫定値 |
| --- | --- | --- |
| allocation_turns：配分用固定手番数 | 整数1以上 | 20 |
| maximum_multiplier：上限倍率 | 有限数1超 | 2 |
| byoyomi_target_ratio：秒読み目標割合 | 有限数0超1未満 | 0.75 |
| response_margin_ms：応答余裕ms | 整数0以上 | 2000 |

四項目必須。項目欠落・重複キー・未知項目・数値の代わりの真偽値を拒否。JSONCは本人が先送りを選んだためJSONを維持。Python更新で対応するという予測はしない。値は安全・最適・検証済みとは呼ばない。

### 計算

自分側の残り時間R、秒読みB、固定手番数N、倍率M、割合q、余裕S。時間はms、1ms未満切捨て。

R>0：基本目標=floor(R/N)、時計境界=max(0,R+B−S)、最終上限=min(floor(基本目標×M),時計境界)、最終目標=min(基本目標,最終上限)。

R=0：最終上限=max(0,B−S)、最終目標=floor(最終上限×q)。両時間0なら予算0。Rが正の間は基本配分を優先し、GUIが0を報告した手番で切替える。わずかな正数で目標が非常に短く、0で急増し得る点は了承済み。

例えばB=30000ms、暫定設定で、R=600000なら目標30000/上限60000ms、R=60000なら3000/6000、R=10000なら500/1000、R=0なら21000/28000。各手30秒以下や時間内応答を保証する式ではない。

配置案：予定time_management.pyにTimeManagementConfig（時間設定データ）とSearchBudget（時間予算データ）、読込・計算の操作。具体API、数値精度方式、巨大な有限値の計算表現、パス基準の具体化は計画内で検討する。合意した許容範囲を無断で狭めたり、式を変更したりしない。表現上の問題で契約変更が必要なら理由と案を提示して本人判断を待つ。

### 後続範囲との境界

全体では主担当が現在スレッド、入力読取りが別スレッド、探索がgoごとの別スレッド。命令/故障を主担当へ受け渡し、入力読取りは内部終了通知で待機解除・回収する。部分入力でreadline待ちに戻らない。go行の読取り時刻を渡して受渡し/回収待ちも計時する。具体入力方式はmacOS対象、他OS移植時の待機・読取り・回収箇所を文書と将来コードへ記載する本人指示あり。今回の設定/配分計画で入力機構を実装しない。

探索は戻り値で中断を明示し、LegalMovesResult（合法生成結果データ）、CheckmateResult（詰み結果データ）、CandidateEvaluation（候補評価結果データ）を区別。根生成で目標到達し予備手があれば中断、未確保なら最初の合法手/手なし確定まで続行する通常停止例外あり。未確定の歩打ちを予備手にしない。完了候補だけ比較。quit/EOF/gameover/エラーは応答抑制し未確保例外なし。送信完了と担当回収を分け、ロック外で終了待ち。これらは承認済み全体設計との整合確認用で、この小範囲へ実装を拡張しない。
