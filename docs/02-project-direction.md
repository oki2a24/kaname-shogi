# プロジェクトの方向性

## この段階で決めたこと

`kaname-shogi` は、将棋の内部処理を自分で理解しながら実装していくプロジェクトです。

盤面、駒、指し手、合法手の判定、対局の進行、そして将来の探索などは、学習の中心として自作します。一方で、将来的に既存の将棋GUIと接続できるよう、広く使われているUSIをエンジンとGUIの通信方法として採用する方向です。SFENは局面を文字列で表す標準的な形式として扱います。

これは「インターフェースは既存の標準に合わせ、中身は自分で作る」という考え方です。USIやSFENへの対応は必要になった段階で進め、最初からすべてを実装することは求めません。

## 最初のゴール

最初の実装上の到達点は、コマンドラインで動く非常に弱い将棋プログラムです。

強さやGUI対応より先に、次のような基本を理解しながら形にすることを重視します。

- 将棋の盤面と駒を扱えること
- 駒の動きと基本的な対局ルールを学び、プログラムに反映すること
- 局面を表示し、手を選べること
- 小さくても対局の流れを最後まで動かせること

この段階では、完全な強さや実戦的な指し手は目標ではありません。「なぜその処理が必要か」を説明できることを優先します。

## 段階的な発展の見通し

順番や内容は実装を通して見直しますが、今はおおよそ次の流れを考えています。

1. 将棋のルールを学びながら、CLIで動く最小の対局プログラムを作る。
2. 合法手の扱いと対局の進行を整え、弱くても一貫して指せるようにする。
3. 局面を評価し、簡単な探索を導入して、少しずつ強くする。
4. USIに対応し、既存の将棋GUIから対局できるようにする。
5. 息子と対局したり、成長を比較したりできる形へ育てる。

各段階で立ち止まり、理解・楽しさ・必要性を確かめます。後の段階を理由に、最初のプログラムを必要以上に複雑にはしません。

## 第32回完了時点の見直し

玉が王手を受けているか、手番側に合法手があるか、詰みで終局かを最小範囲で判定できるようになった。次は、既に実装した駒打ちと詰み判定を組み合わせる打ち歩詰めを小さなルールとして扱う。その後にCLIでの指し手入力と対局進行へ進み、終局時に入力を止める流れを作る。

## 第33回完了時点の見直し

持ち歩で解除不能な王手をかける打ち歩詰めを拒否できるようになった。打ち歩詰め確認中の合法手探索は、打ち歩詰め確認だけを無効にする内部経路で循環を避け、二歩・行き所のない駒・王手放置などの既存規則は維持する。次はCLIでの指し手入力と対局進行へ進み、局面を表示しながら終局時に入力を止める流れを作る。

## 第34回完了時点の見直し

独自の `move` / `drop` 形式で入力を解析し、合法手適用、エラー理由の表示と同じ手番での再入力、局面表示、詰み時の勝者表示と入力停止までを、先手・後手とも人間が入力するCLI対局ループとして実装・テストした。標準入力から合法な指し手を複数手入力し、局面が更新されてEOFで終了する人間対人間プレイも確認した。ただし、詰みまで実際に指し続ける確認はまだである。公式対局の反則負けを再現するのではなく、学習用に入力を局面変更前に検証できる構成を選んだ。次は詰み以外の終局理由を小さく追加する候補を検討する。

## 第35回完了時点の見直し

CLIで半角ASCIIの `resign` を受け付け、手番側の投了と相手の勝利を表示して局面を変更せず終了できるようにした。詰みは入力前に優先し、EOF/Ctrl-Cは勝敗にしない。投了は局面だけから判定できない入力イベントなので、`is_game_over(position)` は詰みだけを判定する責務のまま維持した。次は、CLIで進んだ指し手と局面を保存・再現する「棋譜・局面の保存」を小さく検討する。

## 第36回完了時点の見直し

開始局面と成功した `move` / `drop` の履歴を `GameRecord` に分離して保持し、現在局面を独立複製で参照できるようにした。`position_at` は履歴を開始局面へ再適用して任意手数の局面を再現する。CLIは記録を経由して対局を進め、詰み・投了・EOF・Ctrl-Cで記録を返す。ファイル保存・SFEN・USIは先取りせず、内部の局面・指し手表現を固める段階に留めた。次は保存内容をファイルへ永続化するか、標準形式であるSFEN/USIへ進む候補を比較する。

## 第37回完了時点の見直し

`GameRecord.save(path)` と `GameRecord.load(path)` により、開始局面と成功手を専用JSONファイルへ保存し、読込時に既存の合法手適用で現在局面を再現できるようにした。現在局面を重複保存せず、JSONの構造・型・駒種・座標・持ち駒・履歴を検証してから再適用するため、壊れた記録や不合法な手順を受け入れない。CLIの自動保存・保存読込コマンド、SFEN、USIは先取りしていない。

第37回後に最初の目標との距離を見直した。現在のCLIは先手・後手とも人が入力するため、SFENやCLI保存読込より先に、コンピュータが合法な一手を選べることが必要である。次は評価・探索を先取りせず、合法手を列挙して弱い自動指し手が一手を選ぶ最小の土台を扱う。その後に人間対コンピュータのCLI進行を別テーマとして検討する。

## 第38回完了時点の見直し

`BoardMove`、`DropMove`、`Move` を、局面を変えない中立な一手データとして追加した。`legal_moves(position)` は、既存の局面適用規則を複製局面へ試すことで、全合法手を固定順のタプルとして返す。`choose_weak_move(moves, rng)` は局面を受け取らず、その一覧から注入された乱数生成器で一手を選ぶだけに責務を絞った。これにより、将来の評価・探索や外部将棋エンジン接続は、必要になった時点で別の選択器として追加できる。

最初の目標である「弱くても対局できるCLI」へ最短で進む次の小テーマは、人間とコンピュータの担当手番を定め、既存の入力処理と弱い選択器を対局ループへ接続することである。USI/SFENや評価・探索は先取りしない。

## まだ決めていないこと

以下は、これから検討・設計する事項です。

- 使用するプログラミング言語と開発環境
- 盤面、駒、持ち駒、指し手をどう表すか
- どのルールを最初の対象範囲にするか
- 局面の表示や入力の方法
- テストの進め方
- USIとSFENを導入する具体的な時期と範囲
- 探索、評価、強化の方法
- 公開方法とライセンス

これらは、実装を始める前に必要な範囲で一つずつ決めます。この文書は設計を固定するものではなく、判断の出発点です。
