# kaname-shogi

## プロジェクト概要

将棋のルールを学びながら、小さな段階で育てる自作の将棋プログラムです。強さや完成速度よりも、各処理が必要な理由を説明できることを優先します。息子と将棋を通じて成長を共有することも目的です。

## まず試す

Python 3.14以上が必要です。対局にはPython標準ライブラリだけを使うため、追加パッケージの導入は不要です。リポジトリを取得して、ルートディレクトリから起動します。

```sh
git clone https://github.com/oki2a24/kaname-shogi.git
cd kaname-shogi
python3 --version  # 3.14以上であることを確認
```

確認した版が3.14未満なら、Python 3.14以上を用意し、`python3` がその版を指すようにしてください。3.14以上なら、次のコマンドで起動します。

```sh
python3 -m kaname_shogi
```

## できること

### CLIでの対局

平手の初期配置から、次の形式で対局できます。

1. 人間対人間
2. 人間対コンピュータ（先手が人間、後手がコンピュータ）
3. コンピュータ対コンピュータ

盤上移動、成り・不成、駒取り、持ち駒、駒打ち、二歩、行き所のない駒、王手、自玉を王手にさらす手の禁止、詰み、打ち歩詰め、投了を扱います。持ち駒は盤の上と下に分けて表示します。人間の手番では局面と指し手履歴をJSON形式で保存し、後から読み込んで再開できます。

コンピュータが参加する対局では、次の方針を選べます。未指定時はランダムです。

- **ランダム**：合法手から選びます。
- **一手駒得**：一手指した後の盤上と持ち駒の参考点数差を比べます。
- **二手先読み（駒得）**：自分の一手と相手の応手を読み、相手から見て最も有利な応手を考慮します。

起動後に対局形式を1〜3から選び、コンピュータが参加する場合は方針も選びます。人間対人間では方針を尋ねません。選択は一局中固定です。盤は先手視点で、左から9〜1筋、上から一〜九段です。`+` は先手、`-` は後手、`・` は空マスを表します。日本語を表示できる等幅フォントの端末を想定しています。

### USIエンジン

USI対応アプリから起動する専用エンジン入口があります。標準入出力から直接起動する場合は、リポジトリ直下で次を実行します。

```sh
python3 -m kaname_shogi.usi_engine
```

ShogiHomeで使う場合は、[開発環境をセットアップ](#別pcでの開発環境セットアップ)してから、リポジトリ直下の `kaname-shogi-usi` を実行ファイルとして登録します。[接続手順書](docs/shogihome-connection-guide.md)に手順と確認条件があります。

- `position startpos moves <1手以上>` と `position sfen <SFEN>`（指し手履歴の追加も可）から局面を再現します。`position startpos` 単独には対応していません。
- `Difficulty` 設定で `Random`・`Material`・`TwoPlyMaterial` を選べます。未設定時は `Random` です。
- SFENは構文と内部モデルで表現できることを検査しますが、駒総数や実戦で到達可能な局面かどうかは検査しません。

### 開発用の探索比較

一つのSFEN局面を、二・三・四手の全幅読みとαβ枝刈り付き探索で比較できます。リポジトリ直下で実行します。

```sh
python3 -m kaname_shogi.search.compare --sfen "8k/9/9/9/9/9/9/9/K8 b - 1"
```

評価は開始側から見た駒得差と詰み優先です。各方式の評価値・選択手（USIと日本語）・訪問回数、および評価一致と最善候補への所属を表示します。同点なら既存の合法手生成順で最初の最善手を選びます。訪問回数は探索本体へ入った回数で、合法手生成・詰み判定内部の確認局面は含みません。

この玉だけの例の二手探索は、両方の評価が0、訪問は全幅13回・αβ9回です。通常対局で選べる三方式とは別の開発用コマンドで、反復深化・時間制限・定跡は使いません。駒や合法手の多い局面では四手でも長時間かかるため、小さい局面から使ってください。SFENは履歴を持たず、千日手等の履歴判定は行いません。

反復深化の比較は、次の専用コマンドで実行します。

```sh
.venv/bin/python -m kaname_shogi.search.compare_iterative --sfen "8k/9/9/9/9/9/9/9/K8 b - 1"
```

深さ1〜4の各完了結果を全幅探索と比較し、単独αβの訪問回数・反復の今回分・完了した深さまでの累計を表示します。前回の最善手は同じ開始局面で次の深さを調べる順序にだけ使います。玉だけの例では今回分が4・9・29・64、累計は4・13・42・106です。累計には確認用探索と中断した反復の訪問を含めません。開始局面に合法手がなければ深さ1で終了し、確認用探索で中断した場合は反復完了と比較未完了を分けて表示します。時間制御・通常対局への接続・深さ指定オプションはありません。詳細は[探索比較メモ](docs/knowledge/search-comparison.md)を参照してください。

### 時間制御付き反復探索を一回試す

制御付き反復探索の動きを見る専用開発用コマンドです。SFEN、最大深さ、目標期間、上限期間を明示し、一回の探索結果として終了状態・選択手とその由来・最後に完了した反復の記録を表示します。

```sh
.venv/bin/python -m kaname_shogi.search.run_controlled_iterative \
  --sfen "8k/9/9/9/9/9/9/9/K8 b - 1" \
  --max-depth 4 --target-ms 50 --maximum-ms 100
```

`--max-depth`は1以上、期間は整数msで `0 ≤ target-ms ≤ maximum-ms` を指定します。期間は予算として探索へ直接渡します。上限期間は実応答時間や期限内の完了を保証する値ではありません。開発用コマンドは通常対局やUSIへ接続せず、既存の対局方式と比較コマンドを変更しません。終了状態と結果の意味は[探索停止メモ](docs/knowledge/search-stop.md)を参照してください。

探索部品は既存の時間制御を使い、停止時に合法予備手または最新の完了結果を返します。抑制時は選択手を返さず、以前に完了した記録を保持する場合があります。

結果は標準出力、診断は標準エラーへ出します。終了コードは成功0、比較不一致1、入力不正2、Ctrl+C中断130。内部例外は原因を追えるよう伝播します。中断時は完了済み行を残し、実行中は未完了と表示します。詳しくは[設計](docs/plans/2026-10-17-engine-search-comparison-design.md)と[学習・実装記録](docs/learning/engine-improvement-stage-design.md)を参照してください。

## 制約と確認範囲

- **未対応:** 千日手、持将棋、入玉、通常対局CLIの時間管理、自動保存、反則による勝敗判定。
- **エンジンの強さ:** 評価方式は同点候補からランダムに選ぶことがあります。通常対局の方式は二手までです。開発用比較の二〜四手探索も、対局棋力の向上を保証するものではありません。
- **コンピュータ同士の対局:** 手数上限はありません。詰み、合法手なし、または `Ctrl-C` で停止します。
- **ShogiHome:** Mac版1.28.1・1.28.2の限られた局面と設定で確認しました。TwoPlyMaterialの平手対局一例では20回応答し、最大約28.4秒でした。時計動作や応答時間の上限、他の局面・版での互換性は保証しません。詳しくは[使用感確認の記録](docs/learning/two-ply-final-check.md)と[時計付き停止の確認記録](docs/learning/clock-stop-real-check-conditions.md)、[USI応答の仕様](docs/knowledge/usi-engine-response.md)を参照してください。

## CLI操作

人間の手番では、次のコマンドを入力できます。

対局中に `help` と入力すると、コマンドの書式と短い説明を表示します。表示後は同じ手番で入力を続けられます。

```text
help
```

表示される操作は、盤上の駒を動かす `move <出発筋> <出発段> <到着筋> <到着段> [+]`、持ち駒を打つ `drop <歩|香|桂|銀|金|角|飛> <筋> <段>`、`resign`、`save <path>`、`load <path>` です。`+` は成りを指定し、筋・段には全角数字も使えます。パスは空白を含まない一語です。保存成功後は同じ手番を続け、読込成功後は読み込んだ局面から再開します。

### 盤上の駒を動かす

```text
move <出発筋> <出発段> <到着筋> <到着段>
move <出発筋> <出発段> <到着筋> <到着段> +
```

最後の `+` は成りを指定します。例えば、先手の歩を７七から７六へ動かす入力は次のとおりです。

```text
move 7 7 7 6
```

### 持ち駒を打つ

```text
drop <歩|香|桂|銀|金|角|飛> <筋> <段>
```

例えば、歩を５五へ打つ入力は次のとおりです。

```text
drop 歩 5 5
```

### 投了する

```text
resign
```

投了した側の相手を勝者として表示し、局面と棋譜の指し手履歴を変更せずに終了します。コンピュータは投了しません。

### 棋譜を保存・読込する

```text
save records/game.json
load records/game.json
```

パスは空白を含まない一語で、相対パスと絶対パスを指定できます。保存先の親ディレクトリは自動作成しません。保存成功後は同じ手番を続け、読込成功後は読み込んだ局面を表示して、その局面の手番から続けます。

保存・読込の失敗、入力形式の誤り、不合法手は理由を表示し、局面・手番・履歴を変更せず、同じ人間手番で再入力を求めます。詰み、投了、EOF、`Ctrl-C` などで対局が終了した後は入力を受け付けません。

操作語と成りの `+` は半角です。区切りと筋・段には半角・全角の空白・数字を使えます。実装はPythonの `str.split()` を使うため、その他のUnicode空白も区切りになります。

## テスト

リポジトリ直下で次を実行します。

```sh
python3 -m unittest discover -s tests -v
```

テストメソッド名は検索や個別実行に使える英語とし、日本語docstringで確認する振る舞いと検出したい誤りを説明しています。`-v` を付けると、その日本語説明も表示されます。

## 別PCでの開発環境セットアップ

Python 3.14以上（`venv`・`pip`を利用可能な環境）、Git、初回パッケージ取得用のインターネット接続が必要です。セットアップ対象OSはmacOS/Linuxです。実測環境はmacOS 27.0.1 arm64・CPython 3.14.8と3.15.0で、LinuxとWindowsネイティブは未実測です。Windowsと別Git worktreeへの導入は今回の対応範囲に含みません。

```sh
python3 --version  # 3.14以上であることを確認
git --version
git clone https://github.com/oki2a24/kaname-shogi.git
cd kaname-shogi
python3 scripts/setup_dev.py
.venv/bin/ruff format --check .
.venv/bin/ruff check .
python3 -m unittest discover -s tests -v
```

すでにcloneしている場合は、そのリポジトリへ移動してセットアップコマンドから実行します。スクリプトは `.venv` の作成、`requirements-dev.txt` に固定したRuffの導入、バージョン確認、`git config --local core.hooksPath .githooks` を行います。グローバルのPython環境やGit設定は変更しません。既存フックとの競合は上書きせず停止します。依存関係の取得に失敗した場合も、フックを新たに有効化しません。

セットアップに使う `python3` がPython 3.14以上か、実行前に必ず確認してください。HomebrewのCPython 3.15を選ぶ場合は、実行ファイルを明示できます。

```sh
"$(brew --prefix python@3.15)/bin/python3.15" --version
"$(brew --prefix python@3.15)/bin/python3.15" scripts/setup_dev.py
```

`.venv` とローカルGit設定はcloneで引き継がれません。PCごと・cloneごとに実行してください。`.venv` を別PCへコピーせず、同じ手順で作成します。セットアップは再実行可能ですが、既存の `.venv` のPythonは切り替えません。Pythonを更新するときは、旧 `.venv` を削除せずclone外または別名へ退避し、選ぶ版の実行ファイルからセットアップを行います。失敗時は新しい `.venv` を別名へ退避して旧環境を元の `.venv` へ戻します。移行中は `/usr/bin/python3`、全体PATH、ShogiHomeの保存済み登録設定を変更しません。

### 日常の整形・検査とコミット

```sh
.venv/bin/ruff check --select I --fix .
.venv/bin/ruff format .
.venv/bin/ruff check .
git diff
python3 -m unittest discover -s tests -v
# 内容を確認して対象をgit addし、git commitする
```

Ruffの対象はPythonファイルです。行長88・Python 3.14（`py314`）を対象とし、リンターは `E4,E7,E9,F,B,I,UP,PIE,RUF024,RUF026,RUF100` を有効にしています。`B` はflake8-bugbear由来の、既定引数のリスト共有など気付きにくい誤りを検査するルール群です。型検査や将棋ルールの正しさの保証ではありません。B追加の理由と検証は[Bの学習記録](docs/learning/ruff-bugbear-rules.md)、import順序を統一するIの追加は[Iの学習記録](docs/learning/ruff-import-order.md)を参照してください。importの自動整理は整形の前に実行し、差分を確認します。追加ルールの選定は[追加検査の記録](docs/learning/ruff-practical-rules.md)を参照してください。unsafeな自動修正は一括適用せず、指摘の意図と影響を個別に確認します。

Ruffの厳格化はいったんここで区切り、現設定を基準として維持します。実際の不具合、繰り返すレビュー指摘、用途変更があった場合に、対応するルールを個別に検討します。Ruff更新時は診断と整形差分を確認します。判断理由と更新手順は[品質検査の運用方針](docs/knowledge/python-quality-checks.md#ルール追加と更新の方針)を参照してください。

通常の `git commit` では、**ステージした全Pythonファイルと設定**を一時領域へ複写し、整形とリンターの両検査を実行します。未ステージの変更と未追跡ファイルは検査に混ぜません。失敗するとコミットが止まるので、修正・差分確認・再ステージしてから再試行してください。フックは自動修正や再ステージ、パッケージ取得を行いません。Pythonファイルや設定のシンボリックリンクは拒否します。Gitの `--no-verify` で回避する運用は採用しません。

フック設定と固定版の確認：

```sh
git config --local --get core.hooksPath
.venv/bin/ruff --version
```

期待値は `.githooks` と `ruff 0.16.10` です。フックの検査は単体テスト・レビューの代わりにはなりません。

### 手動構築と環境の再作成

スクリプトが行う主要な操作は次のとおりです。既存フックがある場合は、統合方法を決めてから設定してください。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/ruff --version
git config --local core.hooksPath .githooks
```

Python更新やディレクトリ移動で `.venv` が動かなくなった場合は、使用中の仮想環境を終了し、`.venv` を削除せず別名へ退避してセットアップを再実行してください。退避先は既存の名前と重複させないでください。スクリプトは壊れた環境や既存ファイルを自動削除しません。Linuxで `venv`・`pip` がない場合は、利用するPython配布元の手順で用意してから再実行してください。

設計理由・検証・レビューは[開発環境整備の記録](docs/learning/ruff-local-quality-gate.md)、実装計画は[Ruff導入計画](docs/plans/2026-10-09-ruff-local-quality-gate.md)を参照してください。

## 名前について

`Kaname` は、息子の名前「要」に由来します。「全体を支える大切なところ」という意味も、このプロジェクトが少しずつ積み上がっていく姿に重なります。
